## Головні правила безпеки

1. **Ретранслятор керує справжнім генератором.** До етапу 2 (розділ D) — лише читання: «Дозволити команди» на картці
   генератора вимкнено (так за замовчуванням). Жодних тестів команд на ретранслятор, крім протоколу D.
2. **Один генератор — одна Odoo, що керує.** Команди дозволено або на тестовому сервері, або на проді, ніколи в обох
   одночасно (інакше розклади й таймери двох Odoo перекриватимуть один одного). Опитування (читання) з двох Odoo
   одночасно — допустиме.
3. **Копія проду на тест — лише з нейтралізацією** (розділ G): інакше копія почне опитувати ретранслятор і надсилати
   команди разом із продом.
4. **Стоп-крани без релізу:** «Заборонити команди» (миттєво, жоден POST) і «Опитувати ретранслятор» (вимикає забір і
   розклад) на картці генератора; cron «Генератори: …» — Налаштування → Технічні → Заплановані дії.
5. **Кожна команда етапу 2 — лише з людиною біля генератора, на зв'язку телефоном з оператором Odoo.** Автомати
   генератора й мережі (розмикання мережі знеструмлює офіс) на тестуванні не чіпаємо.

## A. Передача модуля

### A.1. Звідки брати і як викласти

Джерело — каталог `smartgen/td_genset` репозиторію `tnizhnikovskyi-todo/todo_timur`, гілка
`claude/dreamy-ramanujan-p2wlej`, коміт `166db7e` (у каталозі — код, дані, переклади `i18n/uk_UA.po`, тести,
`README.md`, `CHANGELOG.md`; нічого збирати не потрібно). Два варіанти:

1. **Стандарт ToDo для `td_*` (рекомендовано):** скопіювати каталог у репозиторій модулів компанії як
   `custom_addons/td_genset`, гілка `18.0-td_genset-<автор>` → PR у тестову гілку проєкту → після рев'ю ведучий
   розробник вручну викладає на сервер (репозиторій → сервер → «Оновити список застосунків» / `-i` / `-u`).
   Перед кожним викладанням — резервна копія бази і розбір попереджень у лозі.
2. **Без репозиторію компанії** (якщо для тестового сервера його немає): скопіювати каталог `td_genset` (архів або
   `rsync`) у будь-який каталог з `addons_path` сервера, власник — користувач служби Odoo. Новий шлях в `addons_path`
   потребує перезапуску сервера; копія в наявний каталог `custom_addons` — ні.

`__pycache__` не копіювати. Після викладання: Застосунки → «Оновити список застосунків» → у пошуку «Генератори».

### A.3. Перед установкою

1. Резервна копія бази тестового сервера (стандарт ToDo перед релізом) — записати ім'я файлу й час у протокол.
2. Якщо тестову базу щойно відновлено з проду — переконатися, що копію нейтралізовано (розділ G).
3. Повідомити команду: установка модуля перезавантажує реєстр (секунди), простою немає.

**Матриця ролей (B.4)** — категорія «Генератори» у картці користувача (обирається один рівень):

| Хто | Група | Може |
| --- | --- | --- |
| Співробітники офісу, черговий | Генератори: Співробітник | бачить усе; таймер «Робота поза графіком»; «Прийняв» — якщо в ланцюжку; експорт «Показань»/«Подій» (група дає «Доступ до експорту» — README, «Права») |
| Офіс-менеджер / завгосп | Генератори: Адміністратор | + розклад і дні-винятки; паливо: каністри, надходження, заправка |
| Тех. відповідальний (інженер) | Генератори: Тех. адміністратор | + пульт, автомати, «Дозволити команди», ТО (закриття заявок), налаштування модуля, генератори; отримує «Обслуговування: менеджер» |
| Системний адміністратор | Налаштування (base.group_system) | адреса й токен ретранслятора |

Користувач `Administrator` (`base.user_admin`) отримує «Тех. адміністратор» автоматично при встановленні — за потреби
зняти. Генератори, показання, події й тривоги бачать користувачі **усіх 5 компаній** (рішення 1.3, record rules немає);
обладнання й заявки ТО створюються в компанії генератора, команда ТО «Генератори» — спільна (без компанії).

**Передпольотна перевірка (B.6)** — на сервері Odoo, лише GET-запити, токен не потрапляє в історію shell і в звіт.
Скрипт — один файл `smartgen/tools/preflight_relay.py` того самого коміту (лише стандартна бібліотека Python 3.8+),
скопіювати на сервер; запускати Python-ом Odoo (тоді перевіряється й `pytz`):

```bash
export TD_GENSET_RELAY_URL='https://gen-relay.todo.ltd/api/v1'
read -rs TD_GENSET_RELAY_TOKEN && export TD_GENSET_RELAY_TOKEN          # вставити токен, Enter
/шлях/до/venv-odoo/bin/python3 preflight_relay.py --hostid 3130373031334717003D002E \
    --psql 'host=<pg-host> dbname=<база> user=<користувач>'               # --psql — необов'язково
unset TD_GENSET_RELAY_TOKEN
```

Код виходу 0 — «ГОТОВО до етапу 1»; 1 — «НЕ ГОТОВО» з причинами (мережа, TLS, 401, модуль не на зв'язку, годинник,
`pytz`/PostgreSQL без `Europe/Kyiv` …). Окремий рядок — готовність етапу 2 з боку ретранслятора (`commands_enabled`,
`commands_ready`, блокування на контролері). Звіт додати до протоколу.

**Примітка про регламент ТО (B.8).** Якщо мотогодини генератора вже більші за «Перше ТО» (типово 30; на 07.10 у
«Садової» ≈ 35), одразу після першого забору модуль створить заявку «ТО-1 після обкатки» і попередження «Термін ТО».
Якщо обкатку вже пройдено — вказати в «Перше ТО» мотогодини наступного планового ТО (або інтервал за регламентом
сервісу) **до** ввімкнення опитування.

## C. Етап 1 «тільки читання» (мінімум 24–48 год)

### C.1. Увімкнення

Картка генератора → вкладка «Підключення» → **«Опитувати ретранслятор»** (тех. адміністратор) → «Оновити дані».
«Дозволити команди» лишається вимкненим: пульт показує «Команди вимкнено в Odoo…», жодного POST на ретранслятор.

Що буде в перші хвилини: забір щохвилини; перший забір ставить курсор на перший знімок не старший за «Починати
історію з» і доганяє історію сторінками по 500 знімків (до 10 сторінок за запуск cron). Ретранслятор зберігає знімки
з 07.10.2026 (180 днів), тож на тестовому сервері догон — кілька днів історії (≈ 1 500 знімків на добу), до 1–2 хв.
Повні 30 днів — ≈ 43 000 знімків ≈ 87 сторінок ≈ 9 запусків cron, ≈ 2,5 хв обчислень (замір ревю) плюс мережа:
ретранслятор 1.1.1 віддає оми датчиків лише в сирому образі (`raw=1`, трафік ≈ ×5) — разом ≈ 5–10 хв. Під час
догону події створюються заднім числом, тривоги й сповіщення — ні; після догону стан оцінюється один раз.

## D. Етап 2 «бойове тестування керування» (справжній генератор)

### D.1. Умови — усі обов'язкові

1. Спостерігач на об'єкті біля генератора й панелі контролера; телефонний зв'язок з оператором Odoo **весь час**
   кроків 3–5 і 7 (гучний зв'язок).
2. Офіс попереджено: можливі короткі перемикання живлення (крок 4б), час вікна — робочі години, не під час
   критичних робіт офісу.
3. Мережа є («Є мережа», «Живлення: Мережа»), відключень за графіком у вікні не очікується.
4. Генератор справний: огляд спостерігачем, паливо ≥ 50 % (≥ 70 L), АКБ ≥ 24 V, активних тривог контролера немає,
   блокування дистанційного керування на контролері вимкнено.
5. Етап 1 пройдено (C.4); розклад порожній, таймер і тест не запущені; у застосунку SmartGen ніхто не керує під час
   сесії (або попереджені).
6. Команди дозволено **лише на тестовому сервері** (на проді модуля ще немає або його стоп-крани вимкнено).

### D.2. Як працюємо

Перед кожним кроком оператор каже: «Крок N, надсилаю <команду>», спостерігач відповідає «готовий». Після кроку обидва
кажуть, що бачать (Odoo / панель). Будь-який сумнів спостерігача — крок зупиняється (D.3). Протокол — D.7.

Перед кроком 1: оператор знову запускає `preflight_relay.py` (етап 2 — «готово»), перевіряє картку (Онлайн, режим
Авто, мережа є, без банера блокування), натискає вкладка «Підключення» → **«Дозволити команди»** → у діалозі
«Дозволити команди на справжній генератор?» → «Так, дозволити команди». У чатері з'являється «Команди дозволено
(<ім'я>) …» — записати час у протокол.

**Важливо про «стан за розкладом».** Після кінця тесту чи таймера модуль повертає генератор у стан за розкладом;
розклад порожній — це «поза вікном», тобто пакет **«Ручний + Стоп»**: генератор лишається в режимі Стоп і **сам не
запуститься при відключенні мережі**. Тому після кожного кроку оператор повертає звичайний стан офісу — **«Авто»**.

### D.3. Стоп-умови й аварійні дії (для всіх кроків)

| Ситуація | Ознака | Дії |
| --- | --- | --- |

логи, мережа). Телефони — у таблиці ролей.

### E.2. Перенос на прод

Ті самі кроки A–D, відмінності:

1. **Спершу — тестовий сервер:** на картці генератора «Заборонити команди» і вимкнути «Опитувати ретранслятор»

2. Вікно установки — низьке навантаження (напр., вечір); установка — секунди, без перезапуску (якщо шлях addons
   не новий); резервна копія бази проду перед установкою (стандарт ToDo), розбір попереджень у лозі.
3. Код — тим самим шляхом (A.1, той самий коміт або PR з тестової гілки в продову), «Встановити».
4. Адреса й токен — **той самий ретранслятор** `https://gen-relay.todo.ltd/api/v1`; токен — той самий або окремий
   для проду (питання F.4); вводить системний адміністратор проду.
5. Користувачі й групи — прод; ланцюжок ескалації — чергові проду; генератор — у компанії-власниці.
6. Сповіщення: перші 1–2 доби — попередження й інформація «Лише в чаті» (Генератори → Налаштування → Налаштування, блок «Сповіщення»),
   критичні — як погодить замовник; потім — значення за замовчуванням (ТР 2.15, п. 6).
7. Етап 1 на проді ≥ 24 год (C.2, скорочено); етап 2 — «Дозволити команди» після рішення координатора; перший тиждень
   — лише кнопки пульта під наглядом (кроки 1 і 3 протоколу D), потім розклад з погодженими вікнами. Розклад: поза
   вікном генератор у режимі «Ручний + Стоп» і сам при відключенні мережі не запуститься (так у ТР) — якщо офісу
   потрібен цілодобовий автозапуск, вікно розкладу має це враховувати (питання F.10).
8. Після виходу на прод: реєстр «Перелік технічних рішень» — статус «Виконано» з модулем і версією
   (`td_genset 18.0.1.0.0`); функціонал заморожено — лише виправлення помилок; кожна зміна — запис у `CHANGELOG.md`
   і нова версія.

### E.3. Відкат (від швидкого до повного)

### E.4. Моніторинг першого тижня на проді (щодня, ≈ 5 хв, тех. адміністратор)

- картка: «Онлайн», останній знімок свіжий; «Показання» — журнал без пропусків;
- «Події» й «Тривоги» відповідають фактам; журнал команд — без «не підтверджено»;
- лог: `grep -E "WARNING|ERROR" <лог> | grep td_genset` — порожньо або пояснено;
- Заплановані дії «Генератори: …» — активні, останній запуск свіжий;
- розмір таблиці знімків: `select pg_size_pretty(pg_total_relation_size('td_genset_reading'));` (≈ +2 МБ/добу);
- підсумок тижня — координатору.

## G. Після відновлення копії проду на тест

Після встановлення модуля на прод будь-яка копія проду містить генератор з увімкненими «Опитувати ретранслятор» і
«Дозволити команди» та токен ретранслятора. Копія,
запущена як є, **почне опитувати ретранслятор і надсилати команди справжньому генератору разом із продом** (розклад,
таймери). Тому:

### G.1. Обов'язково — відновлення з нейтралізацією

Будь-який зі стандартних способів Odoo 18:

```bash
odoo-bin db -c <conf> load --neutralize <база> <дамп.zip>            # відновлення (нова database.uuid — як копія)
odoo-bin db -c <conf> duplicate --neutralize <джерело> <копія>       # дублювання
odoo-bin neutralize -c <conf> -d <база>                               # після pg_restore тощо, ДО старту служби
```

(або менеджер баз даних → Restore / Duplicate з позначкою «Neutralize»). Нейтралізація Odoo вимикає всі cron і поштові
сервери; модуль `td_genset` (`data/neutralize.sql`) додатково: на всіх генераторах вимикає «Опитувати ретранслятор» і
«Дозволити команди», **видаляє токен** ретранслятора, вимикає cron «Генератори: …»; адреса API лишається.

### G.2. Якщо базу відновили без нейтралізації і служба Odoo ще не запускалася

Виконати в `psql` на відновленій базі **до старту Odoo** (той самий SQL, що `td_genset/data/neutralize.sql`):

```sql
UPDATE td_genset SET relay_enabled = false, commands_allowed = false;
DELETE FROM ir_config_parameter WHERE key = 'td_genset.relay_token';
UPDATE ir_cron SET active = false
 WHERE id IN (SELECT res_id FROM ir_model_data WHERE model = 'ir.cron' AND module = 'td_genset');
```

і за стандартом ToDo — вимкнути поштові сервери та інші інтеграції.

### G.3. Якщо Odoo на копії вже запущено

1. Негайно: картка генератора → «Заборонити команди» і вимкнути «Опитувати ретранслятор» (або SQL з G.2 і
   перезапуск служби).
2. Журнал команд копії (smart-кнопка «Команди»): чи були команди після часу відновлення; якщо були — повідомити
   координатора і тех. адміністратора проду (режим генератора могли змінити).
3. Записати інцидент.

### G.4. Як знову тестувати на копії

Системний адміністратор вводить токен (F.4), тех. адміністратор активує cron «Генератори: …» (Налаштування → Технічні →
Заплановані дії) і вмикає **лише** «Опитувати ретранслятор» — читання з двох Odoo допустиме. «Дозволити команди» на
копії — **ніколи**, поки команди дозволено на проді (правило 2).
