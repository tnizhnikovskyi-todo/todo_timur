## (д) Порядок кроків і готові промпти
Правила тесту — у `CLAUDE.md` (ТЕСТОВИЙ РЕЖИМ). Один крок = одна гілка `flow/<крок>-test` і один PR; PR мержить лише людина або AI за її явним повідомленням (merge-комітом); поки PR не злито, наступний крок стартує від гілки попереднього кроку (ланцюжок гілок, у `inputs` SHA = HEAD гілки старту), злиття не вимагається; рішення гейтів A-17 і A-18 — окремо. Після кожного кроку читай `tests/reports/<ім’я наряду>[-<спроба>].md` (A-23-spisok.md, A-23.md, A-04-1.md, A-04-2.md) (`result`, `checks`, `memo` — спершу «Невпевнений:»).

**Який наряд брати:** у репо з історією (напр. «меблі») після `bootstrap --upgrade` чинний наряд — з найбільшим номером спроби `<крок>-N.yaml` (напр. `A-15-6.yaml`, `A-17-3.yaml`; список друкує bootstrap); `<крок>.yaml` без номера — старий наряд 0.3.x, його не брати. Нижче `A-15.yaml`/`A-17.yaml` читати як «наряд найбільшої спроби». **Виняток — контур коду 1 (Крок 0 нижче):** `A-15-N.yaml` (refresh) не брати, бери `A-15-full.yaml`.

**Крок 0 перед A-16b (репо з уже зібраним стендом, напр. «меблі»):** спершу звір `ls package/addons | grep -E 'td_(home_menu|support|knowledge)'`: якщо модулів немає на поточній гілці, але вони є в іншій гілці `origin` (для «меблів» `flow/A-12-2-test`) — перейди на неї (або злий її), а не йди маршрутом «§27 не злито». Далі порівняй код із SHA гейтів з `package/CHECKS.md`: `git diff --quiet <SHA CHECKS.md>..HEAD -- package/addons package/config package/master-data ':!package/addons/td_*_elearning/*' ':!package/config/manifest.yaml' ':!package/config/CONFIG.md'`. Код 0 (гейти чинні; застаріла мітка стенда / стенд не піднятий) -> окремий наряд `A-15.yaml` (refresh) і гілка, далі A-16b. Код 1 (модулі/конфіг/дані змінено після гейтів) -> `A-11-fix.yaml` (версія `td_<галузь>_knowledge`; перший) -> `A-12-fix.yaml` -> `A-14-N.yaml` (найбільша спроба) -> `A-15-full.yaml` (повний перепідйом з новими модулями, НЕ refresh) -> `A-16-N.yaml` (найбільша спроба; повтор турів) -> A-16b. Refresh не робити в гілці A-16b і не робити, якщо CHECKS.md оновлено в цьому ж контурі. У контурі A-12 fix внести в «Модулі до установки» також `td_knowledge` (ce+ee) і `td_<галузь>_knowledge`, якщо вони є в `package/addons` (рядок AI-NN); версію `td_<галузь>_knowledge` нарядом `A-11-fix.yaml` підняти до `19.0.<X.Y пакета>.0`; `td_knowledge` версію має власну. Якщо складових §27 (`td_home_menu`, `td_support`) у `package/addons` ще немає — A-16b знімає без них і пише рядок AI-NN «§27 не злито; після злиття — контур A-12 fix -> A-14 -> A-15 -> A-16 -> A-16b refresh» (власник — вето); питання власнику не потрібне. **Оновлення наявного репо з історією нарядів («меблі») до 0.4.0** (робить власник набору, не сесія): стартувати з гілки, де лежить історія (для «меблів» — `flow/A-12-2-test`, а не `main`/`repo.base_branch`), і запустити `bootstrap.sh <репо> --upgrade`: CLAUDE.md і TEST-START.md перегенеруються (у т. ч. рядки `flow/decisions.md` вносить AI за E6, недоступний скіл організації — не зупинка, а рядок у `observations/`), відсутні наряди (A-15, A-17b…) додадуться, а наряд зі застарілим `skill_ref` (напр. A-17 з 0.3.1) отримає нову спробу `<крок>-<N+1>.yaml` (`attempt: N+1`, гілка `flow/<крок>-<N+1>-test`; N — найбільша спроба серед нарядів і звітів), старі наряди й звіти не чіпаються. Звіт нової спроби — `tests/reports/<крок>-<N+1>.md`. Без прапорців `bootstrap.sh` наявні файли не змінює; `--force` перезаписує шаблони з `attempt: 1` — лише для нового репо.
