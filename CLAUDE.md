# CLAUDE.md

## Репозиторий

- `factory3d/` — 3D-модель мебельного предприятия и модули Odoo 19 `td_*` (`factory3d/odoo_addons/`: 11 основных
  модулей и мосты). Имена по стандарту компании: модули `td_<область>`, модели `td.*`, поля `td_*`,
  параметры `td.<область>.<параметр>`; карта старых имён (`factory3d_*`, `f3d.*`) — `factory3d/build/RENAME.md`.
  Документация: `factory3d/docs/` (индекс — `docs/README.md`). Сборка модулей: `factory3d/build/`.
- `luxsite/`, `odoo_graph/` — отдельные проекты, к factory3d не относятся.

## Бюджет: правила экономии лимита

Расход ≈ размер контекста × число обращений к модели. Каждый вызов инструмента перечитывает весь контекст.
Держи контекст коротким, а шагов мало; состояние храни в файлах, а не в истории чата.

- Сначала Grep, потом Read нужного диапазона строк. Файл до ~200 строк можно читать целиком.
- Не перечитывать неизменённый файл. Не читать файл «для проверки» после Edit.
- Вывод команд всегда ограничивать: `| tail -30`, `| head -60`, `grep -E "FAIL|ERROR|Traceback" -A 15`.
  Полный лог Odoo в контекст не выводить никогда.
- Независимые Read/Grep — параллельно в одном ходе.
- Веб-поиск — только если ответа нет в репозитории. Документацию Odoo — WebFetch с конкретным вопросом.
- Браузерные MCP — текстовый снимок страницы; скриншот только для проверки визуала.

## Документация factory3d: только кусками

`SPEC.md` модулей — 160–590 KB (до ~150k токенов), `ARCHITECTURE.md` модулей — 70–120 KB.
**Никогда не читать их целиком.** `docs/CONSISTENCY.md` целиком не читать: решения уже внесены в модульные документы.

- Оглавление с номерами строк: `grep -nE '^#{2,3} ' factory3d/docs/modules/<m>/SPEC.md`
  (`<m>` — каталог модуля: `td_factory3d`, `td_viewer3d`, `td_telemetry`, … `td_genset`).
- Раздел или модель: Read с `offset`/`limit` по номерам строк из оглавления
  (модели — `### M-05 …`, представления — `V-xx`, API — `API-xx`, правила — `R-xx`).
- Критерии приёмки: `grep -nE '^\| AC-(1[0-9]|2[0-4]) ' factory3d/docs/modules/<m>/SPEC.md`
- Конвенции для всех модулей: `factory3d/docs/ARCHITECTURE.md` §5; контракты — нужный подраздел §6.
- План сборки модуля (воркеры, файлы, разделы SPEC, порядок слияния): `docs/modules/<m>/ARCHITECTURE.md` §6.

## Агенты и модели

- `coder` (Sonnet) — реализация, тесты, рефакторинг, git-операции. Всё, что больше ~30 строк или 2 файлов.
- `scout` (Haiku) — поиск по коду и документации, только чтение.
- Opus — планирование, приёмка, решения; не пишет большие объёмы кода сам.
- Задача агенту самодостаточна: цель и критерий готовности; файлы, которые можно менять; разделы и ID SPEC,
  которые читать; команда теста; ответ ≤15 строк без кода и диффов.
- Параллельно — только независимые задачи, не больше 3 агентов. Неудачный результат — уточнение тому же агенту
  (SendMessage), а не новый агент.
- Приёмка — тестом и `git diff --stat`, а не перечитыванием изменённых файлов.

## Odoo

- Тесты — скриптами `factory3d/tools/odoo/` (их создаёт шаг 0 менеджера, см. `factory3d/build/MANAGER.md`):
  `run_tests.sh <db> /<module>:<TestClass>`. Скрипт печатает только итог и ошибки.
- Исходники Odoo не читать целиком: Grep по конкретному addon, Read 50–100 строк вокруг совпадения.
