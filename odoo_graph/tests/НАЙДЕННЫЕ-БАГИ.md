# Находки тестов

Ошибки, которые вскрыли тесты. Код `odoo_graph.py` намеренно не правился:
каждая находка закрыта тестом с `@unittest.expectedFailure`, поэтому набор
проходит зелёным, а при починке помеченный тест начнёт падать как
`unexpected success` — это и будет сигналом снять метку.

| № | Что | Критичность | Тест |
|---|---|---|---|
| 1 | домены в виде списков не разбираются | высокая | `test_domain_requirements.DomainRequirementsTest.test_list_style_domain` |
| 2 | падение на расширениях с разным `inherit_name` | средняя | `test_issues_views.XpathCollisionTest.test_mixed_inherit_name_does_not_crash` |
| 3 | пустое представление `<data></data>` не распознаётся | низкая | `test_issues_views.EmptyViewTest.test_paired_empty_data_tag` |
| 4 | `competing_writer` сравнивает значения без нормализации | средняя | `test_issues_actions.CompetingWriterTest.test_values_are_compared_normalized` |
| 5 | `norm_value` не снимает пробелы внутри кавычек | низкая | `test_norm_value.NormValueTest.test_padding_inside_quotes_is_not_stripped` |

---

## 1. `domain_requirements` не понимает домен, записанный списками

**Что не работает.** `DOMAIN_TRIPLE_RE` требует, чтобы тройка условия была
в круглых скобках. Домен, сериализованный списками — а именно так его
записывает веб-клиент Odoo и любой код, прошедший через `json.dumps`, —
не разбирается вообще.

**Вход.**

```python
domain_requirements('[["x_state","=","done"]]')   # -> {}
domain_requirements("[('x_state','=','done')]")   # -> {'x_state': {'done'}}
```

**Ожидалось.** Оба написания одного и того же домена дают одинаковый
результат `{'x_state': {'done'}}`.

**Последствие.** Проверка `unreachable_state` на таких базах слепа целиком.
Хуже того, диагноз подменяется: поле-условие с доменом
`[["x_approval","=","approved"]]`, значение которого никто не выставляет,
попадает в отчёт как `unreachable_gate` («негде заполнить»), хотя настоящая
причина другая — значения `approved` не пишет ни одно действие. Если в поле
при этом что-то пишется, проблема исчезает из отчёта совсем и превращается
в `invisible_result`.

## 2. `find_issues` падает на расширениях с незаполненным `inherit_name`

**Что не работает.** Ключ словаря `by_base` — пара `(inherit_id,
inherit_name)`, и он сортируется: `sorted(by_base.items())`. Если два
расширения ссылаются на одно и то же базовое представление, но у одного
`inherit_name` пустой, сортировка сравнивает `None` со строкой.

**Вход.** Снимок с двумя представлениями `mode="extension"`,
`inherit_id=500`, у первого `inherit_name=None`, у второго
`inherit_name="sale.order.form"`.

```
File "odoo_graph.py", line 381, in find_issues
    for (base_id, base_name), views in sorted(by_base.items()):
TypeError: '<' not supported between instances of 'str' and 'NoneType'
```

**Ожидалось.** Отчёт строится, оба расширения попадают в одну группу
`xpath_collision_risk` — имя базового представления это подпись для
человека, а не часть идентичности базы.

**Последствие.** Анализ обрывается целиком: не строится ни один отчёт.
`fetch_live` всегда заполняет `inherit_name` вместе с `inherit_id`, поэтому
на снимках из живой базы это не всплывает, но `--dump` объявлен рабочим
входом, а снимок — обычный JSON, который собирают и вручную.

## 3. Пустое расширение `<data></data>` не распознаётся

**Что не работает.** Проверка `empty_view` сверяет `arch` с регулярным
выражением `\s*<data\s*/>\s*` — только самозакрывающийся тег.

**Вход.** Представление с `arch = "<data></data>"`.

**Ожидалось.** `empty_view`: расширение ничего не меняет, а значит попадает
в отчёт независимо от того, как записан пустой тег. Парная запись
появляется, когда представление правят руками через
«Настройки → Технические → Представления», а не через Studio.

**Последствие.** Ложное молчание проверки. Критичность низкая: сама
проверка отмечена как `низкая`, потерянная запись ни на что не влияет,
кроме полноты отчёта.

## 4. `competing_writer` сравнивает значения сырыми строками

**Что не работает.** Модуль объявляет `norm_value` как способ «привести
значение из домена или действия к сравнимому виду», и проверка
`unreachable_state` так и делает. Проверка `competing_writer` (пункт 8
в `find_issues`) сравнивает значения через `str(...)` без нормализации.

**Вход.** Поле, в которое пишут два действия: привязанное к автоматизации
со значением `approved` и ручное со значением `" approved"` (лишний пробел
из формы ввода).

```
высокая | ... ставит значение ` approved`, тогда как полем управляют
          автоматизации (значения: approved) ...
```

**Ожидалось.** `средняя` — значение то же самое, логика продублирована,
но запись из согласованного состояния не выводится. Так же должны
сравниваться значения, отличающиеся регистром (`True` / `true`) или
кавычками (`approved` / `'approved'`).

**Последствие.** Завышенная критичность и неверное объяснение: отчёт
утверждает, что «значение не входит в набор автоматизаций» и «автоматизация
это уже не исправит», хотя значение то же. Внутри одного отчёта два пункта
противоречат друг другу: `unreachable_state` считает пару значений
одинаковой, `competing_writer` — разной.

## 5. `norm_value` не снимает пробелы внутри кавычек

**Что не работает.** Порядок операций — `strip()`, затем `strip("'\"")`.
Второго `strip()` нет, поэтому пробелы, оказавшиеся внутри кавычек,
остаются в значении.

**Вход.**

```python
norm_value("' done '")   # -> ' done '
norm_value(" 'done' ")   # -> 'done'
```

**Ожидалось.** `done` в обоих случаях.

**Последствие.** Значение `' done '` из домена не совпадёт со значением
`done`, которое пишет действие сервера, — проверка `unreachable_state`
сообщит о несуществующем тупике. Критичность низкая: так значения
в доменах записывают редко.
