# Ревизия проверок odoo-graph на реальных данных

Снимок: `dumps/edu-online-todo.json` (база `edu-online-todo`, Odoo 19.0, 372 модуля,
снят 2026-09-10). Прогон: `python3 odoo_graph/odoo_graph.py --dump
odoo_graph/dumps/edu-online-todo.json --out /tmp/audit-out` — все отчёты в markdown побайтово совпали с уже лежащими в
`out/` (`00-сводка.md`, `01-проблеми.md`, `impact-*.md`), то есть ревизия относится
к тому же результату, который лежит в репозитории. `graph.json` совпал по узлам и по
числу рёбер, но не побайтово: `arch_fields` возвращает `set`, и рёбра `shows`
выписываются в порядке обхода множества (в цикле «представление → кастомное поле»
в `build_graph` `sorted()` не применяется, хотя для атрибута `fields` узла —
применяется). Вывод инструмента не воспроизводим побайтово; для файла, который
кладут в репозиторий и сравнивают между прогонами, это стоит поправить одной
строкой.

Проверено 36 находок из `01-проблеми.md`. Каждая сверена с исходными записями снимка
(32 кастомных поля, 21 представление, 8 автоматизаций, 17 действий сервера,
10 правил доступа). Код не менялся.

## Разбор находок

### Подтверждены — можно отдавать как есть

**`unreachable_state`: `sale.order.x_discount_visa` никогда не получает `true`.**
Автоматизация id 4 «Віза керівника — знижка узгоджена» имеет условие
`[('x_discount_visa','=',True)]`. Среди 17 действий сервера нет ни одного с
`writes_path = "x_discount_visa"`. Поля нет ни в одном из 21 arch снимка (проверено
поиском всех вхождений `x_` во всех arch — все они внутри `<field name=...>`, регулярка
ничего не теряет). Автоматизации id 2 и id 3 гасят это же поле в `False`. Вывод верен:
ветка не запускается.

**`unreachable_state`: `purchase.order.x_visa_head` никогда не получает `true`.**
Автоматизация id 6 ждёт `[('x_visa_head','=',True)]`. Единственный писатель — действие
id 1326 «Поставити візу керівника закупівель», у него `writes_value: false` (булев
`false` в снимке). Поля нет ни в одном arch. Вывод верен. Отчёт при этом не называет
настоящую причину: действие с названием «поставити візу» пишет `false` — это опечатка
в настройке, а не архитектурное решение.

**`duplicate_placement`: `res.partner.x_todo_segment` вставлено дважды.**
Представления id 4858 (`//field[@name='function']`, `position="after"`) и id 4860
(`//field[@name='website']`, `position="after"`) оба наследуют id 127 `res.partner.form`
и оба содержат `<field name="x_todo_segment"/>`. Атрибута `groups=` в arch нет ни у
одного. Оговорка: `ir.ui.view.groups_id` в снимок не попадает вообще (в записи
представления только `id, name, model, type, mode, inherit_id, inherit_name, arch`),
а название id 4860 — «тільки для ролі». Поэтому дублирование доказано, а его охват
(все пользователи или одна роль) по снимку установить нельзя.

**`orphan_field`: `quality.check.x_todo_tehkarta`.** Поле есть в `fields_manual`
(id 24429), в arch не встречается, в доменах автоматизаций не встречается, ни одно
действие в него не пишет. Одноимённое поле на `mrp.bom` (id 24431) выведено
представлением id 4863. Домен выгрузки представлений (`arch_updated = True` ИЛИ
`arch_db ilike 'name="x_'`) захватывает и стандартные представления, если они
ссылаются на `x_`-поле, — то есть по представлениям вывод надёжен. Остаточный риск:
поле могло использоваться в домене `ir.actions.act_window`, в `ir.filters` или в
отчёте — эти слои не снимаются вовсе.

**`orphan_field`: `stock.putaway.rule.x_todo_obov`.** Подпись —
«ЗАЛИШОК ПЕРЕВІРКИ: обов'язковість». Ссылок нет нигде. Подтверждено. Этот же объект
отдельной строкой идёт как `leftover_artifact` — одна проблема, две строки в отчёте.

**`invisible_result` ×4.** `approval.request.x_needs_director` (пишет id 1322),
`hr.expense.x_over_limit` (id 1321 и id 1331), `purchase.order.x_approval_step`
(id 1319, id 1320), `sale.order.x_discount_approval` (id 1315, 1316, 1318, 1317).
Ни одно из четырёх полей не встречается ни в одном arch. Вывод верен. Он при этом
слабее реальности — см. пропуск П3: эти же четыре поля никто и не *читает*.

**`leftover_artifact` ×9.** Совпадения регулярки проверены по всем узлам: действия
id 1311 «Погодити знижку (перевірка)» и id 1356 «→ КП надіслано (перевірка рецепта)»;
поле `x_todo_obov` (совпадение по подписи, не по имени); правила id 97 «Контрагенти:
менеджер бачить своїх (перевірка)» и id 178 «Власний довідник: бачити лише свої
компанії (перевірка)» — оба с `standard: false`; представления id 4871, 4858, 4860,
4874. Все девять — реальные попадания, ни одного совпадения «на слово». Отдельно
стоит отметить, что регулярка **не** сработала на 12 представлениях с суффиксом
`.todo` в имени (`res.partner.form.migraciya.todo` и т. д.) только потому, что шаблон
требует `todo:` с двоеточием: `\btodo:`. Наименование интегратора здесь совпадает с
маркером мусора, и любое ослабление этого шаблона даст 12 ложных срабатываний сразу.

**`cross_model_field`: `x_todo_tehkarta` в 2 моделях.** `mrp.bom` и `quality.check`,
подписи совпадают, критичность «низкая», формулировка советующая («проверьте, не нужен
ли related»). Правомерно, хотя ценность низкая: копия на `quality.check` уже признана
сиротой отдельной находкой.

**`empty_view` ×2.** id 4871 и id 4874, `arch` в обоих ровно `<data/>`. Подтверждено.
У id 4874 `model: null`, из-за чего колонка «где» в отчёте пустая, — косметический
дефект отчёта, а не проверки.

### Ложные срабатывания

**`xpath_collision_risk`: `res.partner.form` — 3 расширения, `sale.order.form` — 2.**
Проверены все 11 xpath снимка: встречаются только `position="inside"` (6 раз) и
`position="after"` (5 раз). Ни `replace`, ни `remove`, ни `attributes` нет ни в одном
arch. Анкеры разные: id 4876 — `//sheet`, id 4858 — `//field[@name='function']`,
id 4860 — `//field[@name='website']`; для `sale.order.form`: id 4877 — `//sheet`,
id 4861 — `//field[@name='validity_date']`. Ни одно расширение не удаляет и не
заменяет узел, на который опирается другое, — заявленный механизм поломки
(«xpath одного перестаёт находить узел после правки другого») здесь физически
не воспроизводится. Проверка срабатывает на самом факте «расширений больше одного»,
то есть на любой базе с двумя правками одной формы. Реальная проблема в
`res.partner.form` — дубль поля — уже описана `duplicate_placement`.

**`cross_model_field`: `x_plan2_id` создано в 4 моделях.** Модели
`account.analytic.line`, `project.project`, `budget.line`, `budget.report`; тип
`many2one` на `account.analytic.account`, подписи во всех четырёх — «Напрями бізнесу».
Это ровно тот механизм, который сам инструмент распознаёт в `KNOWN_MECHANISMS`
(шаблон `^x_plan\d+_id$`) и объясняет четырьмя строками ниже в том же файле: Odoo
создаёт `x_plan{N}_id` на всех аналитических моделях при добавлении аналитического
плана. Совет «проверьте, не нужен ли related вместо копии» неисполним и неверен:
это не копия, а системный набор полей. Проверка 6 (`by_name` в `find_issues`)
не сверяется с `KNOWN_MECHANISMS`.

**`dangling_action`: «Надіслати КП — завдання на сьогодні» (id 1350).** Проверка
считает дублем любое непривязанное действие, у которого `state` совпадает с `state`
какого-нибудь привязанного действия на той же модели. На `crm.lead` привязано
действие id 597 «Створити активність «Дзвінок»» (`next_activity`, автоматизация id 1
«КП надіслано → перетелефонувати через 2 дні»). id 1350 — «надіслати КП, завдання
на сьогодні», другая по смыслу активность. `state` — это *тип* действия сервера
(`object_write` / `next_activity` / …), а не его содержание; сравнения содержания
проверка не делает.

**`dangling_action`: «Погодити знижку (перевірка)» (id 1311).** Отчёт утверждает:
«на модели sale.order уже есть действие того же типа (object_write), привязанное к
автоматизации». Привязанные `object_write` на `sale.order` — id 1315, 1316, 1318 — все
пишут в `x_discount_approval`. id 1311 пишет `writes_path: "state"`, `writes_value:
"sale"`. Это не дубль: действие принудительно подтверждает заказ. (Сам объект
опасен, но по другой причине, которую отчёт не находит, — см. пропуск П1.)

**`dangling_action`: «Поставити візу керівника закупівель» (id 1326).** Привязанные
`object_write` на `purchase.order` — id 1319 и 1320 — пишут в `x_approval_step`.
id 1326 пишет в `x_visa_head`. Разные поля, дублирования нет. Настоящий дефект этого
действия (`writes_value: false` при названии «поставити візу») отчёт не называет.

Показательна и обратная сторона того же кода: непривязанные `next_activity`-действия
id 1332 «Погодити з керівником — завдання на завтра» (`hr.expense`) и id 1351
«Погодити з фінансами — завдання» (`purchase.order`) не отмечены вообще — только
потому, что на их моделях нет привязанного действия типа `next_activity`. Одинаковые
по устройству объекты попадают или не попадают в отчёт в зависимости от постороннего
обстоятельства на той же модели.

### Дубли других находок

**`dangling_action`: «Позначити «понад ліміт»» (id 1331)** и **«Узгодити знижку»
(id 1317)**. Здесь премиса проверки случайно верна — оба пишут в то же поле, что и
привязанные действия (`x_over_limit`, `x_discount_approval`). Но именно эти два
объекта уже описаны проверкой `competing_writer`, содержательнее и с указанием
значений. В отчёте они идут двумя парами строк об одном и том же.

### Вывод верен, обоснование нет

**`competing_writer` (высокая): «Позначити «понад ліміт»» пишет в
`hr.expense.x_over_limit` в обход автоматизации.** Факт верен: действие id 1331
(`automation_id: null`, `writes_value: false`) и действие id 1321
(`automation_id: 7`, `writes_value: "True"`) пишут в одно поле. Объяснение неверно:
отчёт говорит «ручной запуск выводит запись из согласованного состояния, и
автоматизация это уже не исправит». Автоматизация id 7 имеет триггер
`on_create_or_write` и условие `[('product_id','=',32),('total_amount','>',800)]` —
она переоценивается при любой следующей записи по документу и вернёт `True`.
То есть ручное действие не выводит запись из состояния навсегда, а бесполезно
качает флаг туда-обратно (в пределах одной транзакции сработает защита Odoo от
рекурсии, при следующей записи — нет). Настоящая проблема, которую отчёт не
формулирует: действие называется «позначити «понад ліміт»», а пишет `false`, —
как и id 1326. Уровень «высокая» здесь выставлен по формальному признаку
«значение не входит в набор автоматизаций», а не по последствиям.

**`competing_writer` (средняя): «Узгодити знижку» пишет в
`sale.order.x_discount_approval`.** Факт верен: id 1317 (ручное, `approved`) против
привязанных id 1315 (`head`), 1316 (`director`), 1318 (`approved`). Но вывод
«логика продублирована в двух местах и разойдётся при первой же правке»
противоречит другой находке того же отчёта: `x_discount_visa` никогда не получает
`true`, значит автоматизация id 4 не срабатывает никогда, значит действие id 1318
никогда не запускается — и id 1317 не дубль, а единственный существующий способ
поставить `approved`. Убрать его как дубль означает оставить процесс без согласования
вообще. Отчёт не связывает две находки, хотя обе построены на одном поле.

### Недостаточно данных

**`dangling_action`: «Передзвонити клієнту через 2 дні» (id 1325).** Единственная из
шести, где премиса правдоподобна: id 597 «Створити активність «Дзвінок»» привязано к
автоматизации id 1 «КП надіслано → перетелефонувати через 2 дні», и названия совпадают
по смыслу. Но доказать дублирование нельзя: в снимке у действия сервера есть только
`id, name, model, state, usage, automation_id, writes_path, writes_value`. Поля
активности (`activity_type_id`, `activity_summary`, `activity_date_deadline`,
`activity_user_id`) не выгружаются, поэтому сравнить два `next_activity` по существу
не с чем.

## Пропуски

Отдельно проверено то, на что указывало задание, — и здесь результат обратный
ожидаемому.

**Ограничения разбора, названные в задании, на этом снимке не теряют ни одной
находки.** Измерено:

- Во всех 8 доменах автоматизаций 18 троек. Фильтр `if op not in ("=", "==")` в
  `domain_requirements` отбрасывает 10 из них: `>` — 5 раз, `<=` — 2 раза, `in` —
  3 раза. Но все 10 стоят на **стандартных** полях: `order_line.discount`, `state`,
  `amount_total`, `total_amount`, `amount`. Условий на кастомные поля во всей базе
  всего 5 (`x_discount_visa` — 3 раза, `x_visa_head` — 2 раза), и все пять
  используют `=`. Ни один вердикт `unreachable_state` / `unreachable_gate`
  не меняется. Условий с `!=` и `not in` в снимке нет вообще (при этом строка
  документации функции говорит «для операторов = и !=», хотя код `!=` выбрасывает —
  расхождение кода и описания).
- Вложенные пути через точку встречаются 3 раза, все — `order_line.discount`
  (автоматизации id 2 и 3). `.split(".")[0]` приводит их к `order_line`, который
  кастомным полем не является, — потери нет. Ни одно кастомное поле в этой базе не
  адресуется через точку ни в домене, ни в `writes_path` (все 12 непустых
  `writes_path` — плоские).
- В arch представлений `FIELD_IN_ARCH_RE` не теряет ничего: все вхождения `x_` во
  всех 21 arch находятся внутри `<field name="...">`. Вложенных доменов внутри arch
  (`domain="[('x_...','=',...)]"`, `invisible="x_..."`) в снимке нет.
- `DOMAIN_TRIPLE_RE` не поймала одну тройку за весь снимок — `(1,'=',1)` в правиле
  id 185 «All Orders» (левая часть без кавычек). Значения это не имеет: домены
  правил доступа вообще никуда не передаются (см. П2).

Вывод: три названных места в коде — реальные дефекты, но на данных этого клиента они
стоят нуля находок. Настоящие пропуски лежат в другом.

**П1. Действия сервера, пишущие в стандартные поля, выпадают из графа целиком.**
В `build_graph`, в цикле по `server_actions`, ребро `writes` создаётся только если
путь совпал с кастомным полем: `target = custom_fields.get(s["model"], {}).get(wpath)`.
Из 12 действий с непустым `writes_path` 2 пишут в стандартные поля и не получают
ребра вовсе (в `graph.json` ровно 10 рёбер `writes`). Это самые опасные объекты базы:

- id 1356 «→ КП надіслано (перевірка рецепта)» пишет `stage_id = 3` на `crm.lead`,
  а автоматизация id 1 имеет триггер `on_stage_set` и условие `[('stage_id','=',3)]`.
  Ручное действие с «(перевірка)» в названии запускает рабочую автоматизацию и
  создаёт активности на живых лидах. Отчёт находит этот объект только регуляркой
  по названию и ничего не говорит о связи.
- id 1311 «Погодити знижку (перевірка)» пишет `state = sale` на `sale.order`, то есть
  принудительно подтверждает заказ мимо штатного подтверждения и мимо автоматизаций
  id 2 и id 3, которые срабатывают только при `state in (draft, sent)`.

Ни одна из 12 проверок такую связку увидеть не может: `competing_writer` работает
только по кастомным полям, а связи «действие пишет значение, на которое настроен
триггер автоматизации» в графе нет как типа ребра.

**П2. Правила доступа не анализируются, хотя данные для этого в снимке есть.**
`domain_fields` вызывается только для `automations`; в цикле по `record_rules`
в `build_graph` создаётся единственное ребро `restricts` до модели, домен кладётся
в атрибут узла и больше не используется. Флаг `standard` читается в узел
(`standard=r.get("standard")`) и не используется **ни в одной проверке**. В снимке
два правила с `standard: false`:

- id 178 «Власний довідник: бачити лише свої компанії (перевірка)», `global: true`,
  домен `[('company_id', 'in', company_ids + [False])]` на `res.partner` — глобальное
  правило складывается по И со стандартным id 2 и сужает видимость контрагентов
  по всей базе;
- id 97 «Контрагенти: менеджер бачить своїх (перевірка)», `groups: [17]`, домен
  `[('user_id', 'in', [user.id, False])]` — ограничивает видимость контрагентов для
  группы менеджеров.

Оба попали в отчёт только потому, что в названии есть «(перевірка)». Кастомное
правило доступа с нейтральным названием было бы невидимо полностью, хотя это
изменение модели прав — обязательный пункт «Опису технічної реалізації».

**П3. Нет проверки «в поле пишут, но никто его не читает».** `invisible_result`
говорит только о представлениях. Проверено по снимку: `x_needs_director`,
`x_approval_step`, `x_discount_approval`, `x_over_limit` не встречаются ни в одном
домене автоматизации, ни в одном домене правила, ни в одном arch. То есть все четыре
поля согласования — тупики: система в них пишет, и ничто дальше по ним не ветвится.
Это существенно сильнее формулировки «пользователь не видит результат», и это
основной содержательный вывод по этой базе, которого в отчёте нет.

**П4. Нет проверки «автоматизация мертва».** Из `unreachable` уже следует, что
автоматизация id 4 «Віза керівника — знижка узгоджена» и автоматизация id 6
«Закупка: віза керівника — узгоджено» не срабатывают никогда, а вместе с ними
не запускаются привязанные действия id 1318 «Знижка узгоджена» и id 1320
«Закупка: узгоджено». Отчёт говорит это о *поле*, но не называет мёртвыми сами
автоматизации и действия — а в ТР нужен именно перечень объектов.

**П5. Флаг `active` автоматизаций не используется.** Узел его хранит, ни одна
проверка не читает. В этом снимке все 8 активны, потерь нет, но домен отключённой
автоматизации на равных участвует в расчёте `unreachable` — то есть выключенная
автоматизация способна породить находку критичности «высокая».

**П6. `meta.modules_non_odoo` не используется нигде.** В снимке перечислены
`sale_subscription` (автор «Camptocamp / Odoo», лицензия OEEL-1) и `l10n_ua`
(ERP Ukraine, LGPL-3). Ни `00-сводка.md`, ни `01-проблеми.md`, ни `impact-*.md`
их не упоминают (проверено поиском по выводу и по коду), хотя представление id 4891
«Контроль продовжень» выводит `subscription_state` и `next_invoice_date` — поля
подписочного слоя. Для заготовки «Опису технічної реалізації» сторонний модуль —
обязательный пункт.

**П7. `empty_view` распознаёт только точное `<data/>`.**
`re.fullmatch(r"\s*<data\s*/>\s*", arch)` не сработает на `<data></data>`,
`<data>\n</data>`, `<data><!-- … --></data>`, `<odoo/>`, а также на расширении,
у которого xpath есть, но он ничего не меняет. Здесь оба пустых представления
записаны буквально как `<data/>` — потерь нет, но находка держится на одном символе.

**П8. `duplicate_placement` ключуется по точному `inherit_id`.** Два расширения,
наследующие *разные* представления и оказывающиеся в одной итоговой форме
(расширение расширения), в одну группу не попадут. В этом снимке ни одно кастомное
представление не наследует другое кастомное: все `inherit_id` (127, 619, 984, 2908,
3143, 3554, 3891, 4350, 4629, 1528) лежат вне снимка, рёбер `inherits` в `graph.json`
ноль — то есть словарь `by_view_id` и тип ребра `inherits` на этих данных мёртвый код,
а проверка работает благодаря отсутствию цепочек, а не благодаря логике.

**П9. `competing_writer` сравнивает значения через `str()`, а проверка недостижимых
состояний — через `norm_value()`.** В проверке 8: `auto_vals = {str(...)}`,
`val = str(...)`. Значит `True` (булев) и `"true"` (строка) читаются как разные
значения и дают `conflict = True`, то есть критичность «высокая». Здесь id 1321
хранит `"True"` строкой, id 1331 — `false` булевым, вердикт совпал бы и с
`norm_value`, — потерь нет, но на любой базе, где Studio записала значение в другом
регистре, это фабрикует находку высшей критичности.

**П10. Отчёт смешивает проблемы и не-проблемы.** Заголовок `01-проблеми.md` — «Найдено
36 проблем», сводка — «низкая 8», при том что 4 из 8 «низких» строк это
`odoo_mechanism` с прямым текстом «Проверять как доработку не нужно». Аналитик,
переносящий цифру в ТР, завышает её на 4. Дополнительно: у 3 строк колонка «где»
пустая — у `leftover_artifact` представления id 4874 (`model: null`) и у обеих строк
`cross_model_field` (в коде передаётся `""`).

Мелочью, но из того же ряда: в `impact-sale.order.md` для `x_discount_visa` в колонке
«Кто пишет» стоит «только вручную», хотя тут же в колонке «Где выводится» —
**нигде**; вручную такое поле заполнить нельзя.

## Что стоит доснять в дамп

Эти четыре пробела снимка — причина всех оговорок выше, а не дефекты проверок:
`ir.ui.view.groups_id` (охват дубля поля), поля активности у `ir.actions.server`
(сравнимость `next_activity`), домены `ir.actions.act_window` и `ir.filters`
(остаточное сомнение под `orphan_field` и `invisible_result`), признак «стандартное /
кастомное» для правил на `--live`-снимках (сейчас `fetch_live` ставит `None`).
