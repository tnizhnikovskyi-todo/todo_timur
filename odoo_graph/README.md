# odoo-graph — граф кастомного слоя базы Odoo

Инструмент строит граф доработок конкретной базы Odoo и находит в нём
проблемы, которые не видны ни в коде, ни в интерфейсе по отдельности.

Мотивация: статический граф вызовов Python для Odoo бесполезен — ORM
диспатчит динамически, `super()` разрешается по MRO, собранному в рантайме.
Реальная структура доработок лежит в метаданных базы, поэтому граф строится
из них.

## Что читает

| Слой | Источник | Рёбра графа |
|---|---|---|
| Кастомные модели | `ir.model` (`state=manual`) | — |
| Кастомные поля | `ir.model.fields` (`state=manual`) | поле → модель, поле → связанная модель |
| Представления | `ir.ui.view` (правленые + ссылающиеся на `x_`-поля) | представление → модель, → базовое представление, → поле |
| Автоматизации | `base.automation` | автоматизация → модель, → поле из условия |
| Действия сервера | `ir.actions.server` (`update_path`) | действие → модель, → автоматизация, → поле, в которое пишет |
| Правила доступа | `ir.rule` | правило → модель |

Только чтение метаданных. Бизнес-данные не читаются, в базу ничего не пишется.

## Запуск

По живой базе (нужен API-ключ пользователя Odoo):

```bash
python3 odoo_graph.py --live \
  --url https://example.odoo.com --db example \
  --user user@example.com \
  --save-dump dumps/example.json --model sale.order --out out
```

Ключ в командной строке не передаётся: без него инструмент спросит ключ
с терминала (ввод не отображается и не попадает в history). Для запуска
без терминала — из cron, из CI — есть два способа:

```bash
# ключ в файле, который читает только владелец
(umask 077; cat > ~/.odoo-api-key)   # вставить ключ, затем Ctrl-D
python3 odoo_graph.py --live ... --api-key-file ~/.odoo-api-key

# из переменной окружения
ODOO_API_KEY="$(cat ~/.odoo-api-key)" python3 odoo_graph.py --live ...
```

Аргумент `--api-key` остался ради обратной совместимости, но помечен как
устаревший и печатает предупреждение: значение аргумента видно в `ps`
любому пользователю машины и оседает в history оболочки.

По готовому снимку:

```bash
python3 odoo_graph.py --dump dumps/edu-online-todo.json --model sale.order --out out
```

Без `--model` отчёты строятся по трём самым кастомизированным моделям.
Переменные окружения `ODOO_URL`, `ODOO_DB`, `ODOO_USER`, `ODOO_API_KEY`
заменяют одноимённые аргументы. Зависимостей нет, только стандартная
библиотека Python 3.

Снимок `--save-dump` содержит только метаданные: адрес и имя базы, версию
Odoo, число установленных модулей и слои кастомного слоя. Ни ключ, ни логин,
ни пароль в него не пишутся — снимок можно класть в репозиторий.

## Что на выходе

| Файл | Содержимое |
|---|---|
| `00-сводка.md` | объём кастомного слоя, модели по количеству доработок |
| `01-проблеми.md` | найденные проблемы с критичностью и объяснением |
| `impact-<модель>.md` | анализ влияния: поля, представления, автоматизации, права — заготовка раздела «Опис технічної реалізації» для ТР |
| `graph.json` | граф целиком, для дальнейшей обработки |
| `graph.html` | интерактивная визуализация (один файл, без CDN) |

## Проверки

| Проверка | Что означает |
|---|---|
| `unreachable_state` | автоматизация ждёт значения, которое никто не выставляет — ветка процесса не запускается никогда |
| `unreachable_gate` | поле-условие не выведено в интерфейс и не пишется автоматически — заполнить его нечем |
| `competing_writer` | ручное действие пишет в поле, которым управляет автоматизация |
| `duplicate_placement` | одно поле дважды вставлено в одну форму двумя расширениями |
| `orphan_field` | кастомное поле не влияет ни на что |
| `invisible_result` | система пишет в поле, которого нет ни в одном представлении |
| `xpath_collision_risk` | несколько кастомных расширений одного представления — риск поломки при обновлении версии |
| `leftover_artifact` | объект помечен в названии как тестовый или подлежащий уборке |
| `cross_model_field` | одно имя поля создано в нескольких моделях |
| `dangling_action` | действие сервера не привязано к автоматизации и дублирует привязанное |
| `empty_view` | расширение представления ничего не меняет |
| `odoo_mechanism` | служебное поле Odoo (например `x_plan2_id` аналитического плана) — проверять как доработку не нужно |

## Ограничения

- Ссылки на поля ищутся в `arch` представлений и в доменах автоматизаций
  регулярными выражениями: поле, которое выводится динамическим виджетом
  или собирается в Python-коде модуля, инструмент не увидит. Реестр
  `KNOWN_MECHANISMS` — способ гасить такие ложные срабатывания.
- Доработки в виде установленных модулей (не Studio) видны только в той
  мере, в какой они создают записи в `ir.*`. Разбор исходников модулей
  не делается.
- `--live` требует, чтобы у пользователя были права на чтение `ir.*`;
  без них Odoo вернёт ошибку доступа, и инструмент скажет, каких
  моделей не хватает.
