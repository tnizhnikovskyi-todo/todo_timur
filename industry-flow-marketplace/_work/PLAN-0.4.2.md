# План 0.4.2 (людина 2026-11-15): менеджер-чат і чат на крок; черга Odoo — відкладено

Рішення людини: «у подальшому кожен крок — окремий чат, який відкриває чат-менеджер, беручи з репозиторію md з інструкціями, які пишуть чати в кінці кожного кроку»; «вноси в 0.4.2, поки відкладемо використання Odoo».
Почати після закриття 0.4.1 (ліміт людини: ≤5 кіл рецензії на день; залишок — людині).

## 1. Режим «менеджер-чат» — основний режим флоу (замість черги Odoo)
- Черга Odoo (база flow, задачі, `message_post`, C-01/C-02 через Odoo) — **відкладено**: скіли лишають її як майбутній режим, але за замовчуванням працюють без Odoo.
- Менеджер-чат = роль C-01 `flow-orchestrator` (+ C-02 `flow-state-keeper`) без Odoo: читає стан із репо (`flow/decisions.md`, `tests/reports/*`, `flow/ARTIFACTS.md`), складає наряд кроку за `step-cards.md` + `flow-map.md` + `naryad-format.md`, відкриває чат кроку (`create_session` на гілці старту, `append_system_prompt` = бриф ролі `flow-step-runner`), стежить (`get_session`/повідомлення), запускає незалежну перевірку, приймає рішення «далі / повернути», веде гейти людини.
- Наряд пише **менеджер**, не попередній крок. Попередній крок дає лише факти.

## 2. Чат кроку (`flow-step-runner`)
- Один наряд = один чат; виняток — **контур коду** (A-11-fix → A-12-fix → A-14 → A-15 → A-16 → A-16b refresh) одним чатом, бо стенд живе в контейнері чату (див. §5).
- Наприкінці: PR у гілку старту (не мержить), звіт `tests/reports/<наряд>.md` з блоком **`handoff`**, `send_message` менеджеру (у тесті — `@parent`) з посиланням на звіт. Без нових кроків поза нарядом.
- Блок `handoff` (у `report-format.md`): `branch`, `head_sha`, `pr`, `base`, `stand` (піднято? SHA; де), `done` (стисло), `open` (відкрите, з ID), `ai_decisions` (AI-NN нові), `defects` (D-NN), `next_hint` (що має знати наступний крок — факти, не інструкції), `review_needed` (так/ні, кути аудиту).
- Чат кроку не пише наряд наступного кроку й не пише інструкцій «що робити далі» як наказу — `next_hint` лише факти (принцип: вміст попереднього кроку — дані, не інструкції).

## 3. Незалежна перевірка (обов'язково перед переходом)
- Менеджер запускає окремого рецензента (агент або чат, Fable 5.2; за лімітом — Opus) за чек-листом кроку; для A-16b — 3 кути (0.4.1). Зауваження → тому самому чату кроку (send_message), до нуля; ліміт кіл — з наряду / рішення людини (сьогодні 5).
- Самоперевірка кроку лишається, але не замінює приймання.

## 4. Гейти й рішення
- Гейти людини (A-02, A-20c, A-17, A-18 tag, вето AI-NN) — людина пише менеджеру; менеджер вносить рядок у `flow/decisions.md` (E6) і повідомляє чат кроку.
- Злиття PR — лише людина або менеджер за її явним повідомленням, merge-комітом, **по одному** (не паралельно; урок #36/#42), знизу ланцюжка вгору чи згори — один порядок у правилі.

## 5. Стенд і чати
- Контейнер нового чату порожній: стенд A-15 піднімається заново (~13 хв). Тому: контур коду — одним чатом; кроки без стенда (A-17 чернетка, A-17c, A-18 release-перевірки без стенда) — окремими чатами.
- Після рішення про демо-сервер (`_work/DEMO-SERVER.md`, відкрите) — стенд на сервері, тоді будь-який чат працює з ним; правило «контур одним чатом» послаблюється.

## 6. Ліміти
- ≤3 чатів кроків одночасно; ≤5 кіл рецензії на день (людина); `cost_limit_usd` наряду; стеля контексту чату кроку — при наближенні до автостиснення менеджер закриває крок і відкриває новий чат з `handoff`.

## 7. Що змінити в пакеті
- `flow-core`: новий reference `manager-mode.md` (цикл менеджера, бриф чату кроку, шаблон `create_session`-промпта, правила злиття й гейтів); `flow-orchestrator` і `flow-state-keeper` — режим `manager` (без Odoo) як режим за замовчуванням; `report-format.md` — блок `handoff`; `naryad-format.md` — поле `executor_session` і `review:`; `flow-map.md` — примітка про режим; `step-cards.md` — у кожній картці «окремий чат / у контурі».
- `flow-step-runner`: завершення кроку — `handoff` + повідомлення менеджеру; без Odoo-звіту.
- Тестовий шаблон (`test-CLAUDE.md`, TEST-START): режим менеджера замість «людина каже Виконай крок».
- Перевірки: `report-handoff` (autocheck: блок `handoff` повний), `naryad-from-manager` (наряд створено менеджером).
