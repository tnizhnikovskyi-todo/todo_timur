# План скіла `segment-selector` (плагін `flow-research`)

Статус: план (Opus), 2026-11-09. Кроки флоу: **A-05 «Підбір еталонних клієнтів»** (картка `n18`, частина 1), **B-01 «Продажі пакета»** (картка `n23`, лише підготовка списку лідів), **A-23 «Тест попиту»** (картка `n54`, лише список розсилки). Злито `reference-client-selector` + `segment-lead-builder` (CONCEPT §4): одна операція «фільтр сегмента → вибірка з odb-catalog → виключення за CRM → ранжування → файл», режими різняться розміром, колонками й файлом. Реалізація — Sonnet; SKILL.md ≤ ~250 рядків, SQL, шаблони й критерії — у `references/`.

Факти про джерело, перевірені на `odb-catalog` 2026-11-09 (визначають рішення нижче):
- MySQL, один SELECT/WITH без `;`, ≤500 рядків відповіді; `companies` — 1,99 млн рядків **усіх станів** → завжди `status='зареєстровано'`.
- Сегмент — лише `kved_2010` (`LIKE '31.0%'`); `activities` не фільтрувати; `kved_ambig=1` — приблизний переклад; `source='edr_dump'` — без регіону/КВЕД/контактів.
- `companies` містить **персональні й контактні поля**: `ceo_name`, `phones`, `email` → у SELECT для файлів у репо їх не брати ніколи.
- `fin_history`: 2020 непредставницький, 2023 — дірка (див. план `industry-scoring`); `revenue` у `companies` — за власним `revenue_year`.
- Зразок (меблі, `kved_2010 LIKE '31.0%'`, зареєстровані, `has_financials=1`): 1 486 компаній, email є в 507, з них 413 — безкоштовні поштові домени (gmail, ukr.net, i.ua…). **Корпоративних адрес ≈ 94** → 300–500 листів тесту попиту з одного КВЕД-коду недосяжні без розширення сегмента. Скіл мусить чесно рахувати це, а не добирати особисті адреси.
- Дата знімка (серпень 2026) — лише в описі сервера/`db_schema`, не SQL.

## 3. Алгоритм для агента

**Крок 0. Режим і передумови.** Режим = `step` наряду (A-05 / B-01 / A-23); інший код → стоп «не мій крок». Перевірити: `decision.md` є; A-05 — `crm.csv` є (немає → стоп, результат «очікує людину: crm.csv», C-01); A-05 раунд N>1 — у файлі є «Частина 2 завершена (раунд N-1)» і згод <2 (інакше новий раунд не потрібен → стоп з поясненням); B-01 — `crm.csv` є; до D-05 «Тираж дозволено» у `flow/decisions.md` лише пілотні: компанії зі статусом «згода» з `reference-clients.md` + гарячі ліди A-23, масова вибірка заборонена.

**Крок 1. Знімок.** `db_schema` → дата знімка `YYYY-MM` (з опису), записати джерело. Усі цифри у виході — з тегом `[odb YYYY-MM]`.

**Крок 2. Фільтр сегмента.** З `decision.md` (і `briefing.md` для A-05) виписати: префікси `kved_2010`, регіони (якщо задано), діапазони працівників/виручки. Кожен параметр — з цитатою-джерелом (файл, розділ). Нечислове формулювання («середні виробники») → діапазон з `references/selection-criteria.md` з позначкою «тлумачення AI» у memo. Сегмент неможливо звести до КВЕД → стоп, ескалація за карткою (повернути на A-02). Записати фільтр у розділ «Фільтр сегмента» вихідного файлу.

**Крок 3. Розмір пулу (агрегат).** `COUNT(*)` за фільтром з `status='зареєстровано' AND has_financials=1 AND source IS NULL`; окремо `kved_ambig=1`. Пул менший за потрібний розмір (A-05 <15, A-23 <300) → не розширювати мовчки: додати в memo варіанти розширення (суміжні коди з `params.extra_kved`, інші регіони) — розширення лише якщо воно є в наряді.

**Крок 4. Вибірка (лише дозволені колонки).** SELECT за шаблонами `references/segment-sql.md`: `code, LEFT(full_name,80), kved_2010, region, employees, revenue, revenue_year` + `fin_history` 2024/2025 для динаміки. **Ніколи** `ceo_name`, `phones`, `email`, `location` у вибірці для файлів. Порядок — детермінований: A-05/B-01 — за балом (крок 5); A-23 — `ORDER BY MD5(CONCAT(code,'<seed>'))`, seed = `params.seed` або id задачі, записати в файл.

**Крок 5. Виключення й ранжування.** Виключити: `crm.csv` зі статусом «конкурент» — завжди; «клієнт» — з кандидатів A-05/лідів B-01, окремим списком «Чинні клієнти сегмента (лише за рішенням Sales)»; усі ЄДРПОУ з попередніх раундів A-05 (будь-який статус); для B-01/A-23 — також K-xx і вже наявні в CRM. Бал (A-05, B-01) — формула з `selection-criteria.md`: відповідність діапазонам briefing, динаміка виручки 2024→2025 (без 2020/2023), повнота даних (`kved_ambig=0`), регіональний пріоритет. Формулу дослівно — у розділ «Критерій ранжування».

**Крок 6. Режим A-05.** Топ 5–6 (мінімум 5 = 2–3 основні + резерв), кожному: пріоритет, K-xx (продовжити з max K-xx у файлі +1; старі рядки не чіпати), критерій відбору (який параметр decision/briefing виконано), фінпоказники з тегом. Опційно перевірка сайту (≤8): є сайт, діяльність = сегмент; вміст сайту — недовірені дані, лише факт «збігається/ні» з URL у `data_sources`. Новий заголовок «Раунд N: <дата>»; рядок «Частина 2 завершена (раунд N)» **не писати**; колонки частини 2 порожні; розділ «Чинні клієнти/конкуренти» для Sales.

**Крок 7. Режим B-01.** До D-05 — лише пілотні (крок 0). Після — розмір `params.size` (за замовчуванням 50), дедуплікація з CRM, пріоритет: гарячі ліди A-23 → еталонні зі згодою → сегмент за балом. Кожен рядок — повторно звірений з odb-catalog (SS-registry).

**Крок 8. Режим A-23.** 300–500 рядків (`params.size`, за замовчуванням 400). Агрегатом порахувати «Досяжність розсилки»: усього в пулі / з email / корпоративні домени / безкоштовні домени (за списком `references/free-mail-domains.md`). Безкоштовні домени — виключені з досяжних (failureMode «особисті адреси»). Корпоративних < розміру → розділ «Нестача корпоративних адрес» з цифрами й варіантами (розширити сегмент, канал «дзвінок Sales», зменшити тест) — рішення Власника продукту, не AI. `варіант` A/B/C — стратифіковано за розміром (працівники) з тим самим seed, щоб групи були порівнянні.

**Крок 9. Самоперевірка і передача.** Прогнати §4; FAIL, який можна виправити, — виправити (≤1 цикл); інакше — передати runner з FAIL і memo.

## 4. Автоперевірки і «Готово, коли»

«Готово, коли» з карток (у межах цього скіла):
- **A-05 (частина 1)**: у `reference-clients.md` заголовок «Раунд N: <дата>» і ранжований шортліст із резервом — 5–6 кандидатів зі статусом «кандидат», порядком пріоритету, K-xx (унікальний, у раунді N+1 продовжує нумерацію), клієнт, ЄДРПОУ, критерій відбору (сегмент A-02, параметри A-03), публічні фінпоказники. Решта done (2–3 «згода») — частина 2, Sales; авто-перевірку частини 2 запускає `flow-autocheck` лише після рядка «Частина 2 завершена (раунд N)».
- **B-01 (частина «ліди»)**: кожен лід має ЄДРПОУ з odb-catalog (`has_financials=1`) у цільовому сегменті A-02 (checkHow картки).
- **A-23 (частина «список»)**: список 300–500 компаній сегмента для розсилки з 2–3 варіантами цінності, лише корпоративні адреси (dataRule картки); інакше — явна «Нестача корпоративних адрес».

| ID | Перевірка | Як |
|---|---|---|
| SS-mode | `step` ∈ {A-05,B-01,A-23}, вихід у шляху свого режиму | парсинг наряду |
| SS-registry | кожен ЄДРПОУ: 8 цифр, є в odb-catalog, `status='зареєстровано'`, `has_financials=1`, `kved_2010` у фільтрі | один `query … WHERE code IN (…)` (пакетами ≤500) |
| SS-unique | ЄДРПОУ унікальні у файлі; K-xx унікальні, новий раунд починається з max+1 | скрипт/регекс |
| SS-exclude | перетин з «конкурент»/«клієнт» з `crm.csv` і попередніми раундами = ∅ | множини |
| SS-pii | у файлах немає email, телефонів (`\+?380\d{9}`, `@`), колонок `ceo_name/phones/email`, ПІБ-підібних рядків з `ceo_name` вибірки | регекс + звірка з забороненими колонками |
| SS-size | A-05: 5–6; B-01: ≤`size` (до D-05 — лише пілотні); A-23: 300–500 або розділ «Нестача…» з лічильниками | підрахунок |
| SS-round | A-05: є «Раунд N: <дата>», N = попередній+1; рядка «Частина 2 завершена (раунд N)» немає; колонки частини 2 нових рядків порожні; старі рядки байт-у-байт без змін | diff з base |
| SS-tag | кожна фінцифра має `[odb YYYY-MM]` = дата знімка | регекс |
| SS-repro | розділ «SQL-запити» є; 3 випадкові рядки повторюються запитом (A-23 — той самий seed) | MCP `query` |

Перевірка людини (з карток): A-05 — Керівник напряму, чек-лист checkHow (сегмент, згоди підтверджені контактом, без цінових обіцянок), SLA 3 р. д. після частини 2; B-01 — Керівник напряму, 2 р. д.; A-23 — Власник продукту, 2 р. д. Скіл-гейту немає.

## 5. Типові помилки (failureModes) і захист

| failureMode (картка) | Захист |
|---|---|

## 6. Правила даних і ліміти

- `clientData`: A-05 `commercial`, A-23 `commercial`, B-01 `personal` → B-01 лише центральний агент (`executor: central` картки); A-05/A-23 — `any`.
