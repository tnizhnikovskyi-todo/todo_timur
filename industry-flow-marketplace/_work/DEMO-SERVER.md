# Демо-стенди Odoo на сервері замість Docker у власника (проєкт, 2026-11-14)

> **Статус: відкрите рішення людини** (2026-11-14) — записано в `IMPLEMENTATION-PLAN.md` §5 п.7. Скіли не змінюються до рішення.

Запит людини: «зараз піднімаємо базу, щоб я міг поклацати в себе в докері; потрібно робити це на сервері, і ти будеш робити це сам на сервері,
до якого тобі дадуть доступ». Цей документ — як це влаштувати і що змінити в скілах.

## 1. Що є зараз і чому так не годиться

- Стенд піднімає сесія в хмарному контейнері; власнику віддає `docker-compose.yml` і бекап бази, щоб він підняв у себе.
  Бекап бази при цьому комітили в git (`package/demo/docker/mebli-demo-odoo19.zip`) — бінарники баз у репо не кладемо.
- Хмарна сесія не має вхідного доступу ззовні (стенд у контейнері ніхто не відкриє) і **не має вихідного SSH**: перевірено 2026-11-14,
  порт 22 закритий політикою мережі. Тому «дати доступ по SSH» не спрацює без зміни моделі.

## 2. Як AI отримує доступ до сервера — два варіанти

| | **А. Самохостований раннер GitHub (рекомендую)** | **Б. Claude Code на сервері (Remote Control)** |
|---|---|---|
| Як | На сервері — GitHub Actions self-hosted runner з міткою `flow-demo` у репо галузі. AI запускає workflow `demo-stand.yml` (дії `up / reset / down / list / record`) через GitHub і читає журнал запуску | На сервері встановлено Claude Code, у теці `/srv/flow-demo` запущено `claude remote-control`. Сесія з застосунку працює просто на сервері, з docker під рукою |
| Що може AI | Лише фіксовані дії зі скрипта, усе — через git і журнал GitHub | Будь-які команди в межах користувача `flowbot` |
| Працює з хмарних сесій | Так, уже сьогодні (запуск workflow є серед інструментів) | Лише сесія, відкрита на сервері, або хмарна сесія з підключенням теки (доступне не всім акаунтам) |
| Ризик | Мінімальний: немає shell, кожна дія в журналі | Вищий: повний shell, потрібні жорсткі права |
| Для чого | Щоденна робота: стенд для зрізу A-21, демо-стенд A-15, база для ліда A-22, запис відео | Налагодження сервера, рідкісні ручні роботи |

Рекомендація: **А як основний канал, Б — лише для налагодження** (вмикає людина на час робіт).

## 3. Сервер

- Ubuntu 24.04 LTS; 4 vCPU, 8–16 ГБ RAM, 100 ГБ SSD (5–8 стендів одночасно); Docker Engine + compose plugin.
- Домен: wildcard `*.demo.<домен ToDo>` → IP сервера; Caddy як вхід з автоматичним TLS.
- Користувач `flowbot`: група `docker`, без sudo; раннер працює від нього. Секрети — у `/srv/flow-demo/.env` (поза git) або в GitHub Secrets.
- Chromium + ffmpeg на сервері — щоб запис відео й скриншоти зрізу робились там само, де стенд (без перекачування бази).

## 4. Як влаштований стенд

- Один стенд = один compose-проєкт `/srv/flow-demo/<галузь>/<стенд>/`: `odoo:19.0` (CE) + `postgres:16`, модулі `package/addons/td_*`
  з git на конкретному SHA/тегу, filestore у volume. Назва стенда: `<галузь>-<крок>[-<гілка>]` → `https://mebli-a21.demo.<домен>`.
- Enterprise — окремим образом з EE-аддонами лише за наявності ліцензії (відкрите питання §5 плану); до того EE-стенд не піднімаємо.
- Дані — лише синтетичні/демо (клас `commercial`/`none`); бази клієнтів сюди не потрапляють ніколи.
- Безпека: менеджер баз вимкнено (`list_db = False`, сильний `admin_passwd`), `robots: noindex`, базова авторизація Caddy на весь піддомен
  (логін і пароль команди — у менеджері паролів, не в чаті й не в git); користувачі Odoo — демо-ролі (менеджер салону, замірник, технолог,
  цех, фінансист, директор) зі спільним демо-паролем із секрету.
- Життєвий цикл: стенд живе 14 днів, далі `down` автоматично, якщо не позначено `pin`; стенди ліда A-22 скидаються щоночі;
  бекап бази — на сервері `/srv/flow-demo/backups/` (у git лише SHA і посилання).

## 5. Дії `demo-stand.yml` (що робить AI)

| Дія | Входи | Результат у журналі запуску |
|---|---|---|
| `up` | галузь, крок, git ref, профіль даних (`answers.yaml`), `edition: ce` | URL, SHA, список модулів, час підйому, результат `smoke.sh` |
| `reset` | стенд | перестворена база з того самого SHA і даних |
| `down` / `pin` | стенд | звільнено / закріплено |
| `list` | — | стенди, SHA, вік, розмір |
| `record` | стенд, сценарій (`SALES §6`) | відео й кадри (живий запис), викладені як артефакт запуску |
| `backup` | стенд | файл на сервері, посилання в журналі |

Скрипти — з наявних шаблонів `flow-core/references/templates/tools-odoo/` (`install.sh`, `reset.sh`, `smoke.sh`, `import.sh`) + новий `stand.sh`.
Перевірка після `up`: `smoke.sh` на сервері і HTTPS-запит з хмарної сесії (домен стендів треба додати в дозволені домени середовища).

## 6. Що змінити в скілах (після рішення про варіант)

- Анкета A-02b: поле `demo.target: server | local` (за замовчуванням `server`), домен стендів.
- `prototype-builder` (A-21), `demo-base-builder` (A-15, A-22), `showcase-content` (запис): стенд — через `demo-stand.yml`; у звіті — URL і SHA;
  бекапи баз і `docker-compose` для власника в git не класти.
- `ci-pipeline-builder` / C-00: шаблон `demo-stand.yml` і `stand.sh`; чек C-00 «раннер `flow-demo` онлайн, домен відповідає».
- Автоперевірка: FAIL на бінарники баз (`*.zip`, `*.dump`, `*.sql.gz`) у PR.

## 7. Що потрібно від людини

1. Сервер (параметри §3) і рішення: варіант А, Б чи обидва.
2. Домен для стендів (wildcard DNS) — і додати його в дозволені домени середовища хмарних сесій.
3. Для А: встановити раннер у репо галузі (токен реєстрації бере адміністратор GitHub; AI його не бачить).
   Для Б: встановити Claude Code під `flowbot` і запустити `claude remote-control` у `/srv/flow-demo`.
4. Пароль базової авторизації й демо-пароль — у менеджер паролів і в секрети GitHub/`.env`; у чат не писати.
