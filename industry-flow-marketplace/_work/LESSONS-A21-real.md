# Уроки реального зрізу A-21 «меблі» → правки скілів (виконати ПІСЛЯ підтвердження результату людиною)

Статус: **очікує підтвердження людини.** Джерело: тестове репо `tnizhnikovskyi-todo/industry-flow-test-mebli`, гілка `flow/A-21-real`
(код `package/addons/td_mebli_*`, показ `docs/industries/mebli/prototype-real/`). Після «так» — внести правки циклом Sonnet → Fable 5.2,
оновити тестове репо (bootstrap), закомітити.

## 1. prototype-builder (A-21) — головні зміни
1. Замість самописного HTML-шаблону — **реальний зріз у Odoo 19**: справжні модулі `td_*` (Python-моделі, подання, дані), без Studio і `x_`;
   локальне середовище Odoo 19 CE (скрипти на зразок `factory3d/tools/odoo/setup.sh`, ≈1–3 хв), максимум стандарту, код — лише де стандарту немає.
   Код зрізу — заготовка A-11 (лежить у `package/addons/`).
2. План зрізу (Opus) з перевіркою кожного припущення про стандарт по вихідниках Odoo 19 (файл:рядок); враховувати, що в CE немає
   `mrp_workorder`, `web_gantt`; `spreadsheet_dashboard` у CE — лише sale/account/stock_account.
3. **Продаючі вимоги** як обов'язковий критерій: історія «біль → вигода» з прив'язкою до PAIN/ROLE; брендинг демо-клієнта всередині Odoo;
   ролі-користувачі з логінами й аватарами; насичені правдоподібні дані з **калібруванням** (маржа ~12–40 % з розкидом, реальна трудомісткість
   у годинах, масштаб виручки «фабрики», робочі години 8–17); видимий ефект (маржа, % відходу, економія, завантаження, час до запуску);
   компактні чесні позначки імітацій; без «Новий», порожніх полів, англійських заглушок, обрізаного тексту.
4. **Фірмовий стиль ToDo** у матеріалах (не в UI Odoo): логотип, `#FE5000`, `#101820`, Open Sans — комплект `brand-todo/` як reference скіла.
5. **Два відео**: повне 16:9 1920×1080 3–4 хв і Reels 9:16 1080×1920 55–60 с (гачок 0–3 с, безпечні поля, великі титри); **динамічні**:
   живий запис екрана (кліки, набір, прокрутка, канбан, анімація графіків, count-up, zoom), xfade, Reels — зміна плану 1,5–3 с,
   жодного статичного кадру >2 с, титр ≥1,5 с; заставки окремими сторінками зі своїм CSS (не поверх Odoo, не сторінка логіну).
   Основа відео — **безперервний живий запис сценарію** (Playwright recordVideo) з титрами поверх; бренд — лише заставки/титри/плашка поверх
   запису (оцінка людини: найкраща динаміка — у записі прогону 2 до зміни стилю; монтаж зі скриншотів динаміку вбиває).
6. **Мобільний показ**: справжній мобільний UI Odoo (390×844, isMobile, hasTouch, DPR 3), ≥4 кроки ролей, живий запис, нейтральна рамка телефона.
7. **Блок керівника**: дашборд на одному екрані (власний клієнтський екран, якщо CE-дашбордів бракує), ~10 с у кожному відео, мобільний вигляд,
   одна узгоджена цифра маржі (зважена) у дашборді, звітах і SHOW.
8. **SHOW.md/HTML/PDF** — one-pager «Що отримає фабрика»; числа генеруються з `facts.json`, зчитаного з DOM під час зйомки; збірка падає при
   розбіжності.
9. Автоперевірки: консоль браузера без помилок (`setContent` лише на about:blank, не поверх Odoo); тести модулів; odoo19-lint; без префікса `x_`
   у полях коду; ffprobe-формати відео; покадровий перегляд перших/останніх 5 с.
10. Рецензент **обов'язково переглядає** скриншоти, кадри відео й PDF (не лише функції) — візуальні й продаючі критерії в чек-листі рецензії.

## 2. Інші скіли й флоу
- `demand-test-runner` (A-23): використовувати матеріали A-21 (Reels, повне відео, SHOW.pdf) у лендингу, листах і плані розсилки.
- `concept-mapper` (A-20): перевірка покриття — кожна роль має сценарій, кожна F-xx — крок сценарію, роль на екрані = роль у screens.md
  (знахідки A-21: ROLE-04/07 без сценаріїв, F-17 без кроку, ROLE-03 на S-14).
- `demo-base-builder` (A-15/A-22): переглянути межу з новим A-21 (емуляція Studio/x_ більше не потрібна; демо-стенд = база зрізу + дані).
- `flow-map.md`, картки A-21/A-22/A-11: A-21 стає «реальний зріз» (години, рівень, входи/виходи; код — вхід A-10/A-11); A-22 — перегляд.
- `flow-core/references/templates/tools-odoo`, `c00-checklist.md`: локальне середовище Odoo 19 CE для кроків A-21/A-11/A-14 за зразком factory3d.
- `eval-builder`: евали візуальної якості (кейси з поганими скриншотами/відео → рецензент має повернути).
- `flow-step-runner` / шаблон брифу рецензента: для кроків з візуальним результатом — візуальні й продаючі критерії обов'язкові.

## 3. Процес (для менеджера)
- Критерії рецензії задавати повно від початку (функції + вигляд + продаж + бренд + динаміка + мобільний), щоб не перезапускати цикли.
- Вимоги людини, додані посеред циклу, вносити в пізніші раунди без зміни ранніх промптів (кеш resume).

## 4. Нова роль: контент-менеджер зі своїм Claude (вимога людини 2026-11-10)
Вносити в схему (дошка BPMN, вкладка «Флоу в цифрах» — ролі людей і агентів, картки) і в скіли разом з п. 1–3, після підтвердження результату A-21.
- Роль «Контент-менеджер (маркетинг)» — людина, працює зі своїм Claude (агент співробітника, `executor: any`).
- Як працює: отримує задачу (наряд) у внутрішній базі Odoo флоу в нашому проєкті пакета; її Claude читає наряд через odoo-mcp (явний connection_id
  бази флоу), працює з контентом у GitHub-репо пакета (гілка кроку → PR), звіт — у задачу Odoo; рішення — кнопка в задачі.
- Що веде: продаючі матеріали A-21 (титри, тексти, SHOW one-pager, перемонтаж двох відео з живого запису, бренд ToDo), A-23 (лендинг, листи,
  варіанти цінності), надалі — кейси пілота (D-05) і матеріали релізів (A-18).
- Дані: лише контент у репо (`docs/industries/<галузь>/prototype-real/`, `demand/`), клас `commercial`; без доступу до баз Odoo, крім читання наряду;
  цифри — лише з `facts.json`/джерел репо (узгодженість перевіряє збірка).
- Скіли: окремий скіл для правок контенту (робоча назва `flow-research:showcase-content` — правки титрів/текстів/SHOW, перемонтаж відео з наявного
  запису без перезйомки, перевірка бренду й узгодженості цифр), або режим «контент» у prototype-builder + demand-test-runner — вирішити при внесенні.
- Картки: A-21, A-23 (і D-05, A-18 за потреби) — raciR/executor з роллю контент-менеджера; карта флоу — без нових кроків, нова роль у наявних.
