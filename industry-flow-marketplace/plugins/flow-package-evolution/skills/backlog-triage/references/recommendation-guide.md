# Рекомендація AI (чернетка): три варіанти й аргумент

Рішення «у продукт / у кастом клієнта / відхилено» ухвалює Власник продукту вручну (рішення Власника продукту). Формального порогу немає:
**жодних числових відсічок, балів, формул, «автоматично у продукт», «N клієнтів -> у продукт»**. AI дає факти й аргумент.
Усі формулювання в колонці: «Рекомендація AI (чернетка): …».

## Два показники (обов'язкові в кожній рекомендації «у продукт»)
1. **Кількість клієнтів/лідів у групі** з розбивкою: на супроводі / у впровадженні / лідів. Рахується за різними ідентифікаторами, а не за кількістю рядків.
2. **Використання з D-01** пов'язаних моделей пакета: «жива» / «не жива» (за позначкою D-01) / «метрик немає». Нічого не екстраполювати й не рахувати самому.
Для (б), (в), (г) і (а) без клієнтів на супроводі показник 2 — «метрик немає», обґрунтування лише кількістю клієнтів/лідів.

## Три рекомендації й ознаки
| Рекомендація | Ознаки (перевіряй по фактах) |
|---|---|
| у продукт | запит галузевий: процес типовий для галузі, а не для одного клієнта; є у ≥ 2 клієнтів/лідів або явно галузева суть; ТР галузі не покриває («не знайдено»); пов'язані моделі пакета використовуються («жива») або метрик немає. Це підказки, а не умови |
| у кастом клієнта | специфіка клієнта: інтеграція з його системою, унікальна форма, власна номенклатура, власний регламент; запит один і не лягає на галузевий процес. Для ліда не застосовується. Кастом оформлює PM у B-05 через `odoo19-tr-authoring:tr-change-request`, D-02 CR не створює |
| відхилити (причина) | уже є в пакеті (покриття ТР знайдено: потрібне навчання або доналаштування); дублює інший REQ; поза межами пакета й продукту; дефект уже виправлено в теґу пакета. Причина — одним реченням з посиланням |

## Шаблон аргументу (3-5 рядків, колонка «аргумент» у «Групи»)
```
Факти: <к-сть клієнтів/лідів і стан>; <модель X: жива / не жива / метрик немає>; ТР: <розділ/AC або не знайдено>.
Рекомендація AI (чернетка): <варіант> — <одне речення чому, лише з фактів вище>.
Що перевірити Власнику продукту: <місце невпевненості: сумнівне групування, специфіка чи типовість, застарілі метрики>.
```

## Ознаки клієнтської специфіки (не об'єднувати з галузевим запитом)
Назва або інтеграція конкретної зовнішньої системи клієнта; унікальна друкована форма; власна номенклатура/класифікатор; «як у нас заведено» без посилання на процес галузі; вимога, продиктована договором одного клієнта. Сумнів -> окрема група й рядок у «що перевірити».

## Заборони
- Не писати «ухвалено», «затверджено», «вирішено» про рішення. Колонки «Рішення», «Версія», «Обґрунтування рішення», блок підпису порожні.
- Не підставляти версію пакета: навіть якщо наряд містить цільову версію, це лише заголовок беклогу.
- Не пропонувати прибрати модель пакета через низьке використання: це рішення людини в окремому процесі.
- Для рядків ліда (B-01) не писати «у кастом клієнта»: лише «у продукт» або «відхилити».
- Хибні або застарілі метрики не виправляти: `returned_to: D-01`.
