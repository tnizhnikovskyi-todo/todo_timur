# Конвенція `migrations/` для td_* (крок 5)

Усі твердження про механізм міграцій Odoo нижче — робоча гіпотеза з досвіду. Перед використанням перевірити для
Odoo N через `boost:source-check` (цитата й URL у `memo`); непідтверджене — UNVERIFIED (не вигадувати).

## Каталог і версія
- Шлях: `package/addons/td_<модуль>/migrations/<N>.0.X.Y/`, ім'я каталогу = `version` у `__manifest__.py`.
- Файли: `pre-migrate.py` (SQL до завантаження моделей), `post-migrate.py` (ORM після завантаження); `end-migrate.py`
  лише за потреби (гіпотеза: виконується після оновлення всіх модулів; підтвердити source-check).
- Умова запуску (гіпотеза): встановлена версія модуля < каталог <= версії в маніфесті. Тому при зміні `version` каталог
  має збігатися з нею, інакше скрипт не запуститься.
- Модуль без змін моделей/полів каталогу не має (M-03).

## Сигнатура й вміст
- `def migrate(cr, version):` — стандартна сигнатура скрипта міграції.
- Ідемпотентність: повторний запуск не ламає базу (перевірки `information_schema`, `IF NOT EXISTS`, `WHERE old IS NOT NULL`).
- `pre`: перейменування колонок/таблиць, перенесення значень до зміни схеми; `post`: заповнення нових полів, чистка.
- Заборони: дані клієнта й конкретні ідентифікатори; `DELETE` без умови; прямі виклики мережі; секрети; скрипти поза `migrations/`.
- Кожен скрипт відповідає рядку інвентарю («змінено»); перелік скриптів — у розділі «Скрипти міграції» `upgrade-<версія>.md`
  (лише посилання, одне речення на скрипт).
