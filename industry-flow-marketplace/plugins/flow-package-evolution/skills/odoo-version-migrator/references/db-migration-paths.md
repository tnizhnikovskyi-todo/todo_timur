# Шлях міграції бази (крок 8, розділ «Шлях міграції бази»)

Скіл базу ядра не мігрує. Мігрує Тімлід; AI перевіряє наявність і зміст запису та лог `-u` пакета.

## Інструмент за редакцією (A-07, `docs/industries/<галузь>/business-case.md`)
| Редакція | Інструмент | Примітка |
|---|---|---|
| Enterprise | сервіс міграції Odoo (у картці — q35) | Умови доступу, строки, формат запиту — питання до Тімліда; скіл їх не вигадує |
| Community | OpenUpgrade | Чи є реліз OpenUpgrade під Odoo N — питання до Тімліда, скіл не стверджує |
| Не визначено в A-07 | — | `escalated` Тімліду, без вибору за замовчуванням |

## Що записує Тімлід
Інструмент, джерело (клас бази: лише демо-дані A-15, не копії клієнтів), стенд нової версії (alias з `odoo_connections` наряду),
посилання на лог `-u td_*` (рівень INFO) і SHA, на якому `-u` виконано, дата, хто виконав.

## Порядок (verify)
1. Тімлід переносить демо-базу A-15 інструментом за редакцією й піднімає стенд нової версії.
2. Тімлід виконує `-u` усіх `td_*` на SHA коду і заповнює «Шлях міграції бази» з посиланням на лог (агент shell-доступу не має).
3. Скіл перевіряє: розділ непорожній, інструмент відповідає редакції, лог є, SHA = SHA коду, помилок немає,
   запуск кожного `migrations/<N>.0.X.Y/` видно в лозі (шаблон — `migrations-convention.md`) (M-09).
4. Стан модулів — з логу; `ir.module.module` через odoo-mcp — лише якщо наряд дає підключення класу `demo`/тестова
   (явний `connection_id`, лише читання).
Немає логу або розділ порожній -> `escalated` Тімліду.

Дані клієнтів і їх знеособлені копії для цього кроку заборонені.
