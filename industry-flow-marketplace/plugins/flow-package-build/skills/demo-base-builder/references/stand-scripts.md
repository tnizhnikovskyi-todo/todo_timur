# Контракт скриптів стенда `package/demo/` (A-15)

Скрипти — **тонкі обгортки над контрактом C-00** (`tools/odoo/`). Обов'язкові входи контракту: (1) чиста база за тегом,
(2) установка за тегом, (3) імпорт шаблонів, (4) smoke; **необов'язковий** (5) знімок і відновлення бази (`snapshot.sh <instance>` / `restore.sh <instance>`).
Скіл не пише власних замінників; зокрема **власних `pg_dump`/`createdb`-команд — ніколи**.
Якщо необов'язкового (5) немає в `tools/odoo/`: `up.sh` пропускає крок 7, `reset.sh` = повний `up.sh <instance>`, у README це зазначено, а в `memo` —
відкрите питання Тімліду «додати snapshot.sh/restore.sh у C-00». Це не блокує крок. Точних імен і аргументів скриптів C-00 скіл **не знає** до появи `tools/odoo/` (відкрите питання В-3):
перед написанням обгорток прочитати `tools/odoo/README` або `--help`; немає каталогу чи обов'язкових (1)–(4) — ескалація Тімліду, `result: escalated`.

## Файли
```
package/demo/
  up.sh  reset.sh  answers.yaml  profiles/answers.alt-<N>.yaml
  data/            синтетичні CSV/XML + seed (див. demo-data-rules.md)
  plan.md  README.md  defects.md (лише при дефектах)
```

## `up.sh <instance> [--profile <file>] [--tag <tag>]`
- `instance` — ідентифікатор інстанса (обов'язковий); `--profile` — за замовчуванням `answers.yaml`; `--tag` — тег пакета (за замовчуванням HEAD).
- Послідовність (кожен крок — виклик C-00, зупинка при коді ≠ 0):
  1. чиста база `<instance>` за тегом/ревізією;
  2. модулі `package/addons/` + «Модулі до установки» з `CONFIG.md`;
  3. конфіг A-12 з файлом answers/профілем (команда з `CONFIG.md`, не вигадана);
  4. імпорт шаблонів майстер-даних A-13 (порядок з `package/master-data/README.md`);
  5. демо-дані `data/` у порядку plan.md;
  6. демо-користувачі й групи ролей з ТР (ролі останніми);
  7. знімок `<instance>-snapshot` (`snapshot.sh <instance>`; якщо скрипта C-00 немає — крок пропускається, див. вище).
- Без інтерактиву й питань; паролі демо-ролей — лише зі змінних середовища, у репо не пишуться (В-4).
- Лог — у файл (`package/demo/.logs/up-<instance>.log`, не коміт); в консоль — рядок «OK/FAIL <крок>». У контекст агента — лише `tail -30` і `grep -E "ERROR|Traceback" -A 15`.
- Коди виходу: 0 — готово; 10 — чиста база; 20 — модулі; 30 — конфіг; 40 — майстер-дані; 50 — демо-дані/ролі; 60 — знімок. (Власна нумерація скіла; якщо C-00 задає свою — взяти її.)

## `reset.sh <instance>`
- Відновлює `<instance>-snapshot` (`restore.sh <instance>`). Fallback, якщо знімка або скрипта C-00 немає, — повний `up.sh <instance>` (у README це зазначено).
- Перевірка: змінити один демо-запис → `reset.sh` → запис у початковому стані.

## Режим використання (рішення Тімліда, не скіла)
Обидва скрипти завжди параметризовані `instance`, тож підтримують і «окремі інстанси» (A-16, кожне демо B-01, D-03, тест A-18),
і «один стенд із журналом бронювання». Режим береться з наряду; немає — «Відкрите питання» в README і першим рядком у `memo`.

## Попередній тег (A-18)
Тест оновлення піднімає базу попереднього тегу: `git checkout <тег> -- package/demo/` → `up.sh <instance> --tag <тег>`. Тому скрипти
не посилаються на файли поза `package/demo/` і `package/` за вказаним тегом; README фіксує це правило.

## Журнал установки для README
Таблиця: крок | що встановлено | команда | результат (OK/FAIL, код) | дата. Модулі — перелік із `ir.module.module` (state=installed), конфіг —
перелік VP-xx → значення, імпорт — кількість рядків на CSV. Логи в README не вставляються.
