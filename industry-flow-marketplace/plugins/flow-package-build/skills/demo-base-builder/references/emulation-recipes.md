# Рецепти емуляції в Odoo 19 через odoo-mcp (A-22)

**Обмеження знань.** Точні назви полів моделей, значення selection і тригерів `base.automation` в Odoo 19 тут не фіксуються: перед першою
збіркою звірити їх через `odoo_get_fields` на самій демо-базі (`connection_id` демо-бази) і `boost:source-check`; розбіжність з рецептом — запис у `memo`.

## Правила виклику
- Кожен `odoo_create`/`odoo_write`/`odoo_get_fields`/`odoo_search_read` — з явним `connection_id` = `emu-<галузь>[-<id>]`; після кожного — `connection.db` у відповіді.
- Перед збіркою `odoo_search_read` у демо-базі: що вже існує з префіксом `x_`, щоб не дублювати (повторна збірка = за маніфестом).
- Видалень немає. Помилкову сутність — не видаляти, а перепризначити/деактивувати (`active`, якщо поле є) і записати в `memo`; видалення — лише з дозволом людини.

## Дозволено (і порядок)
1. `ir.model` (кастомна модель, ім'я `x_...`) → 2. `ir.model.fields` (поля `x_...`; збережені поля для підставлених результатів) →
3. `ir.ui.view` (форма, список, пошук; Odoo 19 — корінь списку `list`, не `tree` — звірити `boost:odoo19-lint`) →
4. `ir.actions.act_window` → 5. `ir.ui.menu` → 6. прості серверні дії (оновити запис / створити запис / створити активність) →
7. `base.automation` (за подією або за часом).
Права доступу демо-ролей: `ir.model.access` і групи — лише для створених `x_` моделей.

## Заборонено
`ir.actions.server` з `state='code'` (Python), установка/оновлення модулів, експорт Studio в код, зміна стандартних моделей/полів без `x_`,
`o19demo`, прод, `test-<клієнт>`, будь-який запис без `connection_id`.

## Підставлений результат
Складна логіка (розрахунок, інтеграція, звіт) → збережене поле з готовим значенням з `complexity.md` A-21 / A-20:
- підпис поля й підказка: «[Емуляція] підставлено, не розраховано»;
- банер у формі (`ir.ui.view`) на моделях, де є такі поля;
- рядок у таблиці «Підставлено, не розраховано» в `emulation.md`.
Значення — синтетичні й правдоподібні, не з даних клієнта.

## Строк доступу ліда
Користувач-заглушка `lead-<id>` без контактів з `x_access_until` (дата). Деактивація — `base.automation` за часом з простою серверною дією
(зняття активності користувача). Чи можна так змінювати користувача, звірити в Odoo 19 (`boost:source-check`); не виходить без коду — підкрок Тімліда
(ручна деактивація за календарем), не Python.

## Скидання: «золота копія»
1. Після збірки і проходу сценаріїв Тімлід через менеджер баз дублює базу в `emu-<галузь>-golden` (майстер-пароль — лише в людини).
2. Нічне відновлення з копії — розклад хостингу/C-00 (хто тримає розклад — відкрите питання В-7; агенту майстер-пароль не потрібен).
3. Скіл: описує контракт у `emulation.md`, ставить підкрок у `memo`, після першого скидання перевіряє через odoo-mcp (читання), що демо-дані в початковому стані.

## Один лід — одна база
Лід не бачить даних іншого: окремий інстанс `emu-<галузь>-<id>` або бронювання одного інстанса; дані лише синтетичні.
