# Бриф незалежного аудиту покриття A-16b (0.4.1)

Запуск: після самоперевірки, обов'язково; **у `mode: manager` запускає менеджер** після звіту чату кроку (`review_rounds: 0`), чат кроку лише виправляє зауваження й оновлює `review_rounds`; сам `runner` запускає рецензентів лише в `queue` і запасному режимі (блок `review:` наряду; `flow-core:flow-reviewer`, інша модель, ніж виконавець). Рецензентів **4**, паралельно,
кожен складає **власний перелік із джерел** (не з таблиць INDEX і не з розділів посібника), а потім звіряє з посібниками. Рецензент має Read/Grep/Glob;
runner передає шляхи: `package/docs/user-guide/` (INDEX, admin.md, setup.md, `<роль>.md`, cards/, reference/messages.md, img/, shoot-plan.json), `package/addons/td_*`,
`package/config/CONFIG.md`, `package/templates/answers.yaml`, `package/demo/plan.md`, `package/docs/user-guide/img/ROLE-GROUPS.json`, `package/demo/README.md`, `package/ACCEPTANCE.md`, концепція (`F-xx`, `scenarios.md`),
лог туру A-16 і вихідники Odoo 19.0 (uk.po, security).

## Кут (а) — новий адміністратор, наскрізно `admin.md`
Людина з порожнім сервером і без знання пакета йде за `admin.md` лише тексту. Перелік рецензента — кроки: сервер -> `addons_path` -> `odoo-bin -i` із «Модулі до установки» ->
`--load-language` -> мультикомпанія (якщо VP multi) -> безпека (паролі, 2FA, `list_db`, майстер-пароль, ключі) -> пошта (`web.base.url`, «Ел. пошта», відправник) -> користувачі (TZ) ->
системні параметри (`get_param`) -> меню лише для групи -> бекап/відновлення/neutralize -> оновлення. Для кожного кроку: є виконувана команда? шлях меню правильний за uk.po 19.0?
Окремо **«налаштування з нуля лише за `setup.md`» (0.4.2 §10)**: адміністратор і технолог заводять довідники, товари й поля `td_*` стандартних форм, йдучи лише за `setup.md` (кожна форма й довідник: хто, меню, кроки, обов'язкові поля, типова помилка, кадр під роллю, CSV); перелік форм і довідників рецензент складає з коду (`_inherit` стандартних моделей з полями `td_*`, `_name = 'td.*'` з `ir.actions.act_window`), не з INDEX (г). Пункт без кроку або кадр не під роллю, що налаштовує = зауваження. Обрив (щось треба вгадати) = зауваження. Межа B-04 (конфіг-пакет на базу клієнта) і рядок AI-NN — на місці?

## Кут (б) — працівник кожної ролі, цикл замовлення
Для кожної ролі: перелік дій у життєвому циклі замовлення складається з SPEC/концепції/коду, не з INDEX. Для кожної дії: названо в посібнику роли? кадр знято під
логіном цієї ролі (SHOOT-LOG, shoot-plan.json)? меню/кнопка доступні групам ролі (групи ролі — з `img/ROLE-GROUPS.json` зі стенда (`plan.md` — запасне) + `groups` у XML, `implied_ids`)? дія не падає з AccessError (sudo, ACL)?
кадри не прямим URL? Передача між ролями (хто бачить результат попередньої ролі) описана? Повідомлення системи цієї ролі — у `reference/messages.md`.

## Кут (в) — переліки з коду, F/AC, ACCEPTANCE
Рецензент (інструменти Read/Grep/Glob, без Bash — скриптів не запускає) складає переліки з коду `td_*` через Grep (шаблони: `<menuitem`, `button_box`, `raise (UserError|ValidationError|AccessError)`, `get_param(`, `TransientModel`) або з сирих виводів grep по коду, які runner поклав у теку контексту (це не «чужий перелік», на відміну від таблиць INDEX і виводу `check_guides.py`): menuitem і дії, кнопки заголовка й смарт-кнопки (`button_box`), звіти, майстри (`TransientModel`), поля
`res.config.settings`, `get_param`, тексти `raise`. Звіряє з посібниками й довідником. Далі: кожен F-xx концепції й AC зі SPEC має сценарій/розділ; якщо `package/ACCEPTANCE.md` уже є (повтор після A-17; на першому проході файла немає, звірка — за `guide-acceptance-consistent` в A-17): статус у посібнику = статус
в `ACCEPTANCE.md` (немає «готово» в посібнику при «відхилено» в приймальній таблиці); назви стандартного UI — з uk.po 19.0.

## Кут (г) — власник-новачок (0.4.3)
Власник бізнесу вперше сидить за стендом під логіном ролі й не знає пакета. Рецензент йде за кадрами під роллю (SHOOT-LOG, `shoot-plan.json`) і кодом форм `td_*` та стандартних форм із полями `td_*` (Grep: `<button`, `button_box`, `@api.constrains`, `@api.onchange`) і складає власний перелік перевірок форм:
1. **Дублі:** дві кнопки/смарт-кнопки чи пункти меню з однаковою назвою на одному кадрі (стандартна + `td_` для ширшої групи) — дефект.
2. **Ключова дія ролі** (друк, надіслати, записати, підтвердити) — кнопкою в шапці форми, а не лише в ⚙ -> «Друк»/«Дія»; інакше дефект або пояснення в посібнику, чому так.
3. **Помилка вводу:** кожен `@api.constrains` на полі, яке роль вводить, має `@api.onchange`-попередження з межами значень до збереження.
4. **Бізнес-сигнал** (маржа < 0, ціна < собівартості, обіцяна дата < прогнозної) видно на формі (колір, банер, попередження), а не лише у звіті.
5. **Результат дії:** у посібнику сказано, де він з'явиться (меню, документ, стадія) і чи він залежить від вмісту документа (передумова: рядок-послуга, склад, стадія проєкту).
6. **Наскрізні дані:** дата, відповідальний, клієнт документа-джерела присутні в похідному документі (замовлення -> задача/виїзд/виробництво); запис-контейнер (проєкт, команда, журнал) має довідник, потрібний для роботи (стадії).
Дефект -> D-NN у `package/demo/defects.md` -> A-11/A-12; бажана доробка, а не дефект — за правилом `manager-mode.md` (дефект vs нова вимога).

## Вихід кожного рецензента
Список `{серйозність, місце, що не так, що зробити}` + власний перелік (кількість пунктів і скільки покрито), без загальних фраз. Будь-яке зауваження major повертається виконавцю; повтор
аудиту — до нуля зауважень. Кола ліміт: `review.max_rounds` (у тестовому наряді A-16b — 5) і глобальний ліміт людини ≤5 кругів рецензії на день; після останнього кола зауваження лишилися -> `waiting_human`: перелік людині й чекати її рішення.
