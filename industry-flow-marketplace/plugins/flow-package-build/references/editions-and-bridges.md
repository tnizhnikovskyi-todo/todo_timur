# Редакції CE і EE, мости `td_*_ee`, режим договору — спільні правила збірки пакета

Канон: К-06, К-09, К-12 (`_work/IMPLEMENTATION-PLAN.md` §1). Читають усі скіли `flow-package-build` і, за посиланням, скіли `flow-package-evolution`
та `flow-client-delivery`. Відкриті питання — у кінці файла; їх не вирішувати.

## 1. Принципи
1. Ядро пакета (усі екрани MVP, наскрізний сценарій) працює на **Odoo 19 Community**. Enterprise — підсилення окремими модулями, не залежність ядра.
2. Редакції пакета задає `editions: ce | ee | both` з `docs/industries/<галузь>/OWNER-INTAKE.md` (блокуюче поле, читається, не вгадується). Редакція **клієнта** — параметр `edition`
   в `answers.yaml` (`ce | ee`); для `editions: ce` значення `ee` недопустиме.
3. Модулі `td_*` (ядро) **не мають EE-модулів у `depends`** і не імпортують EE-код. EE-частина — окремі мости `td_<галузь>_<тема>_ee` з `auto_install: True`
   (встановлюються самі, коли є EE-модуль-залежність), `depends` = ядро `td_*` + потрібний EE-модуль. На CE-базі міст не встановлюється й не повинен ламати установку ядра.
4. Ядро без AGPL-залежностей (К-09): жоден модуль ядра не залежить від AGPL-коду (зокрема модулів OCA); OCA — лише ідея, реалізація — у `td_*`.
   Перевірка: поле `license` у `__manifest__.py` кожної залежності модуля ядра (`AGPL-3` -> дефект класу BLOCK). Ліцензія наших модулів — **LGPL-3 за замовчуванням;
   остаточно — рішення власника** (відкрите питання, див. кінець).
5. Твердження «це дає Enterprise» / «цього немає в CE» — лише рядком `edition-claims.md` (`EC-xxx`) з вердиктом `повністю/частково/ні/не перевірено` й доказом (К-12).
   Скіл збірки сам таких тверджень не вводить; вердикт `не перевірено` -> міст позначається «не перевірено», не «працює».

## 2. Профілі модулів у `package/config/manifest.yaml`
```yaml
edition_profiles:            # обидва профілі завжди присутні; другий — порожній не буває при editions: both
  ce:
    modules: [<стандартні CE>, td_<галузь>_core, ...]        # порядок залежностей
  ee:
    modules: [<усе з ce>, <стандартні EE>, td_<галузь>_<тема>_ee, ...]
```
- `ee` ⊇ `ce` (EE-профіль = CE-профіль + EE-модулі + мости). Модуль у `ce`, якого немає в `ee`, — помилка складання.
- Кожен модуль має `origin: std-ce | std-ee | td | todo-ready | integration` (К-09); `std-ee` і `td_*_ee` -- лише в профілі `ee`.
- Параметри `vp-map.yaml`/`answers.yaml`: `edition: ce|ee` і `contract_mode: <значення>` — звичайні параметри (VP-xx) із `default`; `contract_mode` лише
  відображає юридично неоднозначне, винесене в параметр (`legal_ambiguous.to_answers_yaml` анкети, §21 №17); перелік значень задає власник/ТР, скіл його **не вигадує**.

## 3. Вердикт за редакціями
| Ситуація | Правило |
|---|---|
| `editions: both` | перевірка/гейт/CI виконується окремо для `ce` і `ee`; загальний `APPROVE` лише якщо обидва APPROVE; EE недоступна — `APPROVE (CE); EE не перевірено` (`partial: true`, випуск з неперевіреною EE — рішення Власника продукту; див. `gates-aggregator`) |
| `editions: ce` | лише `ce`; рядок `ee` у звіті — `SKIP (не передбачено анкетою)` |
| EE недоступна (нема `ODOO_EE_ADDONS_PATH`, доступу до EE-коду) | вердикт `ee` = `WARN` («не перевірено: EE недоступна»), **не** APPROVE мовчки й не FAIL; у `memo` — що саме не перевірено |
| AGPL-залежність у ядрі | `BLOCK` — серйозність правки A-11 (вердикт гейта — `правки`; для обох редакцій) |
| `td_*` (ядро) залежить від EE-модуля | `BLOCK`; перенести в міст `td_*_ee` |
| міст `td_*_ee` без `auto_install` | `REQUEST CHANGES` |
Редакція в команді: `ODOO_EDITION=ce|ee`, `tools/odoo/preflight.sh --edition ce|ee|both` (`flow-core/references/templates/tools-odoo/README.md`). Чистих баз — по одній на редакцію.

## 4. Рядок звіту
У звіті/`CHECKS.md`/`install-log.md` кожен результат має стовпець `edition` (`ce`/`ee`) і SHA. Без нього результат не зараховується.

## Відкриті питання (до людини / власників пакета)
- Ліцензія наших модулів: LGPL-3 за замовчуванням; OPL чи інша — рішення власника.
- Доступ до EE-коду й EE-бази для тестів — не гарантований; до рішення EE-перевірки дають `WARN`/«не перевірено».
- Перелік значень `contract_mode` і їхній правовий зміст — рішення власника/юриста (не вигадувати).
