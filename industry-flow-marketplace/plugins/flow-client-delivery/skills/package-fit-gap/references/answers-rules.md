# Правила answers.yaml і анкети клієнта

Схема — `package/templates/answers.yaml` на тегу (власник — `flow-package-build:questionnaire-builder`, A-09).
Тут схема не змінюється.

## Значення
- Ключ — на **кожну** не-deprecated VP-xx схеми; deprecated не заповнюються, зайвих ключів немає.
- Значення — одне з допустимих у схемі або рядок `уточнити`.
- `уточнити`, якщо: немає прямої відповіді клієнта; відповідь суперечить іншому джерелу; відповідь поза
  допустимими значеннями; VP залежить від іншої VP, що має `уточнити`.
- Не підставляти default пакета, «логічний висновок» з інших відповідей чи блок очікуваних VP-xx з
  `план_демо-збірки` (це підказка, не джерело).
- Біля кожного ключа коментар-джерело: `# fathom:<id>@hh:mm:ss`, `# анкета:р.N`, або `# причина: …`.

## Типи дефектів для «Запити в D-02»
| Тип | Коли |
|---|---|
| незрозуміле питання | клієнт не зрозумів питання анкети |
| відсутній варіант значення | відповідь клієнта не вкладається в допустимі значення |
| залежна VP | відповідь на одну VP залежить від іншої, а анкета цього не показує |
| функція відсутня | пакет заявляє функцію, якої немає на тегу |
Кожне `уточнити` з причиною «дефект» має FG-D02 рядок: питання/VP, що не спрацювало, запропонований варіант
(чернетка), дата, статус «передано в D-02», колонка «рішення D-02 і версія пакета» порожня.
`уточнити` через відсутність відповіді (клієнта ще не питали) — не дефект, запиту D-02 не потребує, але
потрапляє в перелік питань до клієнта в `memo`.

## questionnaire.md клієнта
Копія анкети пакета на тегу; для кожного питання: VP-xx → відповідь або `уточнити` → джерело. Текст питань
не редагується (дефект — у D-02). Без ПІБ і контактів.

## Валідація
Спільного валідатора поки немає (відкрите питання): перевірити вручну — множина ключів = не-deprecated VP-xx
схеми, значення ∈ допустимих або `уточнити`.
