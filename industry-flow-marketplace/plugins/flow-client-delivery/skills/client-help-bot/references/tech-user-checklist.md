# Технічний користувач `prod-ro-<клієнт>`

Створює людина (B-12), не AI. Бот лише перевіряє те, що бачить через власний запис (`prepare`, крок 5).
- Окремий логін і API-ключ, не особистий акаунт працівника; ключ у конфігурації odoo-mcp центрального агента, не в репо.
- Мінімальні групи: лише потрібні для читання allow-list; без груп зарплати, кадрів, фінансів, якщо DATA_POLICY цього не дозволяє.
- Обов'язково для `answer`: Тімлід підтверджує в `kb-index.md` (чек-лист), що користувач не має прав запису/створення/видалення (роль, дата); це блокувальна умова першого `answer` (README пакета). «Лише читання» на боці Odoo: штатної read-only ролі немає — **відкрите питання** (Тімлід, Архітектор); варіанти не вигадувати. Зараз гарантія — інструменти скіла й allow-list.
- Alias підключення в odoo-mcp: `prod-ro-<scope.id>`; прод клієнта під іншим alias цей скіл не використовує.
- Відкликання згоди клієнта — стоп-лист C-08: наряди `answer` припиняються.
