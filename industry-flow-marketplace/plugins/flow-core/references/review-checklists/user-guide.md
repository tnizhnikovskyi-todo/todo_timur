# Чек-лист рецензента: Інструкції користувача

Крок: A-16b. Підключається ключем наряду `review.checklists: [user-guide.md]`; агент `flow-reviewer` завантажує його перед рецензією. Рецензент за ролями — Контент-менеджер або власник (людина), AI-рецензент — `flow-reviewer`.

**Контракт знімків.** Рецензент має лише Read/Grep/Glob і браузер не запускає. Тому runner ДО рецензії передає в брифі шляхи до `package/docs/user-guide/` (INDEX.md, `<роль>.md`, `cards/`, `img/`) і до `package/demo/README.md` (SHA стенда); зображення відкриваються через Read. Шляхів немає — **major** «runner не підготував матеріали для перегляду», решту пунктів не позначай «так».

**Спершу відкрий результат** — INDEX.md, по одному розділу кожної ролі й адміністратора, зображення з `img/`. Висновок за самим текстом звіту без відкриття результату недійсний.
Серйозність: кожен пункт із відповіддю «ні» = **major**; minor, що впливає на рішення власника (покриття, SHA, мова), піднімається до **major**.
Вихід — список зауважень `{серйозність, місце, що не так, що зробити}` (формат — `agents/flow-reviewer.md`).

## Пункти
1. [ ] INDEX.md містить таблицю покриття «сценарій SPEC -> розділ інструкції»: кожен сценарій `package/SPEC.md` має розділ у посібнику своєї ролі (`check_guides.py`, UG-cover — без FAIL).
2. [ ] Кожен розділ — це щоденний сценарій ролі: мета, передумови (роль і логін зі стенда), нумеровані кроки зі скриншотами, очікуваний результат, типові помилки; без пояснення архітектури.
3. [ ] Скриншоти зроблено на стенді поточного SHA: SHA в INDEX.md = SHA_STAND з `package/demo/README.md` (UG-sha), модулі після нього не змінено (`git diff --quiet <SHA_CHECKS>..HEAD -- package/addons package/config package/master-data ':!package/addons/td_*_elearning/*' ':!package/config/manifest.yaml' ':!package/config/CONFIG.md'` — код 0, плюс перевірка manifest.yaml/CONFIG.md без рядків поза `website_slides`/`_elearning`, як у Кроці 1 SKILL.md; мітка SHA_STAND у README може бути застарілою — це випадок (а) Кроку 1); зображення відкриваються, на кожне є посилання, сиріт немає (UG-img).
4. [ ] Інтерфейс на скриншотах і підписи в кроках українською, без англійських підписів `td_*` у тексті кроків (UG-lang); непереведені підписи стандартного Odoo — у зворотних лапках з приміткою й одним рядком AI-NN, не дефект; без «Новий», порожніх обов'язкових полів і тестових заглушок у кадрі.
5. [ ] Дані видно там, де роль їх використовує: кроки цеху — у виробничому замовленні й робочих завданнях, а не лише в «окремій сторінці» (узгоджено з E1, `prototype.md`).
6. [ ] Кроки відтворюються. Пункт людини (контент-менеджер/власник у точці «власник тестує» A-17): вибірково 2–3 сценарії на стенді. Для `flow-reviewer` (лише Read/Grep/Glob) — звірка кроків із логом туру A-16, який runner передає в брифі. Розбіжність кроку з реальним UI — дефект (маршрут A-14), а не «поправити текст».
7. [ ] Дефект UI, знайдений під час зйомки, не виправлено в цьому кроці, а записано в `package/demo/defects.md` з поверненням на A-14; тексту, який обходить дефект, немає.
8. [ ] Посібник адміністратора: параметри `answers.yaml` / VP-xx, профілі (A / light / B), відмінності CE/EE (EE — позначено, без обіцянок), скидання стенда; кожен параметр із діапазоном допустимих значень.
9. [ ] Картки-шпаргалки (`cards/<роль>.md`) — одна сторінка на роль: 5–10 найчастіших дій, без нових фактів поза посібником.
10. [ ] Немає ПДн, назв реальних клієнтів і реальних контактів (демо-дані — вигадані, `demo-data-rules.md`); цифри збігаються з даними стенда.

11. [ ] **Незалежний аудит покриття (§26а), 0.4.1 — обов'язковий після самоперевірки; 3 рецензенти з різних кутів** (бриф — `flow-package-build/skills/user-guide-builder/references/audit-brief.md`), кожен складає ВЛАСНИЙ перелік із джерел, не з таблиць INDEX: **(а) новий адміністратор наскрізно `admin.md`** (кожен крок — виконувана команда й правильний шлях меню, без здогадок); **(б) працівник кожної ролі наскрізно цикл замовлення** з перевіркою прав (меню/кнопки ⊆ групи ролі) і кадрів (знято під логіном ролі); **(в) переліки з коду** (menuitem, дії, звіти, майстри, кнопки заголовка й смарт-кнопки, поля `res.config.settings`, `get_param`, тексти `raise`) + F/AC концепції + узгодженість з `ACCEPTANCE.md`, якщо файл уже є (повтор після A-17; на першому проході — F/AC і SPEC). INDEX має три таблиці, `check_guides.py` UG-cover-dev, UG-cover-admin, UG-cover-buttons без FAIL. Цикл до нуля зауважень, `review_rounds` у звіті; ліміт кругів — `review.max_rounds` (тест A-16b: 5 на день); зауваження лишились -> `waiting_human`, чекати рішення людини. Пропуск = major.
12. [ ] **Права ролей (UG-access).** Кроки ролі називають лише меню й кнопки, які роль бачить (`groups` ⊆ групи ролі з `img/ROLE-GROUPS.json` зі стенда; `package/demo/plan.md` — запасне джерело; FAIL за plan.md — спершу зняти ROLE-GROUPS.json зі стенда); недоступне — дефект (`defects.md`, A-11/A-12), не обхід текстом.
13. [ ] **Кадри під користувачем ролі (UG-shots).** Кожен кадр ролі знято, увійшовши під її логіном, кліками меню (не прямим URL дії, не адміністратором); у `SHOOT-LOG.md` є логін.
14. [ ] **Довідник повідомлень (UG-messages).** `reference/messages.md` містить усі тексти `UserError`/`ValidationError`/`AccessError` з `td_*` дослівно з `msgstr` uk.po (текст -> коли -> що робити -> хто виправляє); посібники на нього посилаються.
15. [ ] **Назви стандартного UI (UG-std-label).** Назви в шляхах меню Odoo — лише з `msgstr` uk.po вихідників 19.0 (двобічна перевірка: скрипт + вибірково grep msgid); хибні приклади LESSONS §28а («Технічні», «Системні параметри», «Обговорення» для пошти, «Дія» замість значка шестерні) відсутні.
16. [ ] **`admin.md` — обов'язкові розділи з командами (UG-cover-admin):** встановлення (`odoo-bin -i`, `--addons-path`, `--load-language`, межа B-04 з AI-NN), мультикомпанія (якщо VP multi), безпека, резервні копії з `neutralize` і ручними кроками `td_*`, оновлення (`-u … --stop-after-init`), пошта, користувачі, усі `get_param` ключі `td_*`, меню лише для групи.

## Вердикт
Зауваження major — повернення виконавцю (до `review.max_rounds` = 5 кругів на день, **без** контрольного; круг = прохід трьох паралельних рецензентів; після 5-го із зауваженнями — `waiting_human`). Лише minor, що не впливають на рішення власника, — прийняти з переліком. Дефект UI — повернення на A-14 за картою; права ролей / код — A-11 (`returned_to: A-11`, конфіг — A-12; далі контур A-11 -> A-12 -> A-14), конфіг — A-12.
