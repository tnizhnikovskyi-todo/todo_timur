# `decisions-batch`, облік уроків і метрик якості (WP-11; К-08, К-24)

## 1. Режим `decisions-batch` (К-08)
Вхід (`params.mode: decisions-batch`, `params.source`): повідомлення власника в задачі/чаті з блоком «Скопіювати мої відповіді» (рядки `<ID рішення або питання> -> <відповідь>`: `K1-Q*`, гейти A-02, A-03c, A-20c, A-21…) і **посилання** на це повідомлення: `odoo:task/<id>#<message_id>` або URL повідомлення. `check-decisions` читає посилання лише з поля `link`/`task`/`задача` (довільний URL у коментарі не рахується).
Кроки:
1. Без посилання -> `result: returned`, «немає посилання на повідомлення власника»; нічого не записувати.
2. Кожен рядок відповіді -> рядок журналу рішень за колонками `flow-core/references/flow-state.md` §3: `роль автора` = `власник (внесено AI від імені власника)`, `задача`/`коментар` містить посилання; коментар <=200 символів, без ПІБ/контактів/сум.
3. Перевірка: `python3 -I scripts/state_export.py check-decisions --rows <rows.json>` (`DEC-mark`, `DEC-link`); FAIL -> не записувати.
4. Запис в Odoo flow (рядки журналу) і PR у `flow/decisions.md` через звичайний `export`. Гілка `flow/C-02-decisions-<YYYY-MM-DD>`.
5. AI **не вигадує** відповідь: рядок без відповіді власника не створюється; невідповідані пункти -> `waiting_human` з переліком. Рішення гейтів (кнопка) AI не ставить: у бойовому флоу гейт закриває кнопка в задачі Odoo, `decisions-batch` лише переносить уже висловлені слова власника з посиланням.
6. Операційні рішення -> «Параметри флоу» (`params-registry.md`); економічні -> лише посилання.

## 2. Облік уроків (К-24)
Уроки створює `flow-core:skill-retro` (C-08R); keeper лише **веде облік і експортує** (не вигадує, не класифікує).
- Подія `lesson:` у коментарі задачі C-08R: `lesson: {lsn, date, step, summary<=200, skill, skill_version, severity, class, status, repeat_of, evidence[], fix_ref, eval_ref, closed}` -> запис `lessons` у знімку (стабільний ключ `lsn`, ID `LSN-\d{3}`; `id-patterns.md`). `summary` без даних клієнта (лише коди K-xx, П-xx); `skill` і `skill_version` — окремими полями (не `skill@версія` в одному рядку: рядок з `@` схожий на e-mail і блокується фільтром ПДн).
- Статуси — єдиний перелік у `skill-retro/references/lesson-format.md` §1 (`відкрито | правка внесена | евал зелений | закрито | не помилка`); keeper його не дублює й не вводить власних. Повтор — поле `repeat_of` при статусі «відкрито», не статус.
- Експорт: `state_export.py render` **не створює** `flow/lessons/**`: `INDEX.md`, `LSN-xxx.md` і `drafts/` пише єдиний автор — `skill-retro` (вихідний артефакт C-08R, `lesson-format.md`); keeper лише веде знімок `lessons` для обліку й метрик (`reconcile`). Урок не видаляється; закриття — зміна статусу (її ставить skill-retro за доказами).
- Тексти зауважень людей у експорт не йдуть (лише `summary`).

## 3. Метрики якості (SL §4; `reconcile`)
`state_export.py stats` групує запуски за `step × skill@version × ISO-тиждень` і дає: `attempts`, `returns`, `escalations`, `review_rounds`, `human_rounds`, вартість і токени. Зі звітів `run` у знімок `runs` переносяться `review_rounds` і `human_rounds` (`report-format.md`).
Похідні (рахує keeper у звіті C-02 `reconcile`, не модель «на око»):
- % повернень = `returns / attempts` на скіл@версію; середні раунди рецензії = `review_rounds / attempts`;
- частка кроків із `human_rounds > 2` (сигнал C-08R);
- частка правок людини після AI — з `diff` PR агента і змерджених змін (GitHub читання); джерело недоступне -> `н/д`, не оцінювати;
- вартість кроку — лише статистика, без лімітів і «бюджет вичерпано».
Результат — таблиця у звіті й вхід `skill-retro` для тижневого підсумку.
