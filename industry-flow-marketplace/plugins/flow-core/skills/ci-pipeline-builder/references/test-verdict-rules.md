# Правила вердикту тестових job'ів

## Червоне за замовчуванням
Job червоний (exit != 0), якщо виконується хоч одне:
- failures > 0 або errors > 0;
- skipped > 0 (пропущені тести = недійсний зелений);
- запущено 0 тестів;
- у виводі немає підсумку `run_tests.sh` (скрипт упав раніше, обрізаний лог);
- тур зі списку A-16 (`scenarios.md`, «Odoo tour: <ім'я>») без результату в логу;
- вибір образу Odoo N не визначено (`odoo-version-resolve.md`);
- `continue-on-error: true` у тестовому job;
- CE-вузол матриці `package-tests` червоний (CE — обов'язкова редакція); EE-вузол з реальним червоним (`ODOO_EDITION=ee`, доступ є) — теж червоний.

Не червоне, але й не PASS: EE-вузол без доступу до EE (`WARN ee-unavailable`, код 3 скрипта C-00) → вердикт редакції `WARN`; статус `ci` описує «EE WARN ee-unavailable (не перевірено)» (`ci-contract.md`).

## Парсинг підсумку
Правила пишуться **за фактичним форматом** виводу `tools/odoo/run_tests.sh` (C-00). Агент читає скрипт, фіксує зразок рядка підсумку
в цьому розділі `package/templates/ci-workflow.md` і будує регулярний вираз з нього. Формату або лічильника skipped у скрипті немає ->
не вгадувати: `escalated` Тімліду «C-00: підсумок без лічильника <чого>» (відкрите В-1). Приклад умовного формату для фікстур евалів:
`N tests, F failures, E errors, S skipped` (не факт про реальний скрипт).

## Вивід
Повний лог — в артефакт прогону (`upload-artifact`); у консоль — лише підсумок і помилки (grep failures/errors). Секрети й дані клієнта
не друкувати; ідентифікатор клієнта — за DATA_POLICY.

## Self-test (відкрите В-3)
При зміні `ci.yml` job перевіряє правила вердикту на фікстурах-підсумках (`.github/ci-fixtures/`): зелений, failures, skipped, 0 тестів,
порожній лог. Місце в `where` картки не закріплено — питання Тімліду; без фікстур — `self-test: N/A`.

## Тури
Множина турів у job == множині сценаріїв «Odoo tour» з `scenarios.md`. Лишній або відсутній тур — FAIL `tours-list`. Тури пише `testing`,
цей скіл лише запускає їх класи/теги.
