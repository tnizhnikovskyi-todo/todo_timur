# Як зробити кейс з джерела

Загальне правило: кейс будується з **конкретної правки або конкретного режиму помилки**. Немає конкретики — кейс не створюється,
а рядок INDEX отримує причину.

## З наблюдення (`observations/*.md`, формат `boost:skill-feedback`)
Читати frontmatter (`skill`, `kind`, `rule`, `repeat_of`, `evidence`, `source`) і тіло <=12 рядків. Поля тіла «Ожидали / Получили» дають:
- `expected.checks` <- «Ожидали» (одне перевірюване твердження на пункт);
- `expected.must_not` <- «Получили» (що скіл зробив не так);
- `prompt` <- наряд/запит запуску зі звіту (`flow/runs/`, чаттер задачі) без рамки тесту;
- `input.fixtures` <- вхідні артефакти запуску за SHA, знеособлені або відтворені синтетично з тією ж структурою;
- `source` = `observation <файл>`, `step` — з наблюдення чи звіту, `skill_version_seen` — з `skill_versions` звіту.
`kind: success_path` -> кейс-підтвердження (що неочевидний шлях працює), не червоний. `repeat_of` -> `barrier: true`.
Правило наблюдення чужою мовою чи в іншому форматі не «виправляти» — брати як є.

## З failureMode картки
Один failureMode -> один кейс. Фікстура мінімальна, але така, де помилка **можлива**; `expected.checks` — що скіл помітив і назвав помилку
явно; `must_not` — сама помилка з failureMode. `source: "failureMode картки <код>"`. Картку читати `jq`-вибіркою.
Failure mode без перевірюваного формулювання (загальні слова) — рядок INDEX «відкладено: немає конкретної правки», питання Тімліду.

## З інциденту C-07
Беруться: причина (дослівно з розбору `boost:debug-root-cause`), доказ (посилання на артефакт/SHA), крок, чи дійшло до клієнта, результат аудиту.
- Причина «клієнт ввів неправильно» без посилання на доказ -> кейс не створювати, повернути на C-07 «причину не доведено».
- Лише ідентифікатори й ролі (DATA_POLICY C-07); дані клієнта не копіювати.
- Кейс іде в `evals/<код-кроку>/` (евал-набір кроку), `source: "incident <id>"`; фікстура — знеособлена копія входів кроку.

## Антипатерни (не робити)
1. Рамка «це тест» / «ти оцінювач» у `prompt` — скіл поводиться інакше, ніж у наряді.
2. Підрядковий грейдер на формулювання скіла — кейс ламається від перефразу; `contains` лише для шляхів і кодів.
3. Кейс, підігнаний під правку скіла (під уже виправлений текст) — кейс має бути червоним на версії, де людина побачила помилку.
4. Загальний сценарій замість правки («перевір, що скіл робить рев'ю») — немає що перевіряти.
5. Кілька правок в одному кейсі — один кейс, одне правило.
6. Реальні дані клієнта у фікстурі — лише знеособлені чи синтетичні.
7. Кейс з наблюдення не вирішальний для A/B-порівняння Тімліда (`boost:skill-feedback`, `weekly-review.md` §5): позначати лише як джерело.
