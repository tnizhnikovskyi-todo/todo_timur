# Уроки, раунди, зразок і прийняте (WP-11; N-08, N-10, N-11, N-18; К-24)

Розширення циклу C-06. Джерела: `_work/SELF-LEARNING.md` §1–2, `FIRST-TIME-RIGHT.md` §2.7. Ключі наряду й звіту — `naryad-format.md`, `report-format.md`.

## 1. Крок 0 (підпункт 0б) — preflight середовища до витрати бюджету (N-08)
- Після кроку 0 (агенти, alias `flow`) і ДО оренди й виклику виконавця: `tools/odoo/preflight.sh --profile <access_profile наряду> --step <код кроку>` (запуск з кореня репо флоу; `c00-checklist.md`, «Preflight у циклі кроку»).
- Ключ картки: `access_profile` і код кроку з наряду; `--needs` лише як ручне перевизначення.
- Вивід — JSON `[{id,status,msg}]`. Будь-який `FAIL` -> `result: waiting_human`, `waiting_for {role: AI-інженер, what: "<перелік FAIL>", resume: {step, params}}`, оренду не брати, виконавця не викликати. `WARN` -> рядок у `memo` («не перевірено: …», зокрема EE без доступу: К-12, відкрите питання власнику). `MANUAL` -> у `memo` як відкрите питання.
- Скрипта немає (`tools/odoo/` не розгорнуто) -> `FAIL` «preflight відсутній» (не пропускати мовчки).

## 2. Observation за подією (SL §2.1; K-24)
Подія -> observation (`boost:skill-feedback`, шлях `observations/YYYY-MM-DD-<skill>-<slug>.md`) **у тому ж ході**, окремим комітом у гілці кроку, шлях у `observations[]` звіту:
| Подія | Що писати |
|---|---|
| «Повернути» (`returned_from`) | коментар людини дослівно без даних клієнта, код гейта, `skill@версія`, посилання на задачу/PR |
| `escalated` | причина зупинки (ліміт, FAIL, відхилений виклик), спроби, моделі |
| червоний CI на кроці AI | назва workflow, run id, провалена перевірка, SHA |
| зауваження людини під час кроку (чат, коментар PR) | присвоїти `R-NN` у `$T/remarks.md` (рядок `- [R-NN] <суть>`), одразу створити observation з рядком `remark: R-NN` |
Поле «репо/задача» в observation — `<owner/repo>#<task id>`. Дані клієнта — лише коди (K-xx, П-xx). Одне зауваження = один observation; повтор зауваження -> той самий observation + «повтор» (сигнал `repeat_of` для C-08R).
**Джерела `remarks.md`** (не лише самозвіт runner): (1) коментарі «Повернути» з чаттера задачі; (2) коментарі PR кроку (GitHub, читання); (3) повідомлення людини в сесії; (4) самозвіт runner — лише доповнення. На кроці 0 runner створює `$T/remarks.md` і наповнює його з (1)-(3) перед перевіркою (3). **Повторний вхід після «Повернути»** (нова сесія, `$T` порожня): `remarks.md` відновлюється з чаттера задачі й коментарів PR **з початку задачі** (усі спроби), а `--since` = дата першої спроби.
Зауваження, що не є помилкою скіла (побажання, зміна рішення власника), записується з `(не помилка: <причина>)`; без причини — вважається помилкою. Кожну таку позначку runner **виносить у `memo` звіту** («не помилка: R-NN — причина»), щоб людина бачила її на гейті; C-08R звіряє сигнали `chat`/`review-comment` з observations і ловить позначки, яких людина не підтвердила.

## 3. Перевірка перед «done»: `check_lessons.py` (LSN-coverage)
`python3 -I ${CLAUDE_PLUGIN_ROOT}/skills/flow-step-runner/scripts/check_lessons.py --remarks $T/remarks.md --observations observations/ --task <id задачі наряду> --since <дата початку сесії> [--expect-remarks]` (крок 9 (з); результат у `checks[]`). **`--expect-remarks` runner додає, якщо наряд має `returned_from` або `human_rounds > 0`** (людина вже давала зауваження): тоді відсутній чи порожній `remarks.md` = FAIL, а не SKIP (випадок «зауваження не записано»).
- **Прив'язка до сесії**: номери `R-NN` рахуються в межах сесії, а `observations/` накопичується між кроками. Тому observation покриває зауваження лише якщо має `remark: R-NN`, його дата в імені файлу ≥ `--since` і в тексті є `#<id задачі>` (поле «репо/задача»). Без `--task`/`--since` скрипт дає WARN `LSN-session-scope`; runner їх передає завжди.
- `FAIL` = у сесії є зауваження без observation цієї сесії -> створити observation і повторити перевірку (спроба виконавця не рахується).
- Файлу `remarks.md` немає або зауважень немає і прапорця `--expect-remarks` немає -> `SKIP`, код 0 («зауважень у сесії немає»); так само в C-08R і в daily-прогоні. Нерозпізнаний рядок `R-…` (напр. `[R-1]`) -> `WARN` `LSN-remark-format`.
- Режиму «перевірка проти `flow/lessons/`» скрипт не має: у C-08R покриття сигналів перевіряє `skill-retro/scripts/check_retro.py` (ЗАПИТ до WP-03: у `C-08R.yaml` викликати його, а не `check_lessons.py`).

## 4. Раунди (N-10)
- `review.max_rounds` наряду (типово 2; = `rounds.review_max` анкети) — кола виконавець->рецензент; після них **один контрольний** круг (разом <= 3). Далі — `escalated` або `waiting_human` (людина вирішує), не четвертий круг.
- У звіті: `review_rounds` (скільки кіл), `human_rounds` (скільки разів «Повернути»/правки людини на цей крок; береться з `returns` і журналу задачі). `human_rounds > 2` -> observation-подія `human-rounds` і сигнал для C-08R (`mode: event`).
- Вимоги людини посеред циклу — у бриф **наступних** раундів (блок «Зауваження до виправлення»); бриф раундів, що вже відбулися, не переписувати й не змінювати їхні входи.

## 5. Захист схваленого: `ACCEPTED.md` (N-11)
- Якщо крок має `accepted_ref` (звіт) або поряд із `where` є `ACCEPTED.md`: runner дає виконавцю його шлях у брифі як **незмінне**.
- `ACCEPTED.md` ведеться лише там, де він у `where`/outArtifacts картки (зараз A-21, A-21c); інакше runner не пише файл (автоперевірка «зміни лише в where» дала б FAIL), а вносить прийняте в `memo` звіту й ставить `accepted_ref: null` (щоб файл вели скрізь — запит до WP-03 на додавання `ACCEPTED.md` до дозволених шляхів).
- Людина прийняла/похвалила фрагмент (гейт, коментар «це добре») -> runner (де файл дозволено) додає рядок у `ACCEPTED.md` кроку: `що · версія/SHA · файл · хто/коли`.
- Зміна прийнятого — лише з блоком «було / стало» у пам'ятці PR (diff позиції з `ACCEPTED.md`); без нього рецензент ставить блокуюче зауваження. `accepted_ref` — у звіт.

## 6. Зразок (N-18) і `resume`
`params.sample: true` (кроки A-03b, A-20c, A-21, A-21c за карткою; обсяг зразка — з картки `step-cards.md`) -> виконавець робить лише зразок, `sample: true` у звіті, **завжди** `result: waiting_human` з `waiting_for {role: <за карткою>, what: "прийняти/повернути зразок", resume: {step, params: {sample: false}}}`. Повний обсяг — після відповіді людини. K1 в A-03b — той самий механізм (`resume` з відповідями `K1-Q*`; відповіді не вигадувати). `prototype.fidelity: mock` (К-23) -> `waiting_human` з поясненням, виконавця не викликати.

## 6а. Бриф рецензента (`review.checklists`)
Чек-листи з `review.checklists` (файли `flow-core/references/review-checklists/`) runner кладе в `$T/ctx/checklists/` і вказує в брифі; рецензент іде по пунктах і видає зауваження з номером пункту. **Обов'язковий перегляд візуального результату**: сторінка, кадри, скріни, відео-кадри з `where` відкривають (Read зображення / рендер) — «лише код» рецензією не вважається. Немає візуальних файлів у `where`, а чек-лист вимагає їх -> блокуюче зауваження.

## 7. Перерахунок (N-07)
`params.mode: recalc` + `stale: [...]` -> виконавець перераховує лише ці артефакти за `research/DEPENDS.yaml`; після — повторити `check_stale.py` (`checks[]`), `stale` у звіті = залишок (має бути порожнім).
