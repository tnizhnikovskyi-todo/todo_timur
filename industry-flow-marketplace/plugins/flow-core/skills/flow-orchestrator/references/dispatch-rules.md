# Правила диспетчера (деталі до SKILL.md)

## 1. Порядок фільтрів кроку 2
Для кожного кандидата: стоп-лист → «блокує запуск» → preconditions → згода → входи → ідемпотентність → слот.
Перший FAIL дає дію з таблиці §6 і зупиняє обробку кандидата. Стоп-лист перевіряти ДО будь-якої дії (включно з активностями).

## 2. Ключ ідемпотентності
Єдине визначення — `flow-core/references/odoo-bridge.md` §7: `(step, scope.id, attempt, scope-ключ злиття)`, пошук дублів серед задач у будь-якій стадії, крім `Повернено`
(стадія `Скасовано` теж рахується). Тут правило не дублюється. Збіг → `skipped`. Відновлення після збою: перерахувати ключ і продовжити з кроку, де обірвалося; готові задачі не дублювати.

## 3. Оренда й спроби
- Термін оренди = `timeoutMin` картки × 1,5 (коефіцієнт змінюється в `dispatcher.yaml`).
- Оренда минула в `В роботі` = спроба використана: `attempt+1`.
- Невзята задача (оренди не було) спробу не споживає.
- `attempt` > `maxAttempts` → ескалація за полем `escalation` картки; нова задача не створюється.

## 4. Слоти паралельності
Рахувати зі стану Odoo: задачі AI (`executor` ≠ `human`) у стадіях `Черга`, `В роботі`, `Автоперевірка`.
Ліміт: ≤3 на пакет, ≤1 на клієнта. Окремого лічильника не зберігати. Людські задачі й гейти в ліміт не входять.

## 5. Кроки «на одиницю», людські й змішані
- «На одиницю» (кроки з `per_unit_steps` у `dispatcher.yaml`): `limits` × N; N (клієнтів або запитів) записати в `units_N`.
- Людський крок: задача ролі `raciR` + активність; завершення лише кнопкою/позначкою за `path`.
- Змішаний крок: AI-задача + людська задача ролі; людська залежить від AI-частини.

## 6. Результат → дія
| Результат | Дія (`action` у звіті) |
|---|---|
| створено задачу | `created` |
| невзяту/прострочену повернуто в чергу | `requeued` |
| змінено виконавця (центральний агент) | `reassigned` |
| вичерпано спроби / escalated / timeout / costLimit | `escalated` |
| заблоковано рішенням ролі (2×humanSla для raciA) | `blocked` |
| слот зайнятий | `held_slot` |
| стоп-лист (без сповіщень: ескалація й зняття — C-08/runner) | `skipped_stoplist` |
| preconditions / «блокує запуск» / входи FAIL / немає плагіна чи версії в каталозі / відкликана згода й людського виконавця (`raciR`) не визначено | `skipped_precondition` (згода з людським виконавцем → `created` з `executor: human`) |
| дубль ключ ідемпотентності | `skipped` |

## 7. Відкриті питання до людини
- Слот: пари `held_slot` підбирає sweep зі звітів C-01 (`sweep-rules.md` §1).
- Автоматизація Odoo (C-00) для `on-complete` («змінилась стадія → задача оркестратору») — рішення q14: AI готує чернетку, Тімлід затверджує.
- Точні технічні імена полів і стадій Odoo (`flow/ODOO_SCHEMA.md`) — q14: AI-чернетка, Тімлід затверджує; до затвердження не вгадувати.
- Шлях карток кроків у репо флоу (`flow/cards/<код>.json` — пропозиція).
- Чи лишати перехід B-03 → B-02 у `escalation` B-03 (відкрите питання до карти).

## 8. Резервна таблиця «перевірка → код повернення»
Лише коли `returned_to` звіту A-14 не містить усіх кодів (джерело — `returned_to`; зміст CHECKS.md не читати). Береться з `checks[]` звіту (`status: FAIL`):
| id перевірки / гейта | код кроку |
|---|---|
| `pr-review`, `security-review`, `odoo19-lint` (модулі) | A-11 |
| `config-review` (конфіг) | A-12 |
| `master-data*` (майстер-дані) | A-13 |
| `track-convergence` | не повертає самостійно: ставиться лише після APPROVE інших гейтів |
Не збігся жоден id → стоп і активність Тімліду «немає коду повернення». A-17 / A-18: коди бере лише з `returned_to` (таблиці немає); порожньо → стоп.
Лічильник циклів A-11/12/13 → A-14 (3 без APPROVE → ескалація Архітектору) — за `attempt` кроку A-14 у стані Odoo.
