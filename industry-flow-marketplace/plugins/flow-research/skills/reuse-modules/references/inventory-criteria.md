# Критерії інвентаризації готових модулів ToDo (A-03c, К-18)

Для кожного кандидата (модуль із репо `defaults.reuse.repos` анкети, проєкту `defaults.reuse.projects`, власної ERP) заповнити 7 критеріїв. Невідомо — `невідомо`, не здогадуватись.

| Критерій | Що перевірити | Джерело | Правило рішення |
|---|---|---|---|
| Версія Odoo | `version` у `__manifest__.py` (`19.0.x` -> так; `18.0` -> міграція; інше -> невідомо) | репо (GitHub-читання) / `ir.module.module` власної ERP | не 19.0 -> лише «адаптуємо» (потрібна міграція) |
| Редакція | залежності `depends`: EE-залежність визначати за відсутністю модуля в репо odoo/odoo 19.0 (CE); без доступу до CE-вихідників чи EE — «не перевірено» (переліки EE-модулів як факт не наводити, К-12; приклади — лише рядком `edition-claims.md` з вердиктом і доказом) | `__manifest__.py` | залежить від EE -> кандидат лише в `td_*_ee`, не в ядро CE (К-06) |
| Права на код | хто автор, чий репо, ліцензія файла/маніфесту (`license`) | репо | невідомо -> «ні» до уточнення; AGPL у ядрі заборонено (К-09) |
| Тести | є `tests/`, чи проходять на 19 | репо; CI-логи, якщо доступні | немає тестів -> тести дописати при адаптації |
| Підтримка | дата останнього коміту, хто підтримує | `list_commits` | >12 міс. без змін -> позначка ризику |
| Відповідність карті функцій | які `F-xx` з `research/FUNCTIONAL-MAP.md` закриває модуль (повністю/частково) | FUNCTIONAL-MAP, код | не закриває жодної F-xx -> «ні» |
| Основа після рішення | `ToDo-готовий` для «беремо/адаптуємо» (К-09) | рішення сесії | «OCA» як основа не пишеться: лише «ідея з OCA, пишемо в `td_`» |

## Джерела (профіль `research-internal`)
- GitHub репо: лише читання (`get_file_contents` для файлів і каталогів, `list_branches`, `list_tags`, `list_commits`); ref/тег фіксувати в `repo:<шлях>@<sha>`.
- AIKB: `search_knowledge_base` за темою модуля; документ ТР/SPEC модуля.
- Власна ERP (`own-erp`): лише `odoo_search_read` по `ir.module.module` (установлені модулі, версія), без даних клієнтів.
- Дані клієнтів, ПІБ, суми — не читати й не писати; клас даних `internal-aggregated`.

## Межа з A-04
A-04 (`past-projects-analyzer`) збирає патерни й болі проєктів; A-03c — модулі й код, придатні в збірку. Модуль, знайдений в A-04 «Модулі для повторного використання», тут перевіряється за критеріями вище; дублювати болі проєктів не потрібно.
