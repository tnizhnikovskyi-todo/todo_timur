# Конструктор склада — приложение (W-01 … W-08, W-10 … W-14, W-16, W-17, W-21)

Раздел «3D-модель» прототипа (`../prototype/sklad.template.html`) как отдельное приложение: ядро без DOM,
экран отдельно, хост отдельно. Данные — снимок Odoo `../prototype/data.json` (склад WH) и синтетический второй склад WH2
(`src/core/demo.js`); Odoo приложение не меняет. Открытое из Odoo, оно читает склады базы адаптером (`src/adapters/odoo-api.js`, W-11).

## Команды (из этого каталога, нужен `npm install`)

- `npm run dev` — vite, `http://localhost:5173`.
- `npm run build` — сборка в `dist/` (относительные пути, открывается с любого адреса).
- `npm run build:odoo` — та же сборка в `../odoo_addons/wh_constructor/static/app/` (в git не попадает): её отдаёт модуль Odoo.
- `npm test` — unit-тесты ядра и словарей (`node --test test/*.test.js`).
- `npm run e2e` — Playwright против `dist/` (нужны `npm run build` и глобальный `playwright`; браузер уже установлен).
- `npm run perf` — замер плавности (`e2e/perf.mjs`, после `npm run build`): WH и синтетический склад `?synthetic=10000`; печатает время построения 3D,
  draw calls, кадр при вращении (swiftshader медленнее видеокарты), время наведения и выбора в 2D; третий замер — WH со зданием и ~1500 колоннами (здание добавляет ≤ 6 draw calls). Критерий: draw calls ≤ 200, построение ≤ 3 с, перестройка без роста числа групп. Первой строкой печатается полный прогон проверок W-07 на синтетике 10 000 мест (в Node, ядро без DOM): критерий ≤ 200 мс.
  W-17: после каждого замера — смена всех пяти показателей тепловой карты; draw calls при этом не растут (цвет — атрибут экземпляра), печатается время переключения.

  (`opts.bases` — снимки складов по `baseRef`); `project.js` (модель проекта v2, миграции, `openProject`, `nodesOf`),
  `demo.js` (демо-проект и склад WH2), `tree.js` (снимок + слой правок + настройки склада → дерево), `layout.js`
  (раскладка в метрах), `edit.js` (diff/apply, стек несохранённых, undo/redo, операции), `select.js` (чистая логика
  выделения), `locks.js` (блокировки зон), `addressing.js` (адресация мест, W-08), `building.js` (план здания и проходы: геометрия, привязка, граф проходов; без состояния), `bldops.js` (операции здания через слой правок), `plan.js` (план изменений Odoo, W-13), `wizard.js` (мастер «З нуля», W-16), `odoodiff.js` (расхождения с Odoo, W-13), `locexport.js` (экспорт локаций в формат импорта Odoo, W-10; режим «как в плане», I-04), `attr.js` и `capacity.js` (ёмкость, категории хранения, атрибуты зон, сводка; W-14), `projfile.js` (файл проекта `.whproj.json`, W-10), `parse.js` (разбор кодов мест, лоток; W-12), `autolayout.js` (авто-раскладка; W-12), `checks.js` (проверки W-07: пересечения, контур, проходы по технике, высота, нагрузка, места с товаром; чистые функции), `metrics.js` (показатели тепловых карт: ABC, возраст, ниже минимума, пусто, заполненность; W-17), `stock.js` (обновление остатков снимка, поиск «где лежит», карточка места, W-17), `storage.js` (интерфейс хранения + хранилище в памяти), `types.js` (константы).
  Подписи изменений и уведомлений — данные `{ k, p }`, текст собирает i18n.
- `src/view/` — `shell.js` (оболочка), `plan2d.js`, `plan3d.js` (three.js, грузится лениво), `building3d.js` (здание в 3D), `bldplan.js` (слой здания в 2D: редактор, привязка, линейки, рулетка), `bldpanel.js` (панель режима «Будівля»), `panels.js`,
  `capacity.js` и `storage.js` (ёмкость и атрибуты в панели, окно категорий хранения; W-14), `tools.js` (свойства, массовое создание, массив, выравнивание, группировка — разметка форм панели), `parse.js` (окно «Розбір кодів»), `tray.js` (лоток «Не розміщено»), `files.js` (меню «Файл»: окна импорта и экспорта, грузится лениво), `problems.js` (панель проблем), `heat.js` (палитры и легенда показателей, W-17), `card.js` (карточка места, W-17), `wizard.js` (панель мастера «З нуля», W-16), `plan.js` (окно «План змін»: применение, журнал и откат), `odoodiff.js` (окно расхождений с Odoo),  `types.js` (окно типов мест), `help.js` (инструкция), `notify.js`, `keys.js`, `style.css`.
  Каталог типов (W-05, см. ниже): `core/catalog.js`, `core/params.js`, `core/library.js`, окно типов `view/types.js` и `view/preview.js` (превью формы).
- `src/adapters/` — адаптеры источников данных, без DOM: `file.js` (файл XLSX / CSV → снимок, W-10), `csv.js`, `xlsx.js` (свой ZIP + SpreadsheetML, грузится лениво); адаптер API Odoo (`odoo-api.js`) — W-11.
- `src/i18n/` — `uk.js`, `en.js`, `createI18n` → `t(key, params)`. Язык запоминается в `wh-app-lang`.
- `src/adapters/odoo-api.js` — адаптер чтения Odoo 18/19 (W-11, см. «Работа из Odoo»); `src/view/odoopick.js` — окно выбора складов базы.
- `src/host/main.js` — загрузка данных, открытие проекта, монтирование view; `src/host/demostats.js` — демо-движения и возраст для тепловых карт (синтетика с пометкой «демо», W-17); `src/host/storage.js` — хранилище в `localStorage`
  (ключи `wh-app-*`, проект — `wh-app-project-<id>`); `src/host/odoo.js` — хранилище модуля Odoo (см. «Работа из Odoo»).
- `src/core/synthetic.js` — генератор синтетического склада (n мест, 10 рядов × 20 стелажей × 5 ярусов на зону); хост подключает его по `?synthetic=N`
  (только для проверки: проект в памяти, `localStorage` не трогается).
- 3D (D-03): одинаковые элементы (геометрия + материал + тени) — один `InstancedMesh`; `paint` решает видимость и подсветку и собирает матрицы
  (`compose`), клик/наведение — raycast по инстансам → узел, перетаскивание сдвигает матрицы. Тени пересчитываются только при изменении сцены.
  2D: SVG создаётся один раз, перестройка меняет слой содержимого, подсветка — атрибутами только у изменившихся элементов.
  Отладочные данные для perf кладутся в `window.__WH_DEBUG`, если он задан до загрузки.
- `test/` — тесты ядра на `data.json` (`core`, `project`, `i18n`, `metrics` — W-17); `e2e/smoke.mjs` — сценарий в браузере (включая склады, ячейки, файлы и 390 px); `e2e/fixtures/` — файлы для шагов импорта.

## Модель проекта v2 (`core/project.js`)

- `project { schema: 2, id, name, source { kind: odoo|file|scratch, name }, loaded_at, warehouses[] }`;
  `warehouse { id, code, name, company, baseRef | base, saved, pending, building: null }`.
  Склад владеет слоем правок: `saved` (SAVED) и `pending` (PENDING); типы мест склада — `saved.types` (`null` — общий
  справочник `BASE_TYPES`, иначе свой список поверх него). `building` — сохранённый план здания (копия `saved.building`, см. «План здания»).
- Узлы склада производные: снимок Odoo + слой правок → дерево (`tree.js`) → `model.nodes()` / `nodesOf` даёт плоский
  список v2: `level` (zone, rack, bay, level, cell, floor), `tp`, `x y rot w d h`, `code`, `odoo_id` (null у новых и если
  в снимке нет id), `status` (existing, new, changed, archived), `is_location`. Корень любого склада — узел `WH` (id), подпись — код склада.
- Глубина локаций — часть слоя правок: `edit.depth` (`null` = `level` | `cell`) и `edit.depthZones [{ id зоны, d }]`; меняется
  операцией `ops.depth` через «Показати / Зберегти» с undo, как всё остальное. Ячейки яруса — `edit.cells [{ id яруса, n }]` (1–12, через «Показати / Зберегти»); при глубине `cell` и n > 1 ярус
  перестаёт быть местом, местами становятся ячейки `<код яруса>-1..n`.
- Хранилище (`core/storage.js`): `listProjects / loadProject / saveProject / deleteProject` — Promise, плюс синхронные
  настройки `read / write`. Формат версионирован (`migrateProject`). При первом запуске `openProject` создаёт демо-проект и
  переносит в склад WH правки прежних ключей (`wh-app-edit/pending`, прототип `wh-model-edit/pending`); старые ключи остаются.
  Нечитаемый проект не перезаписывается: сырая запись уходит в `wh-app-project-<id>.broken-<время>` (`backupBroken`), открывается
  демо-проект `demo-<время>`, `onNotice` → уведомление.

## План здания и проходы (W-04, D-10, D-21)

- Здание — **геометрия склада в метрах** (не локации Odoo), поле слоя правок `edit.building`: `{ v: 1, contour: [[x, y], ...], hCeil, hSpr, items: [...], nodes: [...] }`.
  `contour` — прямоугольник (4 вершины) или многоугольник; `hCeil` / `hSpr` — высота до потолка / до спринклеров. `items`: колонна `col`
  (центр, сторона), стена `wall` (отрезок, толщина), прямоугольники `gate`, `dock`, `door`, `office`, `charge` (у ворот и доков — `loc`, код локации Odoo
  или `null`), проход `aisle` (ребро графа `a`–`b` между узлами из `nodes`, ширина `w`). Узлы с одинаковыми координатами сливаются — так проходы связываются;
  конец прохода на оси другого прохода делит его (развилка). Маршрутов нет (L2–L3 — позже): ширина проходов нужна проверкам W-07.
- Через слой правок здание проходит как остальные данные: объект правки `building`, diff — общие поля (`bld`) и объекты / узлы по id (`bi`, `bn`),
  операции `model.bld.ops.*` (`bldops.js`: create, remove, contour, vertex, addVertex, delVertex, splitLongest, heights, add, grid, aisle, move, node, set, del),
  «Показати / Зберегти» (`model.save(building)`), undo / redo; числовые правки одного объекта склеиваются, сдвиг — нет. Сброс «к данным Odoo» план здания не трогает.
  Проект хранит его в `warehouse.saved.building`; `warehouse.building` — та же сохранённая копия (проекты, где здание лежало только в `building`, переносятся в слой при чтении).
- Состояние редактора — `model.bld.state` (`on`, `tool`, `grid` 0,1 / 0,5 / 1 м — запоминается как `bgrid`, `snap`, `sel`, `first`, `ruler`), событие `{ type: bld }`.
  Режим «Будівля» (кнопка рядом с 2D / 3D) показывает 2D с редактором и исключает режим «Редагувати». Рулетка (`ruler`) и точки линий — состояние редактора, не проект.
- Места внутри контура: `model.bld.outside()` — ряды и места на полу, не лежащие целиком в контуре (`rectInPoly` с невыпуклыми контурами); панель показывает предупреждение, а новая правка, выводящая место за контур, отклоняется проверками W-07 (ошибка `outside`).
- 3D (`building3d.js`): непрозрачные формы — один `InstancedMesh` с цветом на экземпляр, офисы — второй, контур пола — плоскость и две линии (пол и уровень спринклеров): ≤ 5 draw calls.
- Тесты: `test/building.test.js` (геометрия, привязка, сетка колонн, граф проходов, операции через слой правок, сохранение и «перезагрузка»), шаг e2e «план будівлі…».

## Работа из Odoo (W-21, D-22)

Модуль `../odoo_addons/wh_constructor` отдаёт приложение с адреса базы (`/wh_constructor/app`, меню Склад → Конфігурація → Конструктор складу)
и добавляет в страницу `window.__WH_ODOO__ = { api, db }`. Хост по нему выбирает хранилище: есть — `createOdooStorage` (`host/odoo.js`), нет — `localStorage`.

- Интерфейс `odooStorage` тот же, что у `core/storage.js` (асинхронные `listProjects / loadProject / saveProject / deleteProject`, настройки `read / write`
  в `localStorage` с ключами `wh-odoo-<база>-*`), плюс `init` (права группами Odoo: без «проектирования» `readonly = true`), `me`, `lock`, `unlock`,
  `versions`, `restore`. Обмен — JSON-RPC (`POST /wh_constructor/api/...`, сессия Odoo); `fetch` подставляется (в unit-тестах фейковый).
- Сохранение: `saveProject(p, { commit })`. Явное «Зберегти» (`commit: true`) создаёт версию проекта на сервере (хранятся последние 50);
  черновик (несохранённое, любая правка) версий не создаёт, частые вызовы склеиваются (400 мс). Сервер хранит ревизию `rev`, клиент шлёт `base_rev`;
  если проект в базе новее — ответ `stale`, хранилище больше ничего не шлёт, уведомление «Проєкт змінено іншим користувачем» (перезагрузка страницы).
- Блокировки зон (`core/locks.js`, только если у хранилища есть `lock`): при входе в правку (выделение узла) берётся блокировка его зоны — ближайшего
  предка-группы; занята другим — уведомление `n.zoneLocked`, `edit.change` отказывает правке этой зоны, строка статуса показывает владельца и срок.
  Хост продлевает блокировки раз в минуту (`model.locks.renew`), выход из правки и закрытие страницы их снимают; срок на сервере — 5 минут.
  Блокировка берётся асинхронно: правка в первые миллисекунды после выбора зоны не блокируется.
- **Чтение данных Odoo (W-11, D-06, D-07).** `adapters/odoo-api.js`: `createOdooApi({ api, fetchImpl, pageSize })` → `listWarehouses()` и `load(warehouseId)`; `load` возвращает
  снимок **того же формата, что `data.json`** (те же ключи верхнего уровня `meta, products, locations, purchase_orders, productions, quality_checks`; записи мест — `complete_name,
  quants, capacity, fill, kind` и необязательные `state`, `orderpoint`; у остатка — `age`), плюс `id` места (из него `odoo_id` узла), `usage`, `barcode`, `parent_id`, `storage_category_id`, `removal_strategy_id`, `removal_strategy`,
  `posx/posy/posz`, флаги — те, что есть в версии Odoo. Дополнительные данные лежат в `meta.odoo`: `version`, `warehouse_id`, `view_location_id`, `containers` (зоны и view-корень
  по пути узла — `WH` — с их `id`; `nodesOf` берёт `odoo_id` зон оттуда), `storage_categories`, `putaway_rules`, `orderpoints`, `removal_strategies`, `package_types`. Местом становится локация без дочерних и любая с остатком;
  ключ места — штрихкод локации, а без него имя (при совпадении — `ключ~id`; D-14: в имени короткое имя уровня, полный код — в штрихкоде). `capacity` — max правила пополнения (`kind: bin`), иначе ёмкость категории хранения по товару (`shelf`) или по упаковкам (`pallet_cell`);
  `fill` — остаток к ёмкости (не больше 1), `state` — `out` / `low` / `ok` по min правила. Сервер отдаёт страницы (по умолчанию 2000), адаптер собирает их; ошибка любого запроса — отказ `load`.
  W-17: `load` читает ещё `moves` (выполненные движения за 90 дней, `createOdooApi({ moveDays })`) и кладёт `meta.activity`; возраст остатка — из `in_date` (`ageDays`). Эндпоинты и различия 18 / 19 — `../odoo_addons/wh_constructor/README.md`.
- Склад проекта из Odoo ссылается на снимок через `baseRef = "odoo:<id склада Odoo>"` (`odooRef`, `odooIdOf`); сам снимок в проекте не хранится (проект остаётся лёгким), хост грузит его при открытии
  страницы. Первый запуск в Odoo без проектов — окно «Новий проєкт з Odoo» (выбор складов базы, мультисклад D-09; «Демо-проєкт» оставляет демо); та же кнопка «Проєкт з Odoo…» в верхней панели
  создаёт ещё один проект и перезагружает страницу. Кнопка «Оновити з Odoo» перечитывает снимки складов проекта и вызывает `model.reloadBase()`: дерево перестраивается, слой правок и несохранённое
  остаются (сравнение изменений и применение — W-13). Склад, который не загрузился, остаётся пустым, пользователь получает уведомление. Вне Odoo — `data.json`, как раньше. Остатки без перестройки — «Оновити дані» (см. «Данные склада на модели»).
- Проверка без Odoo: unit-тесты `test/odoo-api.test.js` (фейковый сервер со страницами, формат снимка, дерево и `odoo_id`, `reloadBase`), `test/odoo.test.js` (фейковый fetch и сервер) и шаг e2e с подменой маршрутов `/wh_constructor/api/**`.

## Данные склада на модели (W-17, D-18)

Ядро — `core/metrics.js` и `core/stock.js` (чистые функции, без DOM); состояние — `model.heat`, `model.find`, `model.refreshData`, `model.place`; экран — `view/heat.js`, `view/card.js`, панель над планом в `view/shell.js`.

- **Что добавилось в снимок.** Формат `data.json` прежний; Odoo-адаптер добавляет у остатка `age` (целых дней от `in_date` партии до `now` снимка) и `meta.activity { days, moves: { <код места>: { n, qty } } }` —
  выполненные движения (`stock.move.line`) за окно (90 дней), строка «откуда → куда» считается для обоих мест. В `data.json` этих данных нет: **хост** (`host/demostats.js`, `decorateDemo`) достраивает их детерминированной
  синтетикой (хэш кода места; скошенное распределение, чтобы ABC различались) и ставит `meta.activity.demo = true` — в легенде и карточке стоит «демо». Ядро синтетику не создаёт.
- **Обновление (H1).** Кнопка «Оновити дані» над планом (и чтение при открытии страницы): в Odoo хост перечитывает снимки складов проекта и вызывает `model.refreshData({ baseRef: снимок })`; вне Odoo — `model.refreshData()` пересчитывает
  и перерисовывает из текущего снимка. `mergeStock(base, fresh)` переносит только остатки места (`quants`, `capacity`, `fill`, `state`, `orderpoint`), товары, движения и время снимка; место сопоставляется по id Odoo (иначе по ключу).
  Структура (`kind`, новые и пропавшие локации, id), дерево и слой правок не трогаются, `rebuild` не отправляется (событие `data`; 2D перекрашивается, 3D пересобирает только содержимое мест); новые локации Odoo — через «Оновити з Odoo» (W-11 / W-13),
  уведомление `n.dataAdded` сообщает, сколько их. Правила размещения и категории хранения в карточке обновляются так же, как структура, а не кнопкой данных. Время снимка — в подсказке кнопки и в панели склада.
- **Показатель (H2).** Список «Показник» над планом: «Стан місць» (прежняя раскраска) и пять тепловых карт; выбор запоминается (`wh-app-heat`). `model.heat`: `mode`, `set`, `map()` (код → ключ класса), `counts()`, `hasData()`, `demo()`.
  Классы: заполненность — `f0 / f25 / f50 / f75 / f100 / none` (по `fill`); ниже минимума — `out / low / ok / none` (по `state`, без него — по `orderpoint` и остатку); пустые места — `empty / used`; ABC — `A / B / C / none`
  по числу перемещений места (`abcClasses`: места по убыванию, класс по доле перемещений *до* места: < 80 % — A, < 95 % — B, остальное — C; без перемещений — `none`); возраст — `d30 / d90 / d180 / d365 / dmax / none`
  по самой старой партии с остатком (`ageBucket`, `placeAge`). Новые и несохранённые места раскраску показателя не получают (остаются бирюзовыми и оранжевыми). Легенда (`legendHtml`) показывает цвет, подпись и число мест в классе,
  пометки «рухи за 90 дн.», «демо» и «немає даних» (если у снимка нет движений или дат).

  показателя — только перекраска (`paint` + `compose`, без перестройки). Цвета тем (`--ok`…) перечитываются при смене темы.
- **Поиск «где лежит» (H3).** Строка над планом: название или артикул товара, партия (lot), упаковка; несколько слов — все в одном остатке; от двух символов (`searchStock`). Найденные места подсвечиваются на плане (2D — класс `hit`,
  3D — материал выделения), рядом счётчик, под строкой список «место · товар · количество · партия» (до 50 строк); клик (или Enter — первый) вызывает `model.find.go(код)`: фокус на уровень выше места и выделение. Esc закрывает список, повторно — очищает.

## Применение в Odoo (W-13, D-17)

Работает только в странице из Odoo (`window.__WH_ODOO__`): кнопка «План змін» (`#plan-btn`) рядом с «Оновити з Odoo». Склад проекта должен быть из Odoo (`baseRef = "odoo:<id>"`), снимок содержит `meta.odoo`.

- **План** (`core/plan.js`, `model.changePlan()`): `computePlan(data, edit, cfg)` сравнивает **сохранённый** слой правок (несохранённое в план не входит, `unsaved` — сколько его) с снимком Odoo и возвращает
  `ops` (родители раньше детей; архивация — дети раньше родителей) и счётчики `stats`. Виды операций: `create` (новая локация; ряд, секция и зона создаются как внутренние локации с именем узла,
  место — с коротким именем уровня (`name` из плана нумерации W-08, у ячейки — её код), штрихкодом = полный код и родителем по иерархии; без мест контейнер не создаётся; в Odoo 18 ещё `posx / posy / posz` из плана нумерации W-08), `move` (узел с `from` — перенос существующей
  локации, а не создание; сравнивается родитель в Odoo с родителем в дереве), `rename` (перенумерация `edit.codes`: короткое имя уровня; имя контейнера из `edit.prop`), `attrs` (штрихкод = новый код и позиции после перенумерации),
  `archive` (убранные узлы, которые есть в Odoo и не перенесены; дети раньше родителей), `category` и `orderpoint` (W-14, ниже). Родитель в Odoo — ближайший предок, который есть в Odoo или создаётся этим планом: ряды и секции, которых в Odoo нет
  (дерево по кодам FUR / EB / RCK…), пропускаются. `blocked` — на архивируемом месте или под ним есть остаток (F4), `conflict` — штрихкод уже занят другой локацией: такие операции не применяются
  (`applicable`). Версия Odoo 19 не имеет `posx / posy / posz` — их в операциях нет (`posSupported`).
- **Частичное применение (G4)**: у операции есть `node` (id узла-пути): выбор зоны или ряда — `scopeOptions` / `inScope`; `closure(plan, keys)` добавляет к выбранному родителей новых локаций и родителя переноса.
- **Проверки W-07**: пока в панели проблем есть ошибки (`model.checks.counts().error`), «Застосувати» и файл недоступны; окно показывает число ошибок и кнопкой ведёт к панели проблем и первой ошибке.
- **Применение (G3)**: `wireOps` → `storage.applyPlan` → `POST /wh_constructor/api/apply/run`: сервер применяет одной транзакцией и сам проверяет, что архивируемое пусто (см. README модуля). После успеха хост
  перечитывает снимок (`reloadBase`) и вызывает `model.applied(plan, keys)`: `cleanApplied` убирает из слоя применённое — `del` и убранные узлы (`gone`) архивации, `codes` и имя в `prop` переименований,
  метки `from` у перенесённых. **Созданное слой не меняет**: добавленные узлы хранят структуру (ряд, секции, тип), а снимок Odoo теперь содержит их места — дерево считает такой узел существующим (`adopted`,
  `tree.adoptedAdd`: место — по коду, контейнер — по пути), снимок его не дублирует; `nodesOf` даёт `odoo_id` и статус `existing` (`changed`, если у яруса есть настройка ячеек). Убрать применённое — `del`
  (узел с `adopted` внутри не вычищается из слоя, а помечается `gone`, дерево отдаёт его плану как «убранное» → архивация).
- **Файлом (G3, I-04)**: «Файл для імпорту…» открывает экспорт локаций W-10 (`openExportLocations`, XLSX / CSV в формате импорта Odoo). Режим «как в плане» берёт выбор в плане и даёт то же, что применение через API: контейнеры `internal`, создание, перенос, перейменование, атрибуты и архивация (колонки `.id` и `active`); что импорт сделать не может (категории и их ёмкости, правила min / max, проверка пустого перед архивацией, журнал и откат), перечислено в окне — см. «Ёмкость, категории…».
- **Журнал и откат (G5, G8)**: вкладка «Журнал» (`storage.applyLog`), «Відкотити» — второе нажатие подтверждает (`storage.rollback`). После отката снимок перечитывается: созданные узлы снова «новые» (их слой цел),
  план предлагает создать их опять; откат старого применения возможен только по порядку (сначала более поздние, затронувшие те же локации); откат архивации и переименований возвращает прежнее состояние Odoo, а запись слоя, убранная при применении, не восстанавливается.
- **Тестовая копия (G9)**: при первом применении в проекте окно напоминает прогнать на копии базы; «Більше не нагадувати» — настройка `wh-odoo-<база>-copyack-<проект>`, первое применение — `applied-<проект>`.
- **Расхождения с Odoo (G7)** (`core/odoodiff.js`, `view/odoodiff.js`): «Оновити з Odoo» сравнивает прежний снимок с новым по id локаций — `added` (появилась), `gone` (исчезла), `renamed`, `moved` (другой
  родитель; появившееся и исчезнувшее — верхним уровнем) — и открывает окно. Для каждой строки «Прийняти з Odoo» (по умолчанию: слой не меняется) или «Залишити моє» → `model.keepMine(picks, old)` — несохранённая
  правка слоя (undo, «Показати / Зберегти»): появившееся убирается из модели, исчезнувшее возвращается (узлы из прежнего снимка), переименованное получает прежний код / имя, перенесённое возвращается к прежнему родителю;
  план предложит вернуть это в Odoo.
- Проверка: `test/plan.test.js` (все виды операций, перенос по `from`, частичный выбор, применение на фейковой базе `test/fakeodoo.js`, очистка слоя, «применить → прочитать снимок → то же дерево»), `test/odoodiff.test.js`, `test/odoo.test.js` (маршруты `/apply/*`),
  шаг e2e «План змін» с подменой маршрутов Odoo (открыть, применить часть, файл через экспорт W-10, запрет при ошибках проверок, журнал и откат, расхождения).

## Ёмкость, категории хранения, атрибуты и флаги (W-14, D-15)

Всё — слой правок `edit.attr` (`core/attr.js`: константы и нормализация; `core/capacity.js`: чтение, без DOM) через «Показати / Зберегти» с undo. Правки, которые имеют поле в Odoo, попадают в «План змін» и применяются через API модуля
(порядок на сервере: **категории → локации → правила пополнения**); остальное хранится только в проекте.

- **Слой `edit.attr [{ id, … }]`.** `n|<id узла>` — атрибуты узла (место, ряд, зона, склад): `cat` (ключ категории или `-` — «без категории»), `maxw` и `dm {w,d,h}` (максимальный вес и габариты места — только проект), `repl` / `scrap` / `usage` (флаги места),
  `rs` (id стратегии списания Odoo), `fn` / `at` / `tmin` / `tmax` (функция и атрибуты зоны — только проект), `mm {min,max,product}` (правило пополнения). `c|<ключ>` — категория хранения: `o<id>` — правка категории Odoo (значения целиком),
  иначе новая (`nc1`, `nc2`…, поле `nw`). Новая категория с именем, которое уже есть в Odoo, считается **применённой** (`adopted`): после применения и перечитывания снимка слой её не дублирует — так же, как применённые узлы `adopted`.
- **Читать:** `model.cap.categories()` (список `{ key, id, name, maxw, policy, caps, isNew, adopted, changed }`, `get(ключ)`), `model.cap.node(id)` (категория места с наследованием — ближайшее переопределение выше по дереву, затем категория места в Odoo; габариты; максимальный вес — своё
  значение → вес категории → нагрузка на ярус из типа; флаги и стратегия; правила min / max и товары, для которых их можно задать; функция и атрибуты зоны), `model.cap.summary(id)` (сводка ёмкости), `removalStrategies()`, `packageTypes()`.
  Сводка (`summary`): мест, палетомест (форма `pallet`, тип `PAL` или категория с ёмкостью по упаковке), площадь основания (нижние ярусы, места на полу), объём (габариты места, в том числе заданные), занято / свободно по остаткам, сумма максимального веса, доля заполнения по ёмкости.
- **Править:** `ops.capacity(место, { dw, dd, dh, maxw })`, `ops.catAssign(узел, { cat })` (`inherit` / `-` / ключ; действует на места ниже), `ops.flags(узел, { usage, repl, scrap })` (место с остатком не станет `view`; «место пополнения» отклоняется, если флаг уже есть выше или ниже — правило Odoo),
  `ops.removal(узел, { rs })` (стратегия из списка базы), `ops.zoneFn(узел, { fn, at_<атрибут>, tmin, tmax })`, `ops.minmax(место, { product, min, max })` (только место с товаром в остатке или правилом и только для такого товара), `ops.catSave(ключ | "", { name, maxw, policy, caps })`
  (создание и правка категории; объект правки `scat`, сохраняется `model.save("scat")`; назначение категории сохраняется вместе с ней), `ops.catDel(ключ)` (только новая). Группировка и снятие группировки переносят записи `n|…` на новые id; «Прибрати» и применённая архивация чистят их; «Скинути до даних Odoo» снимает весь слой.
- **План изменений (`core/plan.js`).** Новые виды операций: `category` (создание с `ref` или правка по `id`; `vals { max_weight, allow_new_product, capacities [{ product, package_type_id, quantity }] }`; идёт первой) и `orderpoint` (создание правила — без `id`, правка min / max — с `id` и `prev`).
  Категория, стратегия и флаги — в `attrs` существующей локации (значения, которые уже совпадают с Odoo, операций не дают) или в `vals` создаваемой; назначение категории месту — для **каждого места** под узлом с переопределением; `storage_category_id` — id Odoo или `{ ref }` новой категории.
  `closure` добавляет к назначению категорию, которой ещё нет; `wireOps` передаёт `location_id / product / min / max` правил.
- **Данные Odoo.** Адаптер читает дополнительно `removal_strategy_id` локаций, справочники `removal_strategies` и `package_types` (`meta.odoo`); сервер отдаёт категории хранения склада **и свободные категории компании** — иначе созданная, но ещё не назначенная категория создавалась бы повторно.
- **Экран.** `view/capacity.js` — блоки боковой панели (в режиме «Редагувати» формы, в просмотре — сводка и данные места), `view/storage.js` — окно «Категорії зберігання» (список, создание и правка, ёмкости по товару и упаковке). Функция зоны даёт цвет рамки и подпись в 2D (`data-fn`) и 3D (материал по цвету),
  функция и атрибуты — в подсказке места.
- **Файл для импорта (I-04).** Контейнеры (зона, ряд, секция) во всех режимах экспорта — `internal` без штрихкода (как при применении через API); файловый адаптер считает `internal`-строку без остатка и штрихкода, на которую ссылаются пути других строк, структурой.
  Режим `plan` (`locexport.planRows`, по умолчанию, когда в плане есть операции) строит строки из операций плана: создание, перенос, перейменование, атрибуты, архивация (`.id` — база Odoo, `active` — 0 архивирует; **у каждой строки заполнены все колонки**: пустая клетка в импорте Odoo стирает значение);
  окно перечисляет, чего импорт не умеет (`PLAN_LIMITS`: категории и ёмкости, правила min / max, проект-только поля, проверка пустого перед архивацией, журнал и откат, порядок «создание → изменения → архивация»).
- Проверка: `test/capacity.test.js` (наследование категории, сводка, габариты, функция зоны, ограничения, нормализация слоя; план и применение на фейковой базе 18 / 19; I-04: экспорт, затем модель импорта Odoo, даёт ту же базу, что применение через API),
  шаги e2e «W-14: категория хранения…» и «W-14: функция зоны…».

## Инструменты редактирования (W-06, D-13)

Все операции — слой правок `edit` через «Показати / Зберегти» с undo (`core/edit.js`, `model.ops.*`). Новый слой `edit.prop [{ id, name?, w?, d?, h? }]` —
имя (только подпись, id не меняется) и собственные размеры (до поворота): у места на полу точные, у зоны — не меньше содержимого.

- **Поворот** `edit.rot [{ id, r }]`, `r` = 90 / 180 / 270 (ряд и место на полу). Узел: `rotDeg`; `rot` (меняет ширину с глубиной) — при 90 и 270, `flip`
  (порядок секций / ячеек обратный; 2D `rect2d` в `layout.js`) — при 180 и 270. `ops.rotate(ids)` — как раньше (клавиша R, 90° и обратно), `ops.rotate(ids, deg)` — заданный угол.
- **Свойства** `ops.props(id, f, key)`: имя, X / Y (от угла родителя, до сантиметра), поворот, размеры, число секций и ярусов ряда; применяются только изменившиеся поля.
- **Массовое создание** `ops.mass(зона, { tp, nr, nb, nl, gap, orient })`: ряды ставятся ниже имеющегося содержимого, проход между рядами — `gap`; `model.massInfo(f)` (`massPlan`) — сводка до «Показати».
  Массив мест на полу `ops.grid(место, { nx, ny, sx, sy })` (шаг от начала до начала; исходное место закрепляется на своём положении).
- **Рамка** `model.marquee({ x0, y0, x1, y1 }, add)` (`select.js`: `inRect`): объекты показанного уровня, целиком попавшие в рамку, того типа, что выбран в «Клік виділяє»; в 2D — Shift + протянуть, Ctrl добавляет.
- **Выравнивание / распределение** `ops.align(ids, left|right|top|bottom|cx|cy)`, `ops.distribute(ids, x|y)` — над перемещаемыми объектами (`moveTargets`), одним изменением.
- **Группировка** `ops.groupSel(ids, { name })` / `ops.ungroup(id)`: объекты переходят в новую зону (подзону) и обратно с сохранением положения и **кодов мест**. Узлы Odoo получают записи `add`
  с теми же кодами (`from` — прежний id), прежний корень попадает в `del`; в дереве `tree.js` узел, убранный и созданный заново с тем же id (возврат на прежнее место), сначала удаляется (`reborn`).
  Id узлов меняется (путь содержит родителя), коды — нет; `odoo_id` у перенесённых сохраняется (`nodesOf`), адресация и синхронизация — W-08.

## Адресация (W-08, D-14)

Всё через слой правок «Показати / Зберегти» с undo. Ядро — `core/addressing.js` (без DOM): шаблон, нумерация, уникальность. Запись в Odoo — W-13 («Применение
в Odoo»): `name` (короткое имя уровня), `barcode` (= полный код) и `posx / posy / posz` (Odoo 18) уходят планом изменений.

- **Настройки** `edit.addr` (склад; `null` — по умолчанию) и `edit.addrZones [{ id, ...настройки }]` (переопределение зоны целиком; действует ближайшее выше по дереву). Меняет
  `ops.addr(id, форма)` (`own: "1"` — своё переопределение зоны). Поля (`normAddr`): `tpl` — слова через пробел из текста и сегментов `{зона} {ряд} {секція} {ярус} {позиція}`
  (и `{zone} {row} {bay} {level} {pos}`), слова склеивает `sep`, слово без значений (нет секции у стопки плит, нет позиции у яруса без ячеек) пропускается;
  `seg.<сегмент> { kind: num | alpha, width, start }` (буквы: 1 = A, 27 = AA); `rowFrom` (top | bottom | left | right — сторона входа), `rowMode` (seq | snake),
  `bayDir` (ltr | rtl | oddeven), `levelDir` (up | down), `zoneCode` (текст вместо номера зоны, у переопределения зоны). Позиции (ячейки яруса) — слева направо.
- **Нумерация** `plan(tree, edit, { scope, onlyNew, over })` → `items [{ id, code, name, row, bay, level, pos, posx, posy, posz }]` для мест рядов зоны (зона — узел с рядами; номер
  зоны — по порядку обхода дерева). Ряды — по расстоянию от входа; секции вдоль ряда (у повёрнутого на 90° / 270° — сверху вниз): `seq` — все ряды в одном направлении, `snake` — через ряд
  навпаки, `oddeven` — ряд с нечётным номером получает нечётные секции (1, 3, 5…), с чётным — чётные (2, 4, 6…). Ярус A — нижний (`up`) или верхний (`down`). `posx / posy / posz` — номера
  ряда / секции / яруса (целые), `name` — последний сегмент (позиция или ярус). Места на полу (ворота, тележки, зоны на полу) нумеруются по тому же шаблону зоны: порядок от входа (`rowFrom`), номер идёт в `{позиція}`, а если её в шаблоне нет — в `{ряд}`, `{секція}`, `{ярус}` (первый из имеющихся), иначе отдельным словом в конце; `posx / posy / posz` = 0.
- **Перенумерация** `ops.renum(id, { only })` для склада (`"WH"`) или зоны: слой `edit.codes [{ id, code }]` — код места поверх исходного (Odoo или добавленного). В дереве (`tree.js`) у такого узла `oloc` —
  исходный код (по нему `nodesOf` берёт `odoo_id`), `tree.alias` — новый код → исходный (данные Odoo по новому коду), `tree.renamed` — исходные коды (не «убранные места»). `only` — «только новые»: у каждого уровня
  сначала идут существующие, новые продолжают нумерацию после них; существующие и перенесённые группировкой (`from`) места кода не меняют. Без `only` меняются все, в том числе перенесённые.
- **Уникальность** `findConflicts(tree, others)` / `model.addr.conflicts()`: `dup` — код у нескольких мест склада (`existing` — среди них место Odoo со своим кодом), `other` — новый или изменённый код есть в другом
  складе проекта (прежние совпадения WH и WH2 не считаются). Новые места, которые создают операции (`uniqCode`), сами берут код, свободный и в других складах. `ops` не сохраняет: `model.save` отказывает
  (уведомление `n.codeConflicts`), если в выбранных изменениях участвует место с конфликтом; список с переходом к месту — в панели объекта.
- **Модель**: `model.addr.settings(id) / preview(id, форма) / info(id) / conflicts() / check(tpl)`; `info` — `{ name, barcode, tplCode, same, posx, posy, posz }`.
- Проверка: `test/addressing.test.js` (три схемы, буквы и нули, переопределение зоны, «только новые», конфликты, undo, перезагрузка), шаги «адресация» в `e2e/smoke.mjs`.

## Файлы: импорт и экспорт (W-10, D-06, D-09)

Меню «Файл» в верхней панели (`view/files.js`, грузится при первом открытии вместе с адаптерами): «Імпорт локацій…», «Експорт локацій…», «Експорт проєкту», «Імпорт проєкту…».
Хост передаёт в `mountApp` объект `host { storage, bases, reload }`: хранилище проектов, снимки по `baseRef` и перезагрузку страницы. Скачивание — `Blob` + ссылка (работает и в модуле Odoo);
имя файла только латиницей (`asciiName`: украинские и русские буквы транслитерируются — некоторые браузеры подменяют кириллицу в имени на `download`).

- **XLSX без зависимостей** (`adapters/xlsx.js`, ~7 КБ, отдельный чанк): ZIP (CRC32, сжатие через `CompressionStream` / `DecompressionStream("deflate-raw")`, нужны браузеры 2023 года и новее, Node ≥ 18) и SpreadsheetML одного листа.
  Запись — строки `inlineStr`, числа `n`; чтение — общие строки, `inlineStr`, числа, пропущенные ячейки, первый лист по `workbook.xml`. CSV (`adapters/csv.js`): UTF-8 (BOM снимается) или windows-1251,
  разделитель `,` `;` или табуляция, кавычки и переносы строк внутри поля.
- **Адаптер файла** (`adapters/file.js`, интерфейс как у `odoo-api.js`): `createFileAdapter({ now })` → `open(имя, байты | текст)`, `mapping` / `setMapping({ роль: индекс | -1 })`, `setOptions({ codeFrom })`, `preview()`,
  `listWarehouses()` (склад — первый сегмент полного имени), `load(код склада)` (снимок формата `data.json`: `meta / products / locations`), `project({ id?, name?, codes?, existing })` (проект «из файла»:
  `source { kind: "file", name }`, `loaded_at`, склады со снимком `base` внутри проекта). Роли колонок: `path` (Full Location Name / `complete_name`), `name`, `parent` (Parent Location / `location_id`), `usage` (Location Type),
  `barcode`, `posx / posy / posz`, `product / qty / lot` (остатки `stock.quant`: строки места повторяются). Автоопределение по заголовкам uk / en / ru (`detectColumns`: нормализованное сравнение, словарь синонимов `SYN`).
  Разбор (`parseLocations`): `internal` (или пусто) — место, `view` — структура, остальные типы (клиенты, поставщики…) пропускаются и считаются; полное имя — `path` или `parent/name`;
  код места — штрихкод, если он есть, иначе название (`codeFrom: "name"` — всегда название). Нераспознанное — `issues { row, reason }` (`empty`, `noparent`, `usage`, `dupcode`, `qty`; последняя не отбрасывает место),
  номера строк — как в файле. Место с повторённым путём без остатка — дубликат, с остатком — добавляет остаток. Окно импорта: выбор файла, таблица сопоставления колонок, предпросмотр (места, структура, остатки,
  не распознано, склады), создание проекта; новый проект записывается в хранилище, `storage.write("project", id)` и перезагрузка — он открывается вместо прежнего (прежний остаётся).
- **Экспорт локаций** (`core/locexport.js`, `locationRows(model, { mode, keys })` → `{ headers, rows, counts }`): колонки `name, location_id, usage, barcode, posx, posy, posz` — формат импорта Odoo `stock.location`
  (`location_id` — полное имя родителя). Режим `plan` — «как в плане» (W-14, I-04, см. ниже). Режимы: `all` — все места активного склада и строки структуры (контейнеры, `internal`) над ними; `changed` — места со статусом `new` / `changed` и только те родители, которых нет в снимке Odoo
  (проверка по префиксам `complete_name`). Имя и путь существующего неизменённого места — из снимка, у новых и перенумерованных — из дерева (имя — последний сегмент по шаблону адресации, ячейки — код),
  `barcode` = код, `posx / posy / posz` — из плана нумерации (`addressing.plan`), ноль не пишется. Это основа применения файлом (G3); `id`, архивация, порядок записи и полный план — W-13.

## Проверки и панель проблем (W-07, D-16)

`core/checks.js` — чистые функции без DOM: `runChecks({ tree, edit, data })` → `{ problems, keys, counts }`. Проблема `{ key, type, sev: error | warn, ids (узлы), bld (объекты здания), p, forced }`;
`key` устойчив (тип и объекты) — по нему правка сравнивается с прежним состоянием. Результат считается один раз на дерево (`model.checks.run / problems / counts / marks`).

- **Правила.** `overlap` — ряды и места на полу друг с другом (допуск 5 мм, касание не пересечение); `overlapBld` — с колонной, стеной (отрезок с толщиной, SAT) и офисом здания; `outside` — место не целиком в контуре
  (только если есть план здания); `gap` — просвет между рядами уже минимума техники (зазор < 0,3 м считается «спиной к спине» и проходом не является); `aisle` — проход плана здания уже минимума;
  `heightCeil` / `heightSpr` — высота ряда `n.h` против `hCeil` / `hSpr` здания; `overload` — вес товара яруса / секции стоса (`quant.qty × product.weight` из снимка; вес неизвестен — максимум типа, проблемы нет) против `cap` параметров типа;
  `stockMoved` — ряд или место на полу с остатком стоит не в исходной зоне Odoo.
- **Блокирующие** — `overlap`, `overlapBld`, `outside` (`BLOCK`). `edit.change` строит кандидатное дерево и сравнивает проблемы с состоянием до правки: если появились новые блокирующие, правка откатывается (стек, `ui` и дерево
  как были, события `rebuild` нет), уведомление `{ kind: bad, key: n.chkBlock, force: true }`; вызов операции запоминается (`edit.exec` оборачивает каждую точку входа: `ops.*`, `bld.ops.*`, `moveSet`, `paste`, `types.*`).
  `model.checks.force()` повторяет её с `s.force`: новые блокирующие проблемы записываются в ту же правку (слой `edit.chk`, запись `f|<key>`), и проблема становится предупреждением `forced`. Старые проблемы новую правку не блокируют;
  склеиваемая правка (тот же `key`) сохраняет свои переопределения. Операции возвращают `false` при отклонении (`change`), у `bld.ops.add / grid / aisle` — `null`.
- **Слой `edit.chk [{ id, … }]`** (diff / apply / `reset` / миграции — как остальные слои; `reset` оставляет настройки, снимает `f|`): `t|WH`, `t|<id зоны>` — техника (`t`: id техники из `TECH`, `none`), `m|<id техники>` — минимальная ширина прохода (`w`),
  `f|<key>` — переопределение. Техника: ручная тележка 1,2 · штабелёр 2,4 · ричтрак 2,8 · узкопроходный 1,8 · погрузчик 3,6 м (значения по умолчанию в `TECH`, править можно: `ops.techMin`; выбор — `ops.tech(zone, { t })`, зона наследует склад).
  При группировке / разгруппировке записи `t|` и ключи `f|` переезжают на новые id (`remapChk`), как и переопределения ряда `edit.cfg` (I-01: `reparent` переносит `cfg` вместе с остальными слоями).
- **Места с товаром (F4).** `stockCodes(tree, узел)` — коды с остатком (`qty > 0`, включая базовый код яруса с ячейками). `ops.del` (одиночное и групповое) и любое удаление внутри правки (`removeNode`: уменьшение числа секций / ярусов) отклоняются
  без права переопределить (`n.delStock`); «Архівувати» пустого — обычное удаление (в v2 это статус `archived`). Перенос места с остатком в другую зону (группировка) даёт предупреждение `stockMoved` и уведомление.
- **Панель проблем** (`view/problems.js`, кнопка «Проблеми» с счётчиком в верхней панели): тип, объект, текст; фильтр по виду и типу; клик — `model.checks.goTo` (фокус на зону над объектом и выделение) либо режим «Будівля» для объекта здания;
  там же техника склада и минимальная ширина прохода; техника зоны — в панели зоны. Подсветка проблемных объектов: 2D — класс `prob` у ряда / места / прохода, 3D — отдельный материал `--prob` (`it.pr`). `model.checks.marks()` отдаёт `{ nodes, bld }`.
- Тесты: `test/checks.test.js` (каждое правило, «поставить всё равно», перезагрузка, I-01, замер на 10 000), шаг e2e «проверки: перетаскивание на соседний ряд отклонено…»; `createModel(…, { enforce: false })` и `fresh({}, { noStock: true })` в `test/helpers.js` —
  для старых тестов, которым нужно свободное положение или удаление мест с остатком.

## Разбор кодов, лоток «Не розміщено», авто-раскладка (W-12, D-07)

Режим «склад уже настроен»: любой склад Odoo превращается в модель. Ядро — `core/parse.js` и `core/autolayout.js` (без DOM, без состояния).

- **Правила разбора** (A3). Слой правок `edit.parse` — `null` (правила по умолчанию — прежние, зашитые раньше в `tree.js`: FUR / EB / FG / RCK / PLT и места на полу PAL / KIT / FRONTS / POST / OUT / UNLOAD; числа
  прототипа — 891 узел / 689 мест — не меняются) или `{ rules: [{ id, mask, re, tp, off }] }`. Правила идут по порядку, первое подошедшее решает; `tp` — тип места (пусто — по `{префікс}`, иначе FUR / ZONE), `off` — выключено.
  Меняет `model.ops.parse({ rules })` — как все правки: «Показати / Зберегти», undo, `canReset`, перезагрузка; набор по умолчанию снова хранится как `null`.
- **Маска.** Части `{ряд} {секція} {ярус} {префікс}` (и `{row} {bay} {level} {prefix}`): по умолчанию число; `{x:a}` — буквы, `{x:A-D}` / `{x:0-9}` — один символ диапазона, `{x:*}` и `*` — любой текст; остальное — буквы кода.
  Если в сегменте маски (между `- . _ / пробел`) одна часть уровня, именем узла становится весь сегмент (`R{ряд}` → «R12»). Режим регулярного выражения (`re`): группы `(?<row>) (?<bay>) (?<level>) (?<prefix>)`.
  Уровни по набору частей: ряд+секція+ярус — ряд / стелаж / ярус; секція+ярус — ряд берётся из пути Odoo (родитель, `rackParent`); ряд+ярус — ряд со стопками (`bayLeaf`); ни одной — место на полу. Код с «/» (`ZONE-B/12/4`) остаётся одним местом
  (`pathParts`). `codeSegs(code, rules?)` в `tree.js` — прежний вызов (без правил — по умолчанию). `tree.parseOf(code)` — разбор кода правилами склада.
- **Предпросмотр** `model.parse`: `rules() / defaults() / isDefault() / stats(rules?) / check(rule) / suggest(коды)`. `stats` → `{ total, parsed, bad (нераспознанные), tray (без зоны), hits (по правилам), errs }` и работает по черновым
  правилам без применения. `suggest` подбирает маску по образцам одной схемы: числа — всегда части, буквы — части, если различаются, первая буква в начале — `{префікс}`; части получают имена с конца (ярус, секція, ряд). Окно «Розбір кодів»
  (`view/parse.js`, кнопка в панели редактирования): сводка «З N місць розібрано M», правила (маска, регулярное выражение, тип, «Вимкнено», порядок, удаление), нераспознанные коды с отметкой «у лотку» / «місце на підлозі зони»,
  «Підібрати маску за зразками» (отмеченные коды, без отметок — первые три), «Показати / Зберегти».
- **Лоток «Не розміщено»** (A2). Место без зоны — не разобрано (или разобрано по уровням, но лежит прямо под корнем склада) и путь короче «склад / зона / место»; место-контейнер (внутри него лежат другие места) и место на полу по правилу — не бездомные.
  Такие места не создают узлов, а лежат в `tree.unplaced` (`{ code, id, name, path, tp, cs }`; `model.tray.list() / count()`). Кнопка «Не розміщено» (с счётчиком) в верхней панели видна, когда в лотке есть места; панель `view/tray.js` — список с выбором,
  «Розмістити в…» (зона) и перетаскивание места на зону или ряд в 2D (`plan2d.js`: цель — самый глубокий объект под курсором). `model.ops.place(коды, цель)`: цель — любой узел, берётся ближайшая зона выше; место на полу ставится в зону, разобранное по уровням получает свой ряд и стелаж
  (недостающие создаются). Правка — записи `add` с кодом и `from` (id в исходном пути); место перестаёт быть бездомным, `odoo_id` сохраняется; «Показати / Зберегти», undo; удаление размещённого возвращает место в лоток. Исходной зоны у таких мест нет — предупреждение `stockMoved` не появляется.
- **Авто-раскладка** (A4). После импорта дерево раскладывается как прежде (зоны по горизонтали, ряды вглубь). `ops.autoLayout(id)` для зоны или склада (форма «Авторозкладка» в панели): без плана здания снимает ручные положения детей (`edit.pos`);
  с планом здания (W-04) блоки (зоны, ряды, места на полу) укладываются полками в контур, не задевая колонны, стены и офисы (допуски проверок W-07) и не налегая друг на друга; зазор 4 / 2,5 м, а при нехватке места — 1,5 и 0,6 м. Не помещается — раскладка не меняется, уведомление `n.autoNoFit`.
  Внутренняя раскладка вложенных зон не пересчитывается. Новая правка проходит проверки W-07, как любая другая.
- Тесты: `test/parse.test.js` (прежние числа, маски и ошибки, автоподбор по трём образцам, фикстура другой базы `test/fixture-other.js` — 200 кодов трёх схем: с подобранными правилами разобрано 194 из 200 = 97 %, лоток: размещение и undo, авто-раскладка в контур без пересечений), шаг e2e «розбір кодів…».

## Мастер «З нуля» (W-16, D-08, A5, A6)

Пустой склад Odoo → здание → зоны → ряды → адресация → проверки → план изменений. Новых механизмов нет: мастер собирает готовые части (здание W-04, каталог W-05, массовое
создание W-06, проверки W-07, адресация W-08, файл W-10, применение W-13). Ядро — `core/wizard.js` (без DOM), панель — `view/wizard.js`, модель — `model.wizard`.

- **Вход**: «Файл → Новий проєкт: з нуля…» (`openNewScratch`). В странице Odoo — выбор **существующего** склада базы (`openOdooPick({ single: true })`, `host.odoo.newScratch`; склад не
  создаётся, A6): проект с одним складом `baseRef = "odoo:<id>"` и состоянием мастера. Вне Odoo — склад-заготовка с кодом (`scratchProject`: источник `scratch`, пустой снимок формата Odoo
  `scratchBase` внутри склада; в `meta.odoo` фиктивная view-локация с id −1, чтобы план изменений мог показать, что будет создано). Проект записывается в хранилище, страница перезагружается,
  панель мастера открывается сама.
- **Состояние** — поле `warehouse.wizard` проекта (`null` — мастера нет): `{ v: 1, step, reached, form: { building, zones [{ key, name, x, y, w, d, id }], racks { <id зоны>: { tp, nr, nb, nl, gap, orient, tech, ids } },
  addr { <id зоны>: форма адресации }, addrDone } }`. Значения форм пишутся в проект при каждом изменении поля, id созданных узлов — при применении шага: можно закрыть панель (×), выйти и вернуться
  (кнопка «Майстер» в верхней панели, в том числе после перезагрузки). `model.wizard`: `state / active / start / patch(fn) / finish`, событие `{ type: "wizard" }`. «Завершити майстер» убирает поле: проект обычный.
- **Шаги** (`STEPS`): `building` — прямоугольник Ш × Г или многоугольник (`parsePoly`: пары x,y), высоты, сетка колонн (`buildingApply`: `bld.ops.create / shape / grid`; повтор заменяет контур и колонны мастера);
  `zones` — зоны (`ops.group`) с прямоугольником внутри контура от (0, 0) (`ops.move` + `ops.props`; `zoneIssues`: внутри контура и не друг на друге; `splitZones` — ровные полосы; `zonesApply`);
  `racks` — для каждой зоны тип каталога (стеллажные и стопки), рядов × секций × ярусов, техника зоны (`ops.tech`; проход между рядами по умолчанию — минимум техники), `racksFit` (влезает ли блок в зону и в контур),
  `racksApply` (прежние ряды мастера заменяются, тип добавляется в проект, `ops.mass`); `addr` — шаблон и направления по зоне (`ops.addr` с переопределением зоны; шаблон по умолчанию —
  `<код склада> {зона} {ряд} {секція} {ярус}`: штрихкод локации Odoo уникален в компании, и коды двух складов иначе совпали бы), предпросмотр `model.addr.preview`,
  `addrApply` (`ops.renum(зона, { only })` по зонам мастера: места Odoo не трогаются; конфликты кодов закрывают шаг); `checks` — список проблем, пока есть ошибки (`model.checks.counts().error`), дальше нельзя;
  `plan` — `planSummary` (что будет создано: места и контейнеры), «Застосувати в Odoo…» (окно «План змін», `plan.js`; только в странице Odoo с правом применения) и «Файл для імпорту…» (экспорт W-10).
- **Правки** — обычные: каждый шаг пишет правки слоя (несохранённые, видны в «Показати / Зберегти», отменяются Ctrl+Z); вперёд можно только из готового шага (`stepState`), назад всегда.
  Переход с шага «Перевірки» сохраняет слой (`model.save("WH")`), потому что план изменений строится по сохранённому.
- **Что пришлось поправить в ядре** (нужно для склада с кодом, не равным `WH`, и для адресации до создания): `tree.js` узнаёт применённые узлы слоя и по id `WH/…`, и по пути снимка с кодом склада (`WH1/…`);
  `plan.js: cleanApplied` после создания места сворачивает перенумерацию в код узла (штрихкод места в Odoo = его код), иначе узел слоя и место снимка дублировались.
- Проверка: `test/wizard.test.js` (заготовка, здание 60×30 + 2 зоны + 2 × 4 × 10 × 4 = 320 мест с уникальными кодами, план создания 410 операций, ошибок нет, выход и возврат, повтор «Застосувати», применение на фейковой
  базе Odoo и перечитывание снимка), e2e «мастер «З нуля» вне Odoo…» и «…в Odoo…» (`WH_E2E_ONLY=мастер npm run e2e` — только эти шаги).
