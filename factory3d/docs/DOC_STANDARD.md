# Стандарт документів модуля

Два файли на модуль у `docs/modules/<module>/`: `ARCHITECTURE.md` (технічне рішення й
архітектура за стандартом ToDo) і `SPEC.md` (специфікація для реалізації й тестування).
Мова — українська; технічні імена — англійською; без води: кожне речення — факт, рішення або
вимога. Нумеровані ідентифікатори обов'язкові, бо на них посилаються код, тести й інші модулі.

**Планка якості.** `SPEC.md` достатній, якщо розробник (Sonnet) напише модуль, не ставлячи
жодного запитання, а тестувальник (Opus) напише й прожене тести, не читаючи код розробника.
Перевірка: для кожного поля, ендпоінта, крона, правила — є тип, значення за замовчуванням,
поведінка в краях і відповідний AC; для кожного AC — спосіб перевірки (юніт-тест або ТК на
емуляторі). Невідоме не вигадується: позначається `ВІДКРИТЕ ПИТАННЯ Q-xx` з рекомендованою
відповіддю і тим, що робимо, поки відповіді немає.

## ARCHITECTURE.md — структура

```
# <module> — технічне рішення
Версія, дата, автор (агент), статус (чернетка / на погодженні / погоджено)

## Загальна інформація            — таблиця етапів ToDo: ТР, Архітектура, Розробка,
                                     Тестування, Інструкція; люд./год (з docs/оцінки) 
## 1. Опис процесу і функціональні вимоги
   1.1 Контекст: що є в макеті (посилання на файли plant/*.py, ключі odoo_demo.json,
       вкладки й картки переглядача — конкретні імена функцій/ключів/рядків)
   1.2 Ролі й сценарії використання (хто, що робить, у якому меню)
   1.3 Функціональні вимоги FR-01…FR-nn (одне речення кожна, перевірювана)
   1.4 Межі: що не входить
## 2. Технічна реалізація
   2.1 Місце в системі: залежності (manifest depends), що бере з td_factory3d /
       telemetry, що віддає іншим (контракти з docs/ARCHITECTURE.md §6, за ID)
   2.2 Архітектурна схема (ASCII або mermaid): компоненти, потоки даних, протоколи
   2.3 Нові й розширені об'єкти — огляд (таблиця: модель, призначення, хто пише/читає)
   2.4 Інтеграції: пристрої/зовнішні системи, протокол (P-xx), напрямок, частота,
       що робимо при недоступності
   2.5 Потік даних від пристрою до екрана: крок за кроком, із назвами полів
   2.6 Безпека: групи, стоп-крани, токени, що заборонено
   2.7 Продуктивність і обсяги: записів/добу, ротація, індекси
   2.8 Міграція з демо-бази (x_* поля, data-модуль) і деінсталяція
## 3. Налаштування системи        — таблиця ToDo: Об'єкт | Параметр | Значення (як заповнювати) | Коментар
                                     (ir.config_parameter, довідники, крони, групи)
## 4. Інструкція                   — для експлуатації: 3–6 коротких інструкцій (назва,
                                     для кого, кроки), як «Робота поза графіком» у td_genset
## 5. Ризики й відкриті питання    — Q-01…: питання, кому, рекомендована відповідь, що робимо тим часом
## 6. План сборки агентами         — W0 каркас + воркери W1…Wn: межі файлів, що кожен
                                     здає, порядок злиття; відповідає етапу 4 циклу
```

## SPEC.md — структура

```
# <module> — специфікація
Версія, дата; посилання на ARCHITECTURE.md; список контрактів (C-xx, P-xx), на які спирається

## 0. Дерево файлів модуля       — повний список файлів з призначенням (manifest, models/,
                                    views/, security/, data/, controllers/, static/, tests/,
                                    services/… для колектора/емулятора)
## 1. Маніфест                   — name, version 19.0.1.0.0, depends, data (порядок!), assets,
                                    post_init_hook/uninstall_hook, external_dependencies (python)
## 2. Моделі                     — на кожну модель M-xx:
      - _name/_inherit, _description, _order, _rec_name, домішки
      - таблиця полів: тех. ім'я | тип | параметри (string uk, required, default, index,
        compute/store/depends, related, selection values, ondelete, domain, help)
      - SQL-constraints, _check-методи з текстами помилок
      - методи: сигнатура, вхід/вихід, алгоритм (псевдокод або нумеровані кроки), винятки
      - для стандартних моделей: тільки додані поля/перевизначені методи, з super()
## 3. Представлення й меню       — на кожне V-xx: XML-id, тип (form/list/kanban/graph/pivot/
                                    gantt/search), модель, структура (поля по групах/вкладках,
                                    кнопки з методами, статусбар, декорації, attrs/invisible),
                                    меню (батько, sequence, групи), дії (ir.actions.*)
## 4. Права                      — ir.model.access.csv (усі рядки повністю), record rules
                                    (domain, групи), групи модуля (XML-id, implied)
## 5. Дані                       — data/*.xml і post_init_hook: що створюється, з якого
                                    джерела макета, ключі xml-id, ідемпотентність
## 6. Крони й фонові процеси     — назва, інтервал, метод, що робить за один прогін, ліміти
## 7. HTTP/JSON API              — на кожен API-xx: метод, маршрут, auth, тіло запиту (JSON-схема
                                    з прикладом), відповідь, коди помилок, ідемпотентність, ліміти
## 8. Сервісна частина (якщо є)  — колектор/емулятор: структура пакета, конфіг (env),
                                    стан-машини, протокольні карти (регістри/NodeId/об'єкти/топіки
                                    з типами, одиницями, масштабом), таймінги, логування
## 9. Алгоритми й правила        — R-xx: пороги, розподіл, OEE, баланс — формули з одиницями,
                                    приклади з числами з макета (вхід → очікуваний вихід)
## 10. Стани й переходи          — машини станів (документи, сигнали, рейси): стани, переходи,
                                    хто/що викликає, побічні ефекти
## 11. Обробка помилок           — недоступність пристрою, повтори, застарілі дані (stale),
                                    дублікати, часові пояси (Europe/Kyiv vs UTC)
## 12. Acceptance Criteria       — AC-01…: Given/When/Then, з тех. іменами; кожен AC має
                                    тип перевірки: UT (юніт-тест) / TC (стенд на емуляторі) / MAN
## 13. План тестування (для Opus)
      13.1 Юніт-тести: файл, клас, назва тесту, фікстури, що саме assert — на кожен AC типу UT
      13.2 Стендові сценарії ТК-01…: передумови (сценарій емулятора), кроки, очікуваний
           результат, де дивитися (меню/поле/3D)
      13.3 Тести безпеки: доступ без групи, токен, стоп-крани, ін'єкції в адреси/коди
      13.4 Тести продуктивності: обсяг, час відповіді API, ротація
      13.5 Чек-лист DEPLOY_TEST: установка на копію демо-бази, міграція, відкат
## 14. Definition of Done        — перелік, що має бути зеленим: тести, lint, neutralize.sql,
                                    CHANGELOG, інструкції, перегляд безпеки
## 15. Відкриті питання          — Q-xx (ті самі номери, що в ARCHITECTURE.md)
```

## Правила

- Імена полів/моделей/xml-id — остаточні, не «наприклад». Якщо автор вагається, він вирішує і
  фіксує рішення в розділі «Рішення автора» (A-xx) з обґрунтуванням; менеджер може скасувати.
- Усі числа з макета — з посиланням на джерело (`plant/energy.py:tariff`, ключ
  `energy.totals.peak_kw`, паспорт `equipment_specs.json[role=compressor]`).
- Протокольні карти (регістри, NodeId, об'єкти BACnet, топіки, JSON API) — таблицями з типом,
  одиницею, масштабом, напрямком (R/W) і джерелом (документ вендора або «ПРИПУЩЕННЯ»).
- Стандарти й документи вендорів — з назвою документа і, де можливо, URL; дата перегляду.
- Нічого «буде визначено пізніше»: або рішення, або Q-xx.
- Обсяг: стільки, скільки потрібно для планки якості; типовий SPEC великого модуля — 1 500–3 000
  рядків, малого — 500–900.
- Посилання між модулями — тільки на ідентифікатори (C-xx, P-xx, M-xx, API-xx, AC-xx) з
  назвою модуля: `td_telemetry M-02 td.signal`.

## Чек-лист перед здачею

1. Кожен FR має хоча б один AC; кожен AC — спосіб перевірки у §13.
2. Кожна модель із §2 є в §3 (представлення), §4 (права) і §0 (файл).
3. Усі зовнішні залежності Python перелічені в маніфесті й у §8 (сервіси) з версіями.
4. Усі стоп-крани й токени описані в §2.6 ARCHITECTURE і §4/§7 SPEC.
5. Міграція демо-даних описана покроково з очікуваними кількостями (скільки записів перенесено).
6. Таблиця «Налаштування системи» заповнена значеннями для тестового сервера.
7. Жодного `x_`-поля, жодного «TBD».
