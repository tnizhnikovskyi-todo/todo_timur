## 2. Технічна реалізація

### 2.1 Місце в системі й контракти

**Рішення про пакування (A-42).** GAP рекомендував новий модуль; рішення — **новий модуль `td_energy_control`** (LGPL-3, `application=False`), окремо міст 3D `td_energy_viewer3d` (`auto_install`).

| Критерій | Розширення `td_energy` | Новий `td_energy_control` (рішення) |
|---|---|---|
| Клас ризику | читальний застосунок отримує шлях запису в пристрої | запис ізольовано: немає модуля — немає шляху керування; `meta.control_available=false` (W1 C-32 уже так задумано) |
| Життєвий цикл | видалити «керування» без «Енергетики» неможливо | окреме встановлення/видалення; видалення модуля видаляє його дані як у будь-якого модуля Odoo (D-45, архівних таблиць немає) |
| Залежності | `td_energy` довелося б залежати від `td_bms` і (м'яко) `td_genset_factory3d` | лише `td_energy_control` залежить від `td_bms`; `td_energy` лишається легким |
| Запобіжники | прапори `write_enabled`/`automation_enabled` розмазані по застосунку | одне місце, нейтралізація, `neutralize.sql` модуля |
| Тести й регресія | 208 тестів `td_energy` (142 + W1) зачіпаються кожною зміною керування | окремий цикл; регресія `td_energy` — перевірка контрактів C-38/C-46 |
| Ліцензія/володіння | однакова (LGPL-3) | однакова; окрема тека документів |
| Вартість | менше файлів маніфесту | +маніфест, +ACL (малі) |
| 3D | `td_energy` не може залежати від `td_viewer3d` (JS-імпорт зламав би бандл) | окремий міст за зразком `td_constructor_viewer3d` |

Розділення на `td_energy_control` + `td_energy_automation` відхилено: спільні моделі (`action`, `scenario`) і єдиний потік підтвердження.

**Граф залежностей:**

```

                     ▲                │ (м'яко, importlib/ir.module.module)

```

`td_energy_control` — `depends`: `td_energy`, `td_telemetry`, `td_bms`. `td_energy_viewer3d` — `depends`: `td_energy`, `td_viewer3d`; `auto_install=True`.

### 2.5 Потік даних

**(а) Ручна команда (клас B, дві особи).** 1) `en1` на плитці «Увімкнути QS» → `prepare('qs_close')` → `td.energy.action` `prepared`, токен, перевірки Odoo (`ats_parallel_lock`, `qs_current_ok` … з `td.signal.last_value`). 2) Діалог показує «гаразд/не виконано/немає даних»; «Підтвердити (1/2)» → `confirm(token)` → стан `awaiting_second`, сповіщення `mail.activity` + шина. 3) `en2` → `confirm_second` → перерахунок перевірок → `td.command` на `energy_control/intent` з `payload` (`action_id`, `idem`, `kind`, `params`). 4) Збирач забирає команду (`GET /f3d/telemetry/commands`, ≤ `commands_poll_s`), `CommandLoop` викликає `plugin.call()`; плагін синхронно перевіряє схему/ресурс/жорсткі блокування за свіжими входами й повертає `accepted=true` → `td.command` `done`, дія `executing`. 5) `Executor`: `qs_cmd=2` → верифікація `qs_state=closed` ≤ 10 с (через `ctx.read_signal`) → `done`; API-25 `actions[]` (`done`, `result`) → `_td_close` → журнал, шина, `td_energy` `state` → Пульт оновлюється. 6) Відмова контролера (`qs_ack=2`) або блокування → `failed/blocked` з причиною. 7) «Скасувати» → `undo` → зворотна дія `qs_open` (клас B).

**(б) Автоматика.** `Engine` кожні 2 с: `Inputs` (з `LiveCache`) → сценарії в порядку `backup, peak, self, slots, chp, night, pfc` → запити ресурсів → арбітраж (ручне перекриття > сценарії) → `Actuator` (запис лише за зміни, повторний запис примусових режимів кожні `valid_s/3`) → `Reporter` (стан/події раз на 10 с). Odoo перетворює події на записи журналу `origin='auto'`, чипи сценаріїв — із чисел рушія за шаблонами (R-43 п.5). Конфіг `GET config` кожні 10 с з `If-None-Match`; зміни Odoo (`bump`) видно збирачу ≤ 10 с.

**(в) Шар 3D.** Переглядач запитує `/f3d/viewer/data` → провайдери (seq 100 `energy`, seq 101 `energy_layer`) → `energy.layer` (вузли зі станом `sld_state`, маркери тривог). Живі оновлення: канал `f3d_viewer` (події `td.energy`/сигнали) → `/f3d/viewer/delta` → `applyPatch` → `applyData` розширення → `repaintAll()` і перебудова маркерів (≤ 10 с). Клік по вузлу → `cardBlocks` → «Відкрити картку вузла» → `td_energy.node_card`. З Пульта «Відкрити в 3D» → `action_td_open_3d` → `f3d_viewer.action` (`layers`, `mode='td_energy'`, `code`).

### 2.6 Безпека

- **Групи:** без нових (E-06): `group_td_energy_manager` («Енергетик»), `group_td_energy_chief` («Головний енергетик»), `group_td_energy_user`, адміністратор. Клас A — «Енергетик»; клас B — «Головний енергетик» або друге підтвердження іншою особою (SPEC R-39, матриця 4.2).
- **Запобіжники (шість):** `td.telemetry.write_enabled` → `td.energy_control.write_enabled` → `td.source.write_enabled` → `td.signal.write_enabled` → `F3D_WRITE_ENABLED` збирача; для автоматики додатково `td.energy_control.automation_enabled`. Окремо — **`td.energy_control.remote_switching_enabled`** (D-46, Q-27): при `False` команди дистанційного перемикання (`qs_close`, `qs_open`, `chp_start`, `bess_discharge`, `genset_test`) відхиляються `UserError`; прапор іде збирачу в API-24 `flags`. За замовчуванням усі `False` (demo/стенд — `remote_switching_enabled=True`); `neutralize.sql`; `_td_enable_stand` — лише вручну.
- **Семантика блокувань.** Дві реалізації одного реєстру: Odoo (підказка в діалозі, `confirm` блокується) і збирач (**жорстке виконання**, перед першим і активуючим кроками). `hard+fail` блокує; `hard+unknown+fail_closed` блокує (немає даних = небезпечно); м'які — лише попередження; конфіг лише звужує межі коду. Золоті випадки (SPEC R-41 п.5) — спільний контракт обох реалізацій.
- **Токени й підтвердження.** Токен 24 байти, у БД — `sha256`; TTL 60 с; належить користувачу; `confirm` ідемпотентний (`FOR UPDATE`, `idem`); друге підтвердження — інша особа, TTL 600 с, без обходу адміністратором.
- **Тайм-аути:** токен 60 с; друге підтвердження 600 с; команда в черзі 120 с; `call()` ≤ 1 с (лише прийом; ядро 10 с); виконання ≤ 60 с; крок 8 с; верифікація 10/15/30 с; heartbeat 30 с; застосування конфігу 60 с; скасування 15 хв; сторожові таймери BESS 30 с (автоматика) і скидання 60 с.
- **Ідемпотентність (шарами):** токен/`idem` в Odoo; `idem` у `Store` збирача (повтор → збережений результат); рівневі кроки (повтор безпечний); `event_id` для подій; стани лише «вперед» (з винятком для `expired` за авторитетним звітом збирача).
- **Режими відмов:** 18 рядків SPEC R-53 (Odoo/збирач/контролер недоступні, місцевий режим, несвіжі входи, дубль/втрата результату, падіння під час примусового режиму, часткові кроки, верифікація, конфлікт ручного й авто, невалідний конфіг, розбіжність годинників, зміна запобіжника, відмова пристрою, частота записів, рестарт). Головний принцип: **при втраті керування пристрої повертаються в автоматичний режим сторожовими таймерами**; КГУ, QS і уставка повітря — фізичні стани без таймера (повертаються лише явною командою/скасуванням).
- **Заборонено:** керування системами безпеки (три рівні, R-60), запис у `td_genset` (лише адаптер), `x_`-поля, `safe_eval` над даними БД, секрети/вартість у конфігу збирача.

## 4. Інструкція

**4.1 Увімкнути/вимкнути сценарій (Енергетик → друга особа або Головний енергетик).** 1) «Енергетика → Керування». 2) На картці сценарію натисніть перемикач — відкриється діалог «Сценарій «…»: увімкнути?». 3) «Виконати» (головний енергетик) або «Підтвердити (1/2)» (енергетик). 4) У другого енергетика на екрані з'явиться банер «Очікує другого підтвердження» → «Підтвердити (2/2)» протягом 10 хв. 5) Чип змінюється з «Очікує застосування» на актуальний стан після відповіді збирача (≤ 15 с).

**4.2 Ручна команда з блокуваннями.** 1) Плитка → діалог із текстом і «Перевіркою блокувань». 2) «не виконано» (червоне) або «немає даних» для жорсткої перевірки — «Виконати» неактивне, прочитайте причину. 3) «Виконати» → стани «Надіслано → Виконується → Виконано/Не виконано». 4) Результат і виконавець — у «Журналі команд і перемикань».

**4.3 Змінити пріоритети скидання (Головний енергетик).** «Змінити порядок» → ↑/↓ → «Зберегти порядок» → підтвердження (клас B). Склад і параметри рядків — «Налаштування → Пріоритети скидання». Критичні навантаження додати не можна (допускається лише часткове або умовне зниження, SPEC M-30).

**4.4 Скасувати дію.** У журналі біля виконаної дії (до 15 хв) — «Скасувати дію»; для рекомендацій — «Скасувати» в зеленому банері на Пульті. Скасування — окрема дія з правами за її класом.

**4.5 «Збирач не на зв'язку» / «автоматику призупинено».** 1) Перевірте «Налаштування → Стан керування» (heartbeat, `engine_mode`, причина). 2) Контролер у місцевому режимі — переведіть перемикач у «Дистанційне». 3) Несвіжі дані — «Телеметрія → Колектори». 4) Пристрої самі повертаються в автоматичний режим (сторожові таймери); КГУ/QS перевірте вручну.

**4.6 Відкрити в 3D.** Пульт → «Відкрити в 3D» (шар «Електромережа: стан вузлів», маркери тривог) або вузол схеми/картка → «Показати в 3D» (підсвічування). У 3D клік по вузлу → «Відкрити картку вузла».

**4.7 Увімкнення керування (адміністратор).** 1) Лише після перегляду ризиків (R1). 2) `td.telemetry.write_enabled`, `td.energy_control.write_enabled`, джерела `MB-U73-SWB-CMD`/`ENERGY-CTL`, потрібні сигнали (за таблицею SPEC 5.6), для автоматики — `automation_enabled`; для дистанційного перемикання — `td.energy_control.remote_switching_enabled` (D-46). 3) Збирач: `F3D_WRITE_ENABLED=true`. 4) Починайте з одного сценарію (`pfc`) у години чергування.

Кожне завдання містить: (1) **мету й критерій готовності** — AC зі списку воркера зелені, регресійні команди зелені, `ruff` чистий; (2) **файли, які можна змінювати** — лише власні з таблиці 6.1; (3) **розділи й ID SPEC для читання** — порядок читання за номерами рядків із `grep -nE '^#{2,3} ' SPEC.md` (не читати документ цілком); (4) **команди тестів** з 6.1; (5) **заборони**: не змінювати `__manifest__.py`, кореневі `__init__.py`, чужі файли, `td_genset`, `td_telemetry` (окрім указаних у C-40 файлів збирача для C), не додавати `x_`-полів, `safe_eval`, нових груп; (6) **відповідь ≤ 15 рядків** без коду: змінені файли, тести (команда → підсумок), потрібні зміни в чужих файлах, ризики/питання.
