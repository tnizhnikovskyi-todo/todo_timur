## 1. Опис процесу і функціональні вимоги

### 1.1 Контекст

У макеті `Resources.dc.html` вкладка «Тепло» показує теплову потужність, температуру в цеху, рекуперацію AHU-1 і список «Куди йде тепло» (RV, AHU-1, ворота, офіс). Джерело даних — `td_bms` (`td.bms.heat.balance`, `td.bms.hvac.unit`: `heat_signal_id`, `indoor_c`, `filter_dp_pa`, `airflow`), яке в `td_energy_resources` не є залежністю (D-18). Ядро `td_energy_resources` лишає порожні гаки; міст `auto_install` (`td_energy_resources` + `td_bms`) наповнює їх незалежно від порядку встановлення модулів.

### 1.2 Ролі й сценарії використання

Ролі — як у ядрі (`group_td_energy_user` — перегляд, `…_manager` — «Налаштування → Енергоресурси → Оновити прив'язку ресурсів»). Сценарій: **S-B1** енергетик відкриває вкладку «Тепло»: 4 KPI (потужність, сьогодні, температура в цеху, рекуперація AHU-1), список «Куди йде тепло», нотатки «Що помітила система» з трьома детекторами моста.

### 1.3 Функціональні вимоги

| ID | Вимога |
|---|---|
| FR-B1 | Теплові точки й лічильники з `td.bms.heat.balance` і `td.bms.hvac.unit`, ідемпотентно, незалежно від порядку встановлення |
| FR-B2 | KPI «Температура в цеху», «Рекуперація AHU-1», список «Куди йде тепло», примітка `{capacity}` на графіку |
| FR-B3 | Детектори `preheat_early`, `ahu_recuperation`, `dock_gates` |

### 1.4 Межі

Не входить: керування опаленням і вентиляцією (`td_energy_control`, `heat_schedule_shift` у W2 не підтримується); калориметри окремо від BMS (Q-04); запис у BMS; зміна `td_bms`. Рекуперація — **оцінка** за тепловим балансом (D-36): датчика температури витяжки в BMS немає (Q-B1).

## 2. Технічна реалізація

### 2.1 Місце в системі

`depends`: `td_energy_resources`, `td_bms`; `auto_install=True`. **Рішення A-01:** два модулі замість одного — ядро тестується без BMS (AC-64), `hvac_unit_id` — справжній FK, менеджер може згорнути міст у ядро заміною `depends` (деталі — ARCH ядра §2.1). Контракт C-04: міст читає `td.bms.heat.balance` (сигнали подачі/зворота/тепла, `t_in_set`, `capacity_kw`, `air_wh_m3k`) і `td.bms.hvac.unit` (`heat_signal_id`, `indoor_c`, `filter_dp_pa`, `airflow`); `td_bms` не змінюється.

### 2.2 Архітектурна схема

```
 td_bms: heat.balance · hvac.unit ──read──▶ td_energy_resources_bms
       ├─ _td_bind_extra()  → td.energy.point (HEAT-BOILER, HEAT-CHP, RV-ALL, AHU-1, OFFICE[, DOCK]) + td.energy.meter (HM-*)
       ├─ _td_heat_kpis / _td_heat_list / _td_heat_chart_note → td.energy.res.dashboard (API-01, вкладка «Тепло»)
       ├─ _td_detect_preheat_early | _ahu_recuperation | _dock_gates → td.energy.opportunity.rule (cron_td_energy_opportunity)
       └─ _td_backfill_extra → td.energy.res.interval (R-B5)
```

### 2.3 Нові й розширені об'єкти

| Об'єкт | Призначення | Пише | Читає |
|---|---|---|---|
| `td.energy.point` (розш., M-B1) | `hvac_unit_id`, `_td_bind_extra` | гак моста, `post_init_hook`, V-11 | збирач інтервалів, список «Куди йде тепло» |
| `td.energy.res.dashboard` (розш., M-B2) | гаки тепла | — | OWL «Енергоресурси» |
| `td.energy.opportunity.rule` (3 правила, `data/opportunity_rules.xml`) | детектори моста | крон | екран, W4 |
| `td.energy.res.interval` (розш.) | `_td_backfill_extra` | backfill | usage, API |
| шаблон `ResKpis` (UI-B1) | підпис «оцінка» у KPI «Рекуперація» | — | клієнт |

### 2.4 Інтеграції

Лише ORM-читання `td_bms` і (необов'язково, `env.get`) `td_yard` для сигналу відкриття воріт `DOCK` (Q-08). Недоступність: немає BMS — гаки порожні; немає сигналу воріт — точка `DOCK` не створюється, правило `dock_gates` пропускається.

### 2.5 Потік даних

`td_bms` (сигнали `heat_kw`, `indoor_c`, `filter_dp_pa`) → `td.signal`/`td.reading` → `cron_td_energy_res_build` (лічильники `HM-*`: `flow_integrate`, `estimate`) → `td.energy.res.interval` → `get_resources('heat')` (KPI й список з хуків моста) → екран; уночі `cron_td_energy_opportunity` → детектори моста → `td.energy.opportunity`.

### 2.6 Безпека

Групи й cost-gating — як у ядрі; запису в пристрої немає; `td_bms` не змінюється; ключі вартості без `group_td_energy_cost` видаляються з відповіді (хуки повертають дані, фільтр — у ядрі M-08).

### 2.7 Продуктивність і обсяги

+5–6 лічильників тепла × 96 слотів/доба у складі 2 304 рядків/добу ядра; `HM-RV` — 25 сигналів в одному лічильнику (A-06); детектори моста — у бюджеті 60 с на `_cron_detect` (ТП-05).

### 2.8 Міграція й деінсталяція

`-u`/встановлення створює 5–6 теплових точок і 5–6 лічильників (ідемпотентно за `(resource, code)`). Видалення моста лишає їх (дані ядра), хуки перестають працювати; правила моста видаляються разом із модулем (`noupdate` XML). Якщо `td_bms` встановлено пізніше — міст автоматично встановлюється й створює точки; вручну — «Налаштування → Енергоресурси → Оновити прив'язку ресурсів» (V-11).

## 4. Інструкція

**4.1 Тепло й BMS (енергетик).** Встановіть `td_bms`: міст поставиться автоматично й створить теплові точки. Якщо BMS з'явилася пізніше — «Налаштування → Енергоресурси → Оновити прив'язку ресурсів». Вкладка «Тепло» — «Енергетика → Енергоресурси → Тепло»; «оцінка» біля рекуперації означає розрахунок за тепловим балансом, а не вимірювання.
