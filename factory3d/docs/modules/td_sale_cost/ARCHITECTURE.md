# td_sale_cost — технічне рішення (вау №25)

Міст `auto_install` між `sale_mrp` і набором Завод 3D: у замовленні продажу показує собівартість і маржу з реальних даних виробництва. Специфікація — [SPEC.md](SPEC.md).

## 1. Задача

Менеджер бачить маржу за планом (BOM × ціна), але не знає, скільки коштувало замовлення насправді: скільки відпрацювали верстати, спожили електрики й матеріалів.
Модуль збирає це з пов'язаних МО при відкритті картки: «Собівартість: факт N ₴ · маржа M %» і розбивка за статтями й за МО. Нічого не зберігається.

## 2. Рішення

| # | Рішення | Чому |
|---|---|---|
| D-1 | `depends: sale_mrp, td_factory3d`; `td_machine_connect`, `td_energy`, `td.cut.map` — через `in self.env` | Стандартні дані (журнал часу, `costs_hour`, `stock.move.value`) дають розрахунок без `td_*`; без енергії/верстатів лише статті з «немає даних». Жорстка залежність від них була б зайвою |
| D-2 | Нічого не зберігається; форма — `TransientModel` на клік; колонки списку — нескладені compute, сховані | «Живе» оновлення без кронів і інвалідації |
| D-3 | Один рушій `td.sale.cost.calc` на пакет замовлень | Кнопка, колонки й форма дають однакові числа; журнали читаються пакетом |
| D-4 | Чисті функції `tools/cost.py`; стаття без даних = `None`, не 0 | Юніт-тести порогів, прогресу, прогнозу; «0 ₴» не маскує відсутність даних |
| D-5 | Факт порівнюється з «планом на зараз» | Для МО в роботі повний план дає хибну економію й маржу; прогноз = факт + решта плану |
| D-6 | Відхід розкроя — довідка, брак (`stock.scrap`) — додається | Листи вже списані в матеріалах |
| D-7 | ПідМО входять у замовлення, напівфабрикат виключено з матеріалів батька | Без подвійного рахунку |
| D-8 | «Зараз» — демо-годинник `td.viewer.demo_clock` (як R-30 td_machine_connect) | Відкриті записи журналу демо-бази інакше дають сотні годин |

## 3. Потік даних

`sale.order` → `_td_trees` (МО: `sale_mrp` ∪ `origin`, дерево підМО) → `_td_mos_data` (операції, `time_ids`, `td.machine.state.log`, `td.energy.alloc`, `move_raw_ids`, `stock.scrap`, `td.cut.map`) → `_td_order` (ціна, статті, прогрес, маржі) → поля `sale.order` або `td.sale.cost`.

## 4. Безпека, продуктивність, ризики

Лише `sales_team.group_sale_manager` і `td_factory3d.group_td_manager`; розрахунок від `sudo()`. ≈ 20–30 запитів на кнопку незалежно від числа МО (пакетні `_read_group`/`search`); кешу немає свідомо.
Ризики: маржа відносно ціни всього замовлення, а собівартість лише МО; МО без `origin` замовлення не знаходяться; у демо-наборі немає даних для матеріалів і енергії (SPEC §5).
