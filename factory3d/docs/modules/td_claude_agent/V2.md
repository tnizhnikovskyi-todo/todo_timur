# td_claude_agent v2: AI-команда, ролі й скіли в Odoo

Мета: команда агентів-ролей працює в проєктах Odoo за стадіями (PM/AN/DV), інструкції ролей і скіли
зберігаються в Odoo (видно й редагується в інтерфейсі), Методолог і Менеджер пропонують покращення скілів,
власник затверджує. Routine — тонка: вся «поведінка» береться з Odoo під час запуску.

## 1. Ролі — `td.claude.role`
Поля: name, code (manager/architect/coder/tester/methodologist), sequence, instructions (Text, Markdown —
базовий промпт ролі), model_hint (opus/sonnet — підказка, яку Routine використати), active.
Seed 5 ролей (data, noupdate): Менеджер (PM), Архітектор (AN), Кодер (DV), Тестувальник, Методолог.
Тексти — стисло на основі `factory3d/build/MANAGER.md`, `MODULE_LEAD.md`, `QA.md`, `TEAM.md`.

## 2. Агент = (власник, роль)
`td.claude.agent`: + role_id (required для нових; міграція: наявний агент → роль «Менеджер»).
Унікальність (owner_id, role_id) замість owner_id. Користувач «Claude · <Роль>» (для 2-го власника —
«Claude · <Роль> · <Ім'я>»). Створення: майстер «Створити команду Claude» — вибір ролей → агенти + ключі.
Fire URL/токен — на агенті (кілька агентів можуть мати ту саму Routine).

## 3. Скіли — `td.claude.skill` (mail.thread)
Поля: name, code (slug, унікальний), scope (corporate/role), role_ids (m2m, для scope=role), description
(коли застосовувати — 1–2 речення, як frontmatter SKILL.md), body (Text, Markdown — інструкція), version
(int), state (active/archived), proposal_body, proposal_note, proposal_author_id, proposal_date.
`td.claude.skill.version`: skill_id, version, body, note, author_id, date — історія затверджених версій.
UI: меню Claude → Скіли (список/канбан з фільтрами Корпоративні / за роллю / Є пропозиція), форма:
опис, тіло (моноширинний текст), вкладки «Пропозиція» (diff-ish: поточне vs запропоноване) та «Історія».
Кнопки власника: «Затвердити пропозицію» (version+1, запис в історію, body=proposal), «Відхилити».
Seed (noupdate): корпоративні — `odoo19-standards` (td_*, Odoo 19, з CLAUDE.md і docs/ARCHITECTURE.md §5),
`chatter-etiquette` (як відповідати, td_claude_post, коротко, мова керівника), `safety-gates` (що лише
з «так» власника); рольові — по одному на роль (декомпозиція й планування ліміту / SPEC за стандартами /
реалізація-тести-гілка-PR / тестування за AC / ретро і покращення скілів).

## 4. API для агентів (RPC, публічні методи, лише користувачі-агенти)
- `td.claude.agent.td_claude_brief()` → {role:{code,name,instructions}, skills:[{code,name,description,version}]}
  (корпоративні + ролі агента; без тіл — економія контексту).
- `td.claude.skill.td_claude_read(codes)` → [{code, version, body}].
- `td.claude.skill.td_claude_propose(code, body, note)` → пропозиція (лише ролі methodologist, manager);
  створення нового скіла як пропозиції — `td_claude_propose_new(code, name, scope, role_codes, description, body, note)`.
- Наявні: `td_claude_post`, `td_claude_append_context`.

## 5. Запуски
- Стадія → роль: `project.task.type.td_claude_role_id` (seed за мітками: (PM)→Менеджер, (AN)→Архітектор,
  «Тест (AN)»→Тестувальник, (DV)→Кодер; редагується). Зміна стадії задачі → запит kind="stage" агенту
  цієї ролі того ж власника.
- Хто може запускати: власник АБО агент того ж власника (передача роботи). Агент ніколи не запускає себе.
- Запобіжники: лічильник запусків на задачу за добу `td_claude_hops_today` (ліміт `td.claude.max_hops_per_day`,
  за замовчуванням 6; перевищення → нотатка в чатер і без запуску); прапорець задачі «Пауза Claude».
- Склеювання: той самий агент + запис, запит < 60 с тому в стані pending/sent → новий не відправляти
  (кінд assign/stage); згадки власника відправляються завжди.
- Payload: + role {code,name}, + hops_today.

## 6. Routine (одна на модель)
Тонкий prompt: «прочитай brief → прочитай потрібні скіли → виконуй за інструкцією ролі». Дві Routine на Pro:
Opus (Менеджер, Архітектор, Методолог) і Sonnet (Кодер, Тестувальник). Тексти — `routine_v2_*.txt`.
