# AI-команда в Odoo: схема

Odoo — єдиний канал взаємодії: власник (людина) ↔ агенти і агент ↔ агент. Задача Odoo = одиниця роботи,
чатер задачі = її розмова, стадія = стан процесу. Один запис Odoo = одна сесія Claude на роль.

## Ролі

| Роль (користувач Odoo) | Що робить | Вхід → вихід |
|---|---|---|
| **Менеджер** | декомпозиція цілей на задачі, опис, пріоритети, призначення ролей, планування ліміту (як ресурсів команди), управлінська оптимізація, приймання | ціль власника → задачі з критеріями; результат → «Готово до приймання» власником |
| **Архітектор** | SPEC/ARCHITECTURE за стандартами компанії (`td_*`) і Odoo 19, план воркерів | задача «Специфікація» → документ у репо + посилання в задачі |
| **Кодер** (одна роль, кілька паралельних сесій — по одній на задачу) | реалізація за SPEC, тести, гілка, PR | задача «В роботі» → гілка/PR + звіт тестів |
| **Тестувальник** | прогін тестів, приймання за AC, ручна перевірка на стенді | «Тестування» → «Доопрацювання» (з дефектами) або «Прийнято QA» |
| **Методолог** | покращення самої схеми: скіли, плагіни, CLAUDE.md, промпти ролей, метрики | ретро по закритих задачах → пропозиції; зміни правил — лише після згоди власника |

Одна роль = один користувач Odoo (5 ліцензій), а не один користувач на кожну сесію.

## Процес (стадії проєкту «AI-розробка»)

```
Беклог → Специфікація (Архітектор) → Затвердження SPEC (власник) → Готово до роботи
→ В роботі (Кодер) → Тестування (Тестувальник) ⇄ Доопрацювання (Кодер)
→ Прийнято QA → Приймання (Менеджер → власник) → Розгортання (власник дає «так») → Готово
```

Перехід стадії або призначення ролі = запуск агента цієї ролі для цієї задачі. Рішення, що змінюють
спільне (злиття в гілку розгортання, прод, правила команди), — тільки після «так» власника в чатері.

## Середовище виконання

Агенти — хмарні сесії Claude Code (ізольовані контейнери з репозиторієм), а не процес на сервері Odoo:
повний функціонал (код, тести, git, конектори, скіли) без доступу агентів до самого сервера.
Запуск — Routine ролі через API-тригер з модуля `td_claude_agent`; диспетчер Routine веде зв'язок
«задача+роль → сесія» (`td.claude.session`). Все — на підписці власника (власник — єдина людина в контурі).

## Ліміти (планує Менеджер)

- Паралельно не більше 3 активних сесій-виконавців (правило CLAUDE.md), черга за пріоритетом.
- Routine: 30 запусків/год на Routine, 100/год на акаунт; ліміт підписки спільний для всіх ролей.
- На задачі: оцінка (кількість сесій/годин роботи агента) і факт; перевищення → Менеджер ескалює власнику.
- Запобіжники агент↔агент: агент не запускає сам себе; ліміт «хопів» на задачу за добу; стоп-слово власника.

## Що змінити в модулі `td_claude_agent` (v2)

1. Ролі: агент = роль (Менеджер, Архітектор, …) зі своєю Routine і промптом; власник один.
2. Тригери не лише від власника, а й від агентів-колег (згадка, призначення, зміна стадії) з запобіжниками.
3. Зв'язок сесії: (задача, роль) → сесія.
4. Поля задачі: роль-виконавець, оцінка/факт ліміту, гілка/PR, лічильник хопів.
5. Шаблон проєкту «AI-розробка» зі стадіями вище; правила «стадія → роль».

## Етапи

0. Встановити `td_claude_agent` на timur-o19demo; один агент наскрізно через Routine (затримка, конектор
   у створених сесіях, продовження сесії).
1. Модуль v2 + шаблон проєкту + промпти ролей (на основі `factory3d/build/MANAGER.md`, `MODULE_LEAD.md`, `QA.md`).
2. Пілот на одній реальній задачі factory3d (дефект або невелика доробка); метрики: час, хопи, витрата ліміту.
3. Методолог: ретро пілоту → зміни скілів/промптів → наступні задачі.
