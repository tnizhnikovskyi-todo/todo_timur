## 1. Опис процесу і функціональні вимоги

### 1.1 Контекст: що є в макеті

Прототип конструктора (артефакт, `build/constructor/PROTOTYPE.md`) показано замовнику; його відповіді — CD-01…CD-24. Усі моделі й поля Odoo ідуть із прототипу без перейменувань.

| Що в прототипі / макеті | Де | Що стає в Odoo |
|---|---|---|
| Площадка: будівля, сітка колон, активна версія | `site` у `db` артефакта | `td.site` (M-01); габарит будівлі демо 150×72×9 (`plant/layout.py:W,D,H`, CB-12) |
| Шар: відмітка, крок сітки, проходи, пожежні проходи, мережі, права за ролями, колір | `layers` | `td.layer` (M-02), `edit_group_ids` → `res.groups`, JSON-поля `aisles`, `fire_paths`, `utilities`, `bounds` |
| Місце за шаблоном + ручні правки комірок; коди `FG-R1-B01-L4` | `slots`, `plant/layout.py`, `odoo_demo.json → locations` (689 локацій) | `td.slot` (M-03): `template`, `params`, `overrides`; комірки обчислюються (R-01), публікуються в `stock.location` з `td_code`, `td_loc_kind`, `td_capacity` (CB-05) |
| Каталог: категорія → тип → варіанти (габарити, сервіс, підключення, модель) | `catalog`, `plant/equipment_specs.json` (93 паспорти), `passports` | `td.equipment.variant` (M-04) на `td.equipment.passport` (CB-07), категорія `td_category` (M-12) |
| Розміщення: варіант на шарі з x, y, поворотом, кодом | `placements`, `plant/layout.py:MACHINES` | `td.placement` (M-05) → `maintenance.equipment` (+ `mrp.workcenter`) за `td_code` |
| Перевірки: 7 видів, `warn`/`block` | `settings.checks` | `td.check.config` (M-06), клієнт наживо + сервер при публікації (DEC-10) |
| Чернетка → публікація, історія версій | `versions` | `td.layout.version` (M-07), майстер публікації (M-08…M-10) |
| Завантаження моделей GLB/OBJ/STL/FBX/3MF/DAE, STEP/IGES/IFC «буде на сервері» | IndexedDB, діалог варіанта | вкладення на варіанті, перетворення в браузері (DEC-03), `pending_conversion` (DEC-04) |
| Підкладка DXF, DWG «на сервері» | діалог «Підкладка DXF» | вкладення шару; DXF — у браузері, DWG — фаза 2 (DEC-18) |
| Приклад «Меблеве підприємство» і «Порожня площадка» | вбудований JSON; кнопка | `data/seed_site.json` + `post_init_hook` (DEC-13); `site/create` (R-23) |
| 3D-бандл переглядача | `td_viewer3d/static/lib/three/three-bundle.esm.js` (three r160: GLTFLoader, OrbitControls, CSS2D) | перевикористовується; бракуючі завантажувачі вендоряться (DEC-06) |

### 1.2 Ролі й сценарії використання

| Роль | Група | Що робить (меню «Завод 3D → Конструктор» і «Планування») |
|---|---|---|
| Користувач | `td_factory3d.group_td_user` | відкриває конструктор у режимі перегляду, бачить усі шари й версії |
| Технолог | `group_td_constructor_technologist` | ставить обладнання на шарах, де він у `edit_group_ids`; веде каталог варіантів і 3D-моделі |
| Комірник | `group_td_constructor_storekeeper` | малює стелажі й комірки (шаблони) на «своїх» шарах |
| Інженер | `group_td_constructor_engineer` | правит мережі: проходи, пожежні проходи, щити й магістралі, підкладку |
| Менеджер | `group_td_constructor_manager` | усе: площадки, шари, права шарів, перевірки, публікація, версії |
| Адміністратор | `td_factory3d.group_td_admin` | параметри, стоп-кран публікації |

Сценарії: S1 нова площадка (порожня або за зразком) → S2 налаштувати шари → S3 розставити стелаж шаблоном → S4 додати варіант із 3D-моделлю → S5 перетягнути обладнання з живими перевірками → S6 опублікувати (майстер, перелік, підтвердження) → S7 повернути чернетку до версії.

### 1.4 Межі: що не входить

- **Фаза 2:** малювання переглядачем розкладки з опублікованих шарів замість запечених GLB (Q-08); DWG-підкладка (серверне перетворення, Q-06); серверні бібліотеки STEP/IFC (Q-02); BIM-обмін.
- Шаблон «зона-контур» лише малюється; публікація в `td.zone` — Q-03. Ворота/док як шаблон місця (CD-08 — не в першій черзі).
- Збереження залишків, переміщення товару, виробничі замовлення — стандартні модулі; конструктор лише створює довідкові записи (локації, обладнання, робочі центри).
- Редагування `maintenance.equipment`/`stock.location` поза публікацією не блокується; конструктор їх не «заморожує».
- **Не зроблено у хвилях 0–2 (рішення замовника чекає):** `.whproj.json` і одноразове перенесення проєктів «Конструктора складу» з відключенням `wh_constructor` (F11-05, CD-31 Q3 — потрібні зразки файлів, Q-16); експорт «Місця в Excel» (F15-03, Q-17); повне покриття англійської викликами `t()` (Q-15); оновлення моста `td_constructor_viewer3d` під нові генератори й будівлю (Q-22).
- **Поза рамками CD-30:** автономний сервер і коннектор до іншої облікової системи (з'явиться клієнт — окреме рішення); конвертер STEP/IGES/IFC і сховище сирих показань — поза Odoo лише пізніше (CD-29).

### 2.2a Ядро + адаптер (CD-29)

CD-29: Odoo — система обліку (дані, права, публікація, API); 3D-ядро редактора — JS + Three.js **без залежностей від Odoo**; дані йдуть через адаптер; **прототип і модуль — один код**. Схема збудованого:

```
┌──────────────────── ядро factory3d/core/constructor/*  (JS, Three.js; без @web/@odoo/fetch) ───────────────────┐

│ adapter.js — контракт: load/save/check/publish/uploadModel/… + capabilities {publish, check, library, storage,  │
│   stock, putaway, odoo_import, rollback, render, files, variants, comments, locks}                             │
└──────────────▲──────────────────────────────────────────────────────────────────▲──────────────────────────────┘
               │ OdooAdapter (adapter_odoo.js)                                   │ ArtifactAdapter (artifact/*)
┌──────────────┴───────────────────────────────┐              ┌──────────────────┴───────────────────────────────┐
│ модуль td_constructor                        │              │ прототип-артефакт (одна HTML-сторінка)            │
│ constructor_action.js (Owl) + odoo_host.js:  │              │ proto/src/main.js + page.css; сховище `db` →      │
│   three r160 з td_viewer3d, умовні моделі,   │              │   localStorage → пам'ять, IndexedDB (модель);      │

│   ORM → stock.* · maintenance · mrp          │              │   `check`                                          │
└──────────────────────────────────────────────┘              └────────────────────────────────────────────────────┘
   node tools/build_core.mjs module → static/lib/f3d-core/constructor.esm.js (коміт)     build_core.mjs proto + proto/build.py → index.html
```

- **Один код.** Усе, що можна порахувати без Odoo, написано один раз у ядрі: скасування/повтор, виділення, копіювання, пресети, розбір кодів, лоток, авторозкладка, геометрія будівлі, класи теплових карт, розкладка й ZPL етикеток, специфікація стелажів, порівняння варіантів. **Дзеркала Python↔JS** (золоті фікстури) лише там, де потрібні запис в Odoo чи блокування публікації:
  генерація комірок і адресація, перевірки, «чи вміститься», Code128, таблиці, специфікація, правила розбору (SPEC §9.1).
- **Адаптер** — єдине місце, що знає про Odoo (`adapter_odoo.js`, API `/f3d/constructor/*`) або про базу артефакта (`artifact/adapter_artifact.js`). Ядро говорить нейтральними термінами («місце зберігання», «категорія зберігання», «правило розміщення», «правило поповнення»); `stock.*` — лише в адаптері Odoo (CD-30: інша облікова система пізніше — інший адаптер).
- **Capabilities.** Адаптер оголошує, що вміє; ядро ховає решту через `can(name)`. В артефакті немає серверних можливостей: PDF — «на сервері», «Куди покладе» — «оцінка», блокування зон не емулюються, коментарі без виконавців (SPEC §8.4).
- **Збірка.** `tools/build_core.mjs module` (esbuild, ESM, без three.js) → `static/lib/f3d-core/constructor.esm.js`; файл **комітиться** (на сервері не збирається), хеш вмісту — `CORE_BUILD` у `core_loader.js` скидає кеш браузера. `tools/build_core.mjs proto` → IIFE, який `proto/build.py` вставляє в один HTML (бюджет 900 КБ, після S6 — 833 КБ мінімізований).
  Модуль завантажує ядро **динамічним `import()`**, у bundle Odoo воно не входить (як `f3d-loaders`, DEC-06). Хост модуля передає ядру three.js (r160 з `td_viewer3d`), умовні моделі й завантажувачі (`static/src/model/*`, W3), форми запису Odoo; хост прототипа — власні (three r147, діалоги артефакта).
- **Тести.** `node tools/test_core.mjs` (Node, без Odoo: відносні імпорти, контракт адаптера, збірка свіжа, слайси `test_core_s1…s6.mjs`), HOOT у модулі (`static/tests/editor/s*.test.js`), Playwright на прототипі (`build/constructor/proto/test_s*.js`), `TestCoreNode` запускає Node-набір з Odoo-тестів (SPEC §13.6).

### 2.4 Інтеграції

Зовнішніх систем і протоколів P-xx немає. Опційно на сервері: `cascadio` (STEP → GLB), `IfcConvert` (IfcOpenShell, IFC → GLB); їх відсутність не помилка — файл лишається `pending_conversion`, картка варіанта це пише (R-20). Доступний набір визначається при завантаженні файла, перевірка — `services.convert.CONVERTERS`.

**Доповнення (злиття, v0.2).** Інтеграції лишаються всередині Odoo; нових протоколів P-xx немає. Нове: читання стандартних моделей під `sudo` у межах відповіді після перевірки групи («перегляд») — залишки/рухи/правила (API-13/14, R-33), стратегія розміщення (API-15), стрічка локацій складу (API-16, R-35); прямий запис у Odoo — лише категорії зберігання (API-12, менеджер, `confirm: true`, CD-20);
усе інше потрапляє в Odoo **лише публікацією** (план R-31, журнал R-32). Файли (XLSX/PDF/PNG) рендерить сервер з даних ядра (API-19, `reportlab`, `openpyxl`, `xlsxwriter`, `qrcode` з залежностей Odoo); у браузері локально — ZPL, CSV, PNG, SVG. Недоступність стрічки Odoo після публікації публікацію не скасовує (база порівняння створюється при наступному «Оновити з Odoo»).

### 2.5 Потік даних: від миші до запису Odoo

1. Відкриття: API-03 `load` → стан (шари, місця, розміщення, каталог, права, `etag`) → сцена three.js.
2. Перетягування/форма: клієнт перераховує R-02…R-10 (живі зауваження); при `block` об'єкт повертається; інакше `OdooStore.queue(op)`.
3. Автозбереження (`autosave_ms`): API-04 `save` — одна транзакція, права користувача (ir.rule + R-11), `etag`-конфлікти, `site._f3d_touch` (R-21).
4. Модель варіанта: файли → браузер (R-15) → GLB → API-09: сервер перераховує метадані (R-19), пише вкладення, `model_status`; STEP/IFC → `_f3d_convert_model()` (R-20).
5. «Опублікувати»: `flush` → API-06 → майстер: `build_plan` (R-12: перевірки, збіг за кодом, create/update/archive) → менеджер відмічає архівації → `action_confirm` → `apply_plan` у одній транзакції під `sudo()` → версія зі знімком (R-14).
6. Результат: `stock.location` (`td_code`, `barcode`, `td_loc_kind`, `td_capacity`, `td_site_id`), `maintenance.equipment` (`td_code`, `td_passport_id`, `td_zone_id`), `mrp.workcenter`; viewer бачить їх штатно через `td_code` (CB-01).

### 2.5a Додаткові потоки (злиття)

1. **Відкриття:** `core_loader.js` → `import(f3d-core)` → `OdooAdapter.load` (API-03: + `types`, `presets`, `rules`, `site.addr/warehouse/…`, `layers[].items`) → `mountEditor`; можливості з `capabilities` ховають зайве.
2. **Адресація:** панель «Адресація» → попередній перегляд кодів (ядро, R-25) → `/site/addr` (`renumber='new'|'all'`) → закріплення опублікованих → звичайна правка чернетки.
3. **Застосування в Odoo:** «Опублікувати» → `flush` → API-06 → майстер із вкладками за видами (R-31) → `action_confirm` (область, виключення, нагадування про копію БД) → одна транзакція під `sudo` після перевірки менеджера й `publish_enabled` → версія + `td.publish.op` (R-32) → оновлення бази порівняння (R-35).
4. **Робота зі складом:** API-13 пачками → `S.stock` → теплові карти й картка місця; API-14 → «Де лежить»; API-19 `labels_pdf` → файл; ZPL будує ядро.
5. **Спільна робота:** варіанти (API-21) — перемикання знімками; коментарі (API-22) оновлюються раз на 15 с; оренда зони (API-23) береться при виборі об'єкта й продовжується раз на хвилину; історія й контрольні точки (API-24).

### 2.6 Безпека

- **Групи:** 4 ролі (§1.2) у привілеї `privilege_td_constructor`; менеджер імпліцитно містить три ролі й `td_factory3d.group_td_manager`; `group_td_admin` → менеджер.
- **Права на шар (CD-02):** `ir.model.access` дає ролям право на `slot/placement`, `ir.rule` звужує до шарів, де група користувача в `layer.edit_group_ids` (порожньо → лише менеджер); другий бар'єр — `_f3d_check_edit` із текстом «Шар «X» редагує …» (R-11). Структура шару, групи, перевірки, публікація, версії — лише менеджер.
- **Публікація:** під `sudo()`, але лише після перевірки групи менеджера, стоп-крана `publish_enabled` (DEC-17), `draft_rev` майстра, блокування рядка площадки `NOWAIT`; ніколи не `unlink`; архівація — лише позначені рядки без `blocked`.
- **Файли:** розмір ≤ `max_model_mb`, перелік розширень, `name` вкладення очищується, перевірка магічних байт GLB, `meta` клієнта не довіряється; API-09 — `csrf_token`; API-10 — доступ за читанням варіанта.
- **Ін'єкції:** коди й префікси — регулярка CB-01; JSON-поля — схеми R-22 і ліміти розміру; ORM лише параметризовані запити (єдиний сирий SQL — `_f3d_touch`, параметри `%s`).
- **Мультикомпанія:** `company_id` дочірніх сутностей `related` stored + глобальні правила (DEC-12).
- Токенів і зовнішніх ендпоінтів немає; кіоску немає; нових стоп-кранів, окрім `publish_enabled`, немає.

**Доповнення (злиття, v0.2).**
- **Нові сутності** (`td.slot.type`, `td.slot.preset`, правила, варіанти, коментарі, оренди) мають власні права (SPEC §4.5): читає «перегляд», пишуть проєктувальники, видаляє менеджер (типи, пресети), керує варіантами лише менеджер; журнал `td.publish.op` — лише читання (пише сервіс публікації).
- **Публікація й відкат:** `sudo` лише після перевірки групи менеджера й `publish_enabled` (відкат — лише після перевірки менеджера; стоп-кран його не блокує); `confirm: true` обов'язковий для API-07, API-12 save/delete, API-18 rollback; відкат атомарний (savepoint) і нічого не видаляє (створене → `active=False`).
- **Оренда зон (CD-31 Q6):** необов'язкова поверх `etag`; чужа діюча оренда відхиляє правку (`AccessError`) у `td.draft.mixin`; `su` і контекст `f3d_no_lock_check` її пропускають; менеджер оренду чужого не обходить, а знімає записом; `zone_uid` ≤ 32 символи.
- **Коментарі:** додає будь-хто з доступом, змінює/вирішує/видаляє автор або «Проєктування»; виконавець — лише користувач із доступом до конструктора; завдання `mail.activity` створює сервіс під `sudo` після перевірки.
- **Вхідні дані:** `addr.tpl` — лише `[A-Za-z0-9._/#:-]` ≤ 64; `parse_rules` — ≤ 30 правил, ≤ 5000 у лотку, regex перевіряється; таблиці — ≤ 25 МБ, ≤ 200 000 рядків; payload рендерерів — ліміти (етикетки ≤ `labels_max`, PNG ≤ 12 аркушів, план ≤ 200 000 примітивів); JSON-поля — R-22 (≤ 256 КБ, вкладеність ≤ 8, невідомі ключі відкидаються).
- **Без токенів і зовнішніх ендпоінтів:** сторінка «Інструкція» (`/f3d/constructor/help`) — `auth="user"`; ядро й прототип не звертаються до CDN (у модулі XLSX/PDF — на сервері, AC-05).

### 2.7 Продуктивність і обсяги

Seed: ~600–1 000 комірок, ~250 розміщень, ~50 варіантів — API-03 ≈ 250 КБ. Комірки не зберігаються (обчислюються), тож `slot` — десятки рядків. Знімок версії ≈ 150 КБ (вкладення, не рядок БД); версій — одиниці на тиждень. Редактор: InstancedMesh, рендер на вимогу. Публікація 360 комірок — пачкові `create` (≤ 20 с). Індекси: `(site_id)` на всіх дочірніх, UNIQUE `(site_id, code_prefix)`, `(site_id, code)`, `(site_id, uid)`; `td_site_id` — індекс. Ротація не потрібна; знімки не видаляються.

**Доповнення (злиття, v0.2).** Склад 5–50 тис. комірок: комірки не зберігаються (обчислюються); `stock/state` рахує агрегати за кодами й ріже відповідь пачками (≤ 2000 локацій, ≤ 2 МБ), стрічка локацій — пачками до 20 000 (стеля 50 000); у браузері — `InstancedMesh` і рендер на вимогу; мета прототипа лишається ~600–2000 комірок. Один документ `db` артефакта на варіант (бюджет 256 КіБ). Версії: публікації не видаляються, контрольні точки — не більше `versions_keep` (50);
знімки варіантів — вкладення (`ir.attachment`). Розмір ядра ≈ 1 МБ (`constructor.esm.js`, вантажиться раз із кешем за `CORE_BUILD`); прототип після S6 — 833 КБ (< 900 КБ). **Навантажувальний тест на 5–50 тис. комірок не виконано** (Q-21).

### 2.8 Міграція, seed і деінсталяція

`x_*`-полів немає. `post_init_hook` (SPEC §5.2): параметри → категорії паспортів → seed площадки → зв'язування за кодами → базова версія v1 → звіт. Seed беруть з макета (`model_static.json → layout`, `plant/layout.py`, `equipment_specs.json`) через прототип; очікувані кількості — `meta.counts` у `seed_site.json`; ключові числа: 360 комірок `FG-*` (5 рядів × 18 пролітів × 4 яруси), 96 `RCK-*`, 144 `FUR-*`. Повторний запуск нічого не дублює. `uninstall_hook` видаляє лише власні параметри; записи Odoo й знімки лишаються.

**Доповнення (злиття, v0.2).** Нові моделі й поля міграції `post_migration` MERGE §3.6 не потребують: `addr` порожній = пресет `legacy`, `loc_tree='flat'`, `depth_mode='level'`, `warehouse_id` порожній, нові перевірки без налаштувань не виконуються. Реальні міграції (ідемпотентні): `19.0.1.0.1` (порожній план незміненого сіда), `19.0.1.2.0` (`floor_spot` у дозволені типи шарів «Склади»), `19.0.1.3.0` (xml-id довідників зони). Знімки версій `schema: 1` читаються, нові пишуться як `schema: 2` (SPEC R-40). `uninstall_hook` без змін.

## 4. Інструкція

**І-1. Створити площадку** (менеджер). «Завод 3D → Планування → Площадки → Створити» або «Конструктор → Нова площадка» → назва, код, розмір будівлі → автоматично 5 шарів і 7 перевірок. Налаштуйте для кожного шару групи редагування.
**І-2. Намалювати стелаж** (комірник). «Конструктор» → вкладка «Місця» → шаблон «Паллетний стелаж» → кількість пролітів і ярусів → префікс (`FG-R7`) → поставити на сцену → за потреби вимкнути або змінити окрему комірку. Чернетка зберігається сама.
**І-3. Додати варіант обладнання** (технолог). «Планування → Каталог варіантів → Створити» → тип (паспорт), габарити, зона обслуговування, точки підключення, потужність, маса → «Завантажити модель» (GLB, OBJ+MTL, STL, FBX, 3MF, DAE; STEP/IFC очікують перетворення) → «Підставити габарити з моделі». Файл > 20 МБ відхиляється; > 50 тис. трикутників — запропонують спростити.
**І-4. Розставити обладнання** (технолог). «Конструктор» → «Каталог» → перетягнути варіант на шар, `R` — поворот; зауваження з'являються наживо; при режимі «Заборона» об'єкт повертається.
**І-5. Налаштувати перевірки** (менеджер). Площадка → вкладка «Перевірки» → для кожної: увімкнено, «Попередження»/«Заборона».
**І-6. Опублікувати** (менеджер). «Конструктор» → «Опублікувати» → у майстрі перегляньте «буде створено / оновлено», відмітьте архівації (за замовчуванням не відмічені) → «Підтвердити й опублікувати». Нова версія — в «Версії планування».
**І-7. Повернути чернетку.** «Версії планування» → версія → «Повернути чернетку до цієї версії». Записи Odoo не змінюються; наступна публікація запропонує архівувати зайве.
**І-8. Налаштувати адресацію** (менеджер чи проєктувальник шару). Редактор → вкладка «Адресація» площадки/зони/місця → пресет або шаблон `{zone} {row} {bay} {level} {pos}` → перегляд перших кодів і лічильник змін → «Застосувати». За замовчуванням нумеруються лише нові місця (опубліковані зберігають коди); «Перенумерувати все» — лише менеджер, потрібні нові етикетки.
**І-9. Застосувати зміни в Odoo й відкотити** (менеджер). «Опублікувати» → у майстрі вкладки «Створення / Перенесення / Перейменування / Атрибути» → за потреби «Зона або ряд» і «Лише обране» → перший раз — зробіть копію бази → «Підтвердити й опублікувати». «Версії планування» → версія → «Відкотити публікацію» (лише якщо створене не використано й немає пізнішої публікації); «Журнал публікацій» показує операції.
**І-10. Варіанти планування й навчальна копія** (менеджер). «Варіанти» → «Створити з поточного» → працюйте в активному варіанті; порівняння двох варіантів показує цифри (місць, палетомісць, площа, об'єм, ємність, операцій плану); тур, що змінює дані, сам створює навчальну копію («Залишити зміни» / «Скасувати»).
**І-11. Коментарі, задачі, блокування зон** (усі / проєктувальники). Клік по місцю → «Коментар» або «Задача» з виконавцем (з'явиться завдання в Odoo); значки з числом на плані. Вибір об'єкта в режимі правки бере зону в оренду на 5 хв (значок з іменем); чужу зону можна дивитися й коментувати, але не змінювати.
**І-12. Етикетки й залишки** (комірник). «Етикетки» → вибір (виділене, зона, ряд, усе) → Code128/QR → PDF/PNG/ZPL; «Показник» → теплова карта (заповненість, нижче мінімуму, ABC, вік); «Перейти до місця»/«Де лежить» — пошук за кодом, товаром, партією.
**І-13. Структура з Odoo й файли** (менеджер, проєктувальник). «Імпорт» → XLSX/CSV або «З Odoo» → правила розбору кодів → перегляд → «Розкласти автоматично»; нерозібране — у лотку «Не розміщено»; «Оновити з Odoo» показує розбіжності (з'явилося, зникло, перейменовано, інший батько).
Докладніше — «Інструкція конструктора» (меню «Завод 3D», 36 тем UK/EN, `/f3d/constructor/help`) і `core/constructor/README.md`.

## 6. Як збудовано (злиття, хвилі 0–2)
