# td_live_production — специфікація (демо: живе виробництво)

Версія 0.1.3 · модуль `19.0.1.0.3` · лише демо-стенд (не частина продукту). План і рішення LP-01…07 — `build/live/PLAN.md`.

## 1. Склад і залежності

`depends`: `mrp`, `sale_mrp`, `td_factory3d`, `td_machine_connect`. М'яко (перевірка реєстру): `td_iot_sim` (цілі верстатам), `td_energy` (тариф),
`td_energy_analytics` («Що якщо»). Без `x_`-полів; поля в стандартних моделях з `td_`.

| Модель | Призначення |
|---|---|
| `td.live.day` | Доба: замовлення, МО, виручка, собівартість, маржа план, гаряча ділянка й її завантаження, перенос на наступну зміну, нотатка, `generated` + стан генерації (`gen_phase`, `gen_done`, `plan_json`), задачі. Унікальна `(date, company_id)`. |
| `td.live.downtime` | Запланований простій верстата: причина, стан (`setup`/`idle`/`fault`), хвилини, `planned→active→done`, зв'язок із `td.downtime`, `owned`. |
| `td.live.job` | Фонова задача (`catch_up`, `generate_day`): стан, фаза, `total/done/failed/skipped`, причини невдач, черга, `then_start`, підсумок, помилка. |
| `td.live.engine` (abstract) | Планувальник, диспетчер, догнати минуле, підготовка компанії, запуск/зупинка; файли `td_live_*.py`. |
| `mrp.production`, `sale.order` · `td_live_day_id` | Позначка «створено модулем»: диспетчер веде лише МО доби з `generated = True`. |

Параметри `td.live_production.*` (Налаштування → «Живе виробництво», `group_td_admin`): `enabled` (False; лише кнопками «Запустити»/«Зупинити»,
у формі статус), `orders_per_day` 8, `shift_start`/`shift_end` 7.0/15.5, `workdays` `0123456`, `hot_section` «Присадка» (`-` — вимкнено),
`hot_factor` 3.5 (множник тривалості операцій гарячої ділянки), `downtime_pct` 6, `job_budget_s` 30 (секунд за запуск крона-виконавця).
Службові: `demo_clock_backup`. Контекст `td_live_now` — «зараз» (naive UTC) для тестів; демо-годинник двигун не враховує.

## 2. Вимоги

| ID | Вимога |
|---|---|
| LP-01 | Лише демо-стенд; крони диспетчера й нічного плану вимкнені, `uninstall_hook` вимикає крони й прибирає параметри, бізнес-даних не чіпає. |
| LP-02 | Генерація доби ідемпотентна (одна доба — один план), частинами: план → замовлення (по одному) → розклад (чиста функція) → запис дат (по 25 нарядів) → завершення. Шаблони з бази: клієнти підтверджених SO, вироби зі специфікаціями-маршрутами. Варіант маршруту «жадібно»: гарячі верстати «повні» на 150 % зміни, решта на 85 %; операції гарячої ділянки в `hot_factor` довші. Ціна — прайс ±8 % у межах маржі 25…40 %. Один наряд на верстаті, наряди МО послідовно, у зміні; залишок — на наступну. Простої між нарядами ≥ 8 хв, аварій ≤ 2 на добу. Запобіжник: черга верстатів > 1,5 доби зменшує замовлення до чверті. Не реалізовано: фури `td_yard`, карти розкрою. |
| LP-03 | `td_dispatch()` (крон щохвилини, ≤ 150 подій і ≤ 40 с за такт): наряд стартує, коли настав час, попередній завершено, верстат вільний; завершується за планом ±15 % (детермінований шум); простої, закриття МО (компоненти списуються, бракуюче оприбутковується, партія `LIVE-<дата>`), відвантаження через 20 хв. Ідемпотентно й сумісно з автостартом/автостопом `td_machine_connect` (у т. ч. Enterprise). Помилка кроку відкочується savepoint-ом; конкурентне оновлення піднімається (Odoo повторить). Стан верстата `td.machine` змінюється лише для подій не старших за 10 хв. |
| LP-04 | «Догнати минуле»: МО без позначки модуля з усіма датами плану раніше за сьогодні завершуються датами планів, замовлення відвантажуються; нічого не видаляється. Кожна МО — окрема транзакція зі savepoint; невдала лишається як була, причина — у її чаттері. Enterprise: працівник для старту (на РЦ без операторів — користувач або перший активний), перевірки якості `passfail` проходять штатним `do_pass()`. |
| LP-05 | C-LP-01 (`build/live/PLAN.md`): `env["td.sim.device"]._td_push_machine_targets([{code, state, reason, until}])` лише за наявності моделі й методу, інакше `{"ok": 0}`. Ціль має КОЖЕН активний `td.machine`, поки диспетчер увімкнено: `working` — наряд у роботі; `idle` — наладка, очікування, перерва, «Немає завдання», «Поза зміною»; `down` — лише «Поломка». `until` = найближча зміна за планом + 2 хв, не далі `now` + 15 хв; без роботи теж 35 цілей. Збій не ламає такт; `ok = 0` — одне попередження на годину. |
| LP-06 | «Запустити»: є готовий план на сьогодні — вмикає одразу (`enabled`, обидва крони, демо-годинник вимкнено, нічний крон — 02:00 Київ); немає — у фоні «догнати минуле» (якщо є старі відкриті МО) → генерація доби, а запуск після їх завершення (`then_start`). «Зупинити» повертає годинник і скасовує відкладений запуск. |
| LP-07 | `td_prepare_company()` ідемпотентно: назва «Меблеве підприємство»; валюта UAH; собівартість компонентів ₴ лише де 0; зонний тариф `td_energy` з учорашньої доби (ніч 0,5× / напівпік 1,0× / пік 1,5× від 8,4 ₴; раніше створений «з сьогодні» зсувається на вчора, бо «Що якщо» бачить період до вчора); `td.energy.whatif._td_seed_demo()` із причинами пропуску сценаріїв у звіті. Є проводки — `UserError` до змін. SO в іншій валюті переводяться на прайс у ₴ без зміни сум. |
| LP-08 | `td_sequences_ahead()` перед створенням документів: `number_next` послідовностей SO, МО й переміщень компанії > найбільшого числового суфікса наявних імен. Ідемпотентно. |
| LP-09 | Важкі кнопки («Згенерувати сьогодні», «Згенерувати завтра», «Догнати минуле», «Запустити» без плану) лише ставлять `td.live.job` і повертають «запущено у фоні». Крон-виконавець (активний, раз на 10 хв + `ir.cron._trigger` після постановки й після порції) бере найстарішу активну задачу порціями ≤ `job_budget_s`: кожна порція — своя транзакція з commit, до 3 спроб при конфлікті (потім елемент у кінець черги, після 3 відкладень — невдача). Повторне натискання не дублює (унікальний індекс на активні). Прогрес і підсумок («закрито N з M, топ-3 причини») — у налаштуваннях, у `td.live.job` і в добі. Помилка задачі — стан «Помилка» з текстом, не нескінченний цикл. |
