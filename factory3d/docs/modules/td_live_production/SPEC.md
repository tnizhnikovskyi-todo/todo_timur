# td_live_production — специфікація (демо: живе виробництво)

Версія 0.1 · модуль `19.0.1.0.0` · лише демо-стенд (не частина продукту). План і рішення LP-01…07 — `build/live/PLAN.md`.

## 1. Склад і залежності

`depends`: `mrp`, `sale_mrp`, `td_factory3d`, `td_machine_connect`. М'яко (перевірка реєстру): `td_iot_sim` (цілі верстатам), `td_energy`
(тариф), `td_energy_analytics` («Що якщо»). Без `x_`-полів; поля в стандартних моделях з `td_`.

| Модель | Призначення |
|---|---|
| `td.live.day` (M-01) | Доба: замовлення, МО, виручка, собівартість, маржа план, перевантажена ділянка, її завантаження, перенос на наступну зміну, нотатка. Унікальна `(date, company_id)`. |
| `td.live.downtime` (M-02) | Запланований простій верстата: причина (`mrp.workcenter.productivity.loss`), стан (`setup`/`idle`/`fault`), хвилини, `planned→active→done`, зв'язок із `td.downtime`, ознака `owned`. |
| `td.live.engine` (M-03, abstract) | Планувальник, диспетчер, догнати минуле, підготовка компанії, запуск/зупинка. Три файли `_inherit`. |
| `mrp.production.td_live_day_id`, `sale.order.td_live_day_id` | Позначка «створено модулем»: диспетчер керує лише такими МО. |

Параметри `td.live_production.*` (Налаштування → «Живе виробництво», група `group_td_admin`):

| Ключ | За замовчуванням | Зміст |
|---|---|---|
| `enabled` | False | Головний вимикач (лише кнопками «Запустити»/«Зупинити»; у формі — статус); без нього крони нічого не роблять |
| `orders_per_day` | 8 | Замовлень на добу (2–3 рядки = МО в кожному) |
| `shift_start` / `shift_end` | 7.0 / 15.5 | Зміна за Києвом |
| `workdays` | `0123456` | Робочі дні (0 — пн); демо працює щодня |
| `hot_section` | Присадка | Мітка-дільниця (`mrp.workcenter.tag`); `-` — без перевантаження |
| `hot_factor` | 3.5 | Множник тривалості операцій перевантаженої ділянки |
| `downtime_pct` | 6 | Частка робочого часу верстатів на простої, % |

Службові: `demo_clock_backup` (значення `td.viewer.demo_clock` до запуску). Контекст `td_live_now` — «зараз» (naive UTC) для тестів і
віртуального часу; демо-годинник двигун не враховує.

## 2. Вимоги

| ID | Вимога |
|---|---|
| LP-01 | Модуль ставиться лише на демо-стенд; крони вимкнені, `uninstall_hook` вимикає крони й прибирає параметри, бізнес-даних не чіпає. |
| LP-02 | `td_generate_day(day)` ідемпотентно (одна доба — один план): шаблони беруться з бази (клієнти підтверджених SO, вироби зі специфікаціями з операціями, їхні кількості з історії), нових шаблонів не створюється. Рядки замовлення — варіант маршруту «жадібно» за навантаженням: гарячі верстати «повні» на 150 % зміни, решта на 85 %. Ціна рядка — прайс ±8 %, затиснена так, щоб планова маржа лишилась у 25…40 %. МО на кожен рядок (`origin` = номер SO), розклад із кінцевою потужністю РЦ (один наряд на верстаті, наряди МО послідовно, у межах зміни; залишок перенесено на наступну). Операції гарячої ділянки довші в `hot_factor` разів. Простої між нарядами (≥ 8 хв; аварій ≤ 2 на добу). Запобіжник: черга верстатів понад 1,5 доби зменшує кількість замовлень до чверті. Фури/ворота й карти розкрою (`td_yard`, відходи 8–18 %) — не реалізовано в 0.1. |
| LP-03 | `td_dispatch()` (крон щохвилини, ≤ 150 подій за такт): наряд стартує, коли настав плановий час, попередній завершено, верстат вільний (немає наряду й простою); завершується за планом ±15 % (детермінований шум за ключем наряду); простої відкриваються й закриваються за часом; МО закривається (компоненти списуються, бракуюче оприбутковується, партія `LIVE-<дата>`), замовлення відвантажується через 20 хв після останньої МО. Кроки ідемпотентні й сумісні з автостартом/автостопом `td_machine_connect` (у т. ч. з Enterprise `mrp_workorder`): наряд у роботі чи з відкритим таймером не стартує вдруге, завершений не завершується вдруге, простій, відкритий станом верстата, лише класифікується. Помилка кроку відкочується savepoint-ом, такт триває. |
| LP-04 | `td_catch_up()`: МО без позначки модуля з усіма плановими датами раніше за початок сьогодні завершуються датами планів (наряди послідовно, МО закривається, замовлення відвантажується); відкриті записи втрат верстата закриваються на початок наряду. Нічого не видаляється. Згенеровані МО доганяє диспетчер. |
| LP-05 | Контракт C-LP-01 (див. `build/live/PLAN.md`): `env["td.sim.device"]._td_push_machine_targets([{code, state, reason, until}])` лише за наявності моделі й методу, інакше `{"ok": 0}`. `working` — наряд у роботі; `idle` — наладка, очікування, перерва; `down` — лише «Поломка». `until` = очікуваний кінець стану + 2 хв. Збій емулятора не ламає такт; `ok = 0` при непорожніх цілях — одне попередження на годину. |
| LP-06 | Кнопка «Запустити живе виробництво»: `enabled`, обидва крони активні, `td.viewer.demo_clock` вимкнено (значення в `demo_clock_backup`), нічний крон — найближчі 02:00 Europe/Kyiv. «Зупинити» повертає годинник. Нічний крон: план на сьогодні (якщо немає) і на завтра, потім сам ставить наступний `nextcall` на 02:00. |
| LP-07 | `td_prepare_company()` ідемпотентно: назва «Меблеве підприємство»; валюта UAH; собівартість компонентів ₴ лише де 0; зонний тариф `td_energy` з поточної доби (ніч 0,5× / напівпік 1,0× / пік 1,5× від 8,4 ₴, діючий тариф закривається вчорашнім днем); `td.energy.whatif._td_seed_demo()`. Валюта: до будь-яких змін перевіряється, чи є проводки (`account.move.line`); якщо є — `UserError` з причиною й кількістю, нічого не змінено. Підтверджені SO в іншій валюті переводяться на прайс у ₴ без перерахунку сум (стандартний `write` це забороняє, тому `BaseModel.write`). |
