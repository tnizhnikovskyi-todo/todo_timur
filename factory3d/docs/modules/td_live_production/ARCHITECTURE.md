# td_live_production — технічне рішення (демо: живе виробництво)

Модуль робить демо-завод живим у реальному часі: щодоби нові замовлення, наряди, що стартують і завершуються, простої з причинами,
закриття МО й відвантаження. Лише для демо-стенда. Специфікація — [SPEC.md](SPEC.md).

## 1. Принципи

- **Розрахунок окремо від ORM.** `tools/` — чисті функції з юніт-тестами: `clock`, `noise`, `planner`, `dispatch`, `pricing`, `tariff`.
  Моделі збирають вхід з бази й застосовують результат.
- **Такт без пам'яті.** Диспетчер збирає стан із бази й дискретною симуляцією (`dispatch.simulate`) отримує події з часовими мітками до
  «зараз»: старт наряду = `max(плановий старт, кінець попереднього, верстат вільний)`, завершення через `план × (1 ± 0,15)`. Один тик після
  паузи дає ті самі записи, що й тики щохвилини; перший запуск посеред доби одразу закриває минуле. Тривалість — функція ключа `wo<id>`.
- **Ідемпотентність і Enterprise.** Крок перевіряє стан перед дією: наряд `progress` чи з відкритим таймером не стартує (його міг запустити
  автостарт `td_machine_connect`); `done` не завершується; простій, відкритий станом верстата, лише класифікується. Старт іде через
  `td.machine._td_start_at` (працівники Enterprise — duck typing; на РЦ без операторів — запасний працівник). Дати нарядів пишуться з
  `bypass_duration_calculation`; `button_start` першого наряду МО скидає плани решти (`button_unplan`) — диспетчер їх відновлює.
- **Помилка одного кроку не зупиняє такт** (savepoint, попередження); конкурентне оновлення (`SerializationFailure`) піднімається.

## 2. Фонові задачі

Усе, що довше за кілька секунд, виконується не в запиті (Cloudflare ~100 с, `limit_time_real` ~120 с), а в `td.live.job`:

- Кнопка = `td_enqueue` (унікальний частковий індекс не дає дубля) + `ir.cron._trigger` крона-виконавця.
- Виконавець: `FOR UPDATE SKIP LOCKED` на найстарішу активну задачу → порція → commit → ще порція, поки не вичерпано `job_budget_s`; далі
  сам себе будить. Порція = одна одиниця роботи: замовлення, 25 нарядів, МО, ≤ 15 с подій диспетчера. Обрив процесу втрачає лише порцію:
  стан (`gen_phase/gen_done/plan_json` у добі, `queue` у задачі) лежить у базі.
- `catch_up`: диспетчер для керованих МО → черга старих МО (по одній за порцію; конфлікт → повтор, далі в кінець черги).
  `generate_day`: план → замовлення → розклад → запис дат → завершення → (для сьогодні) диспетчер. Диспетчер ігнорує добу з `generated = False`.
- `then_start` — «Запустити» без плану: ланцюг задач, після останньої вмикається живе виробництво (`td_activate`).
- Нічний крон лише ставить задачі; такт диспетчера обмежений 40 с і 150 подіями, тож довга пауза доганяється за кілька тактів.

## 3. Швидкість закриття МО

На сервері закриття МО (профілювання без запису): ≈ 5–6 с, ≈ 1150 запитів; `button_mark_done` — ≈ 860 запитів (td_energy ≈ 330, правила
поповнення ≈ 250), решта — шар модуля. Зроблено: історичні події не чіпають `td.machine` (менше блокувань; конфлікти з кроном верстатів
і повтори були головною причиною «30 с на МО»); дати виконаних рухів — одним `UPDATE` (108 → 7 запитів); порції й повтори замість
довгої транзакції. Енергію td_energy при закритті не вимикаємо: вона входить у вартість МО.

## 4. Ризики

- Накопичення черги: запобіжник зменшує кількість замовлень, якщо верстати завантажені понад 1,5 доби.
- Компоненти оприбутковуються «на вимогу» під час закриття МО; фури `td_yard` і карти розкрою — поза версією.
- Закриття МО/відвантаження чіпає приватні механізми складу Odoo; дати рухів — прямий SQL (лише два поля).
- Валюта SO: `BaseModel.write` в обхід заборони стандартного `write`; лише демо-база без проводок.
