# Changelog

## 19.0.1.1.3 — крон «Телеметрія: застарілі сигнали й офлайн-колектори» без SerializationFailure

Оновлення: `-u` модуля. Схеми й дані не змінюються, міграційних скриптів немає.

- DEC-20: `td.signal._cron_stale` і `td.collector._cron_offline` не падають на `SerializationFailure`/`LockNotAvailable`/
  `DeadlockDetected`, коли ті самі рядки пише push колектора чи інший щохвилинний крон. Рядки блокуються
  `FOR UPDATE SKIP LOCKED` за зростанням id (`tools/locking.py`, `lock_skip_locked`; у REPEATABLE READ рядок, змінений
  паралельною транзакцією після знімки, теж пропускається: пачка блокується по одному рядку у власних savepoint),
  кожен сигнал записується у власному savepoint, SQL блокувань не пише «bad query» в лог. Пропущений рядок опрацює наступний
  запуск через хвилину; бізнес-поведінка (stale за вікном, офлайн колектора за 3·`status_interval_s`) не змінилась.
- `td.signal._mark_stale` пропускає зайняті рядки лише з контекстом `td_skip_locked` (його ставить крон); виклики з API
  (`_apply_status` джерела, вимкнення читання) працюють як раніше.
- `_cron_offline`: колектор із його джерелами обробляється в одному savepoint; зайняте джерело чи колектор лишає колектор
  `online` до наступного запуску (стан джерел не розходиться зі станом колектора); колектор, що вийшов на зв'язок
  після початку крону, не стає `offline`. Сигнали, зайняті іншою транзакцією, візьме `_cron_stale` за таймаутом.

## Unreleased
- Фікс T-5: `_apply_status` не стирає `last_error` при невідомому `state`; для gauge/counter зайвий `text` у показанні
  ігнорується (колектор шле `value`+`text` для змаплених станів, тому відхиляти не можна); неправильний HTTP-метод → 405 у
  JSON-конверті (`method_not_allowed`, заголовок `Allow`); додано `static/description/icon.png`.
- Фікс T-1b: статуси `stale`/`offline`/`unknown` (немає свіжих даних після зупинки стенда) залежать від часу, а не від значення —
  крок 8 пише їх у `status_notes`, а не в `mismatches`; кроки 6 і 9 виконуються.
- Фікс T-1 (міграція рівня 0 застрявала в `partial`): крок 8 (`hooks.verify`) звіряє знімок, який зробив крок 2, а не живий
  рівень 0; статус `warn`/`alarm` через пороги каталогу, яких на рівні 0 не було, — не розбіжність (звіт: `status_notes`);
  показання — кожне `x_f3d_reading` має мати `td.reading` (рядки, які рівень 0 уже почистив, не заважають); при
  повторному запуску значення сигналу `sim_data`, свіжіше за `last_ts`, підхоплюється з рівня 0 (не відкочуючи новіші
  дані телеметрії). Кроки 6 (заявки) і 9 (вимкнення рівня 0) виконуються, якщо лишились лише такі різниці.
- DEC-19: `td.collector._touch` пише `last_seen`/`last_ip`/`last_push_at` не частіше за раз на
  `min(td.telemetry.touch_interval_s, status_interval_s)` с (30 за замовчуванням); зміна стану, IP чи версії — одразу;
  push — один `write` замість двох.
