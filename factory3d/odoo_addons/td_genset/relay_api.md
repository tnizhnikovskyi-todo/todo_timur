# API ретранслятора SmartGen — повний довідник для розробника модуля Odoo

Документ самодостатній: його достатньо, щоб написати модуль Odoo для моніторингу й керування генератором. Усі приклади відповідей — справжні, зняті з робочого API 07.10.2026 (лише прибрано IP модуля).

---

## 1. Що це і як влаштовано

**Об'єкт:** генератор біля офісу ToDo («Садова вулиця», Київ). Контролер **SmartGen HGM6120N**, модуль зв'язку **CMM366B-4G** (до контролера по USB, у мережу — по 4G).

```
Контролер HGM6120N ──USB── модуль CMM366B-4G ──4G/TCP──▶ ретранслятор (VPS) ──▶ хмара SmartGen (застосунок SmartGen)
                                                               │
                                                               ├─ SQLite: повідомлення, знімки показань, журнал команд
                                                               │
                                                               └─ HTTPS API  ◀── Odoo (erp.todo.ltd) — ваш модуль
```

- Ретранслятор стоїть між модулем і хмарою SmartGen і прозоро пересилає трафік: застосунок SmartGen працює як раніше.
- Він збирає все, що модуль надсилає, розшифровує регістри контролера і віддає показання через HTTPS API.
- Через той самий API Odoo надсилає команди (Авто / Ручний / Пуск / Стоп …). Ретранслятор вставляє їх у з'єднання модуля так само, як це робить хмара SmartGen. **Керування перевірено на живому контролері 07.10.2026**: `manual` і `auto` виконуються за ~3 с.
- **Ретранслятор нічого не надсилає в Odoo сам.** Odoo опитує API (pull). Вхідний доступ до Odoo ззовні не потрібен; потрібен лише вихідний HTTPS з сервера Odoo на `gen-relay.todo.ltd:443`.
- Генератором керує не лише Odoo: ще й застосунок SmartGen і кнопки на самому контролері. Модуль **не може вважати себе єдиним джерелом команд** — фактичний режим завжди брати з показань.

**Ціль модуля Odoo** (погоджено з Тимуром Нижниковським — замовником модуля):
- показання генератора в Odoo: поточні значення, журнал, аналітика, події;
- керування: розклад, робота поза графіком з таймером, дні-винятки, ручні кнопки; журнал команд обов'язковий (див. розділ 9).

## 2. Підключення

| Що | Значення |
|---|---|
| Базова адреса | `https://gen-relay.todo.ltd/api/v1` |
| Авторизація | заголовок `Authorization: Bearer <токен>` у **кожному** запиті |
| Токен | видає Тимур. У коді й репозиторії його **не тримати**; в Odoo — у системному параметрі (`ir.config_parameter`, наприклад `smartgen.relay_token`), доступ лише адміністраторам |
| Протокол | HTTPS (сертифікат Let's Encrypt, звичайна перевірка сертифіката), HTTP/1.1 або HTTP/2 |
| Формат | JSON UTF-8 у відповідях; тіло POST — JSON (заголовок `Content-Type` не перевіряється, але ставте `application/json`) |
| Час | усі `ts` / `created` / `sent` / `done` — секунди Unix (UTC, дробові); поля `*_utc` — той самий момент рядком `2026-10-07T15:57:22Z`. Розклад генератора — за київським часом (Europe/Kyiv), переводьте самі |
| Таймаут клієнта | 15–20 с (сервер відповідає за мілісекунди) |
| Модуль на об'єкті | один, `hostid = "3130373031334717003D002E"`. Параметр `hostid` у запитах можна не передавати; передавайте, якщо модуль має бути готовий до кількох генераторів |
| Кешування | відповіді мають `Cache-Control: no-store` |

Перевірка з термінала:
```bash
curl -s -H "Authorization: Bearer $TOKEN" https://gen-relay.todo.ltd/api/v1/status
```

> ⚠️ **Робочий API керує справжнім генератором.** Під час розробки команди надсилайте лише на локальний стенд (розділ 10). На робочий API — тільки читання, доки Тимур не дозволить інше.

## 3. Загальні правила

- Токен перевіряється **першим**: без токена або з неправильним будь-який запит (навіть на неіснуючий шлях) → `401`.
- Помилка завжди має вигляд `{"error": "текст"}`, іноді з додатковими полями (`"known": [...]` — відомі hostid).
- Курсорні списки (`/readings`, `/raw`, `/commands`) повертають записи з `id > since` за зростанням `id`. `id` лише зростають і ніколи не повторюються (навіть після очищення старих записів).
- Параметри `since` і `limit` — цілі ≥ 0; не число → `400 {"error": "bad request: ValueError"}`. `limit` обмежено 2000.
- Тіло запиту — до 64 КБ.

| Код | Коли | Приклад тіла |
|---|---|---|
| 200 | успіх | |
| 201 | команду прийнято в чергу | запис команди |
| 400 | не JSON; не число в `since`/`limit`; невідома команда; кілька модулів і не вказано `hostid` | `{"error": "body must be JSON"}`, `{"error": "unknown command, allowed: ['auto', 'gen_close_open', 'mains_close_open', 'manual', 'start', 'stop', 'test']"}`, `{"error": "hostid is required", "known": [...]}` |
| 401 | немає токена / не той токен | `{"error": "missing or wrong token"}` |
| 403 | команди вимкнено на ретрансляторі | `{"error": "commands are disabled on the relay (RELAY_COMMANDS_ENABLED=0)"}` |
| 404 | невідомий шлях / команда / hostid; ще немає жодного знімка | `{"error": "not found"}`, `{"error": "no such command"}`, `{"error": "unknown hostid", "known": [...]}`, `{"error": "no readings yet"}` |
| 405 | шлях правильний, метод ні | `{"error": "method not allowed"}` |
| 409 | команду **зараз** виконати не можна (тимчасово) | `{"error": "modem is not connected right now"}`, `{"error": "command format not learned yet: …"}`, `{"error": "5 commands already waiting for this modem"}` |
| 413 | тіло більше 64 КБ | `{"error": "body too large"}` |
| 500 | внутрішня помилка ретранслятора | `{"error": "internal error"}` |
| 502/503/504 | ретранслятор недоступний (від nginx, тіло може бути HTML) | — |

## 4. Ендпоінти

| Метод і шлях | Для чого | Як часто викликати з Odoo |
|---|---|---|
| `GET /status` | стан ретранслятора й модуля: на зв'язку, режим, готовність команд | раз на 1–5 хв (моніторинг зв'язку) і перед командою |
| `GET /latest` | останній знімок показань | для екрана «зараз» і перевірки режиму після команди |
| `GET /readings` | знімки після курсору — **основне джерело даних** | cron раз на 1–5 хв |
| `GET /raw` | сирі повідомлення протоколу | лише діагностика, у модулі не потрібен |
| `POST /commands` | надіслати команду контролеру | на переходах розкладу/таймера, кнопки |
| `GET /commands/<id>` | стан однієї команди | після POST, раз на 2–3 с до фінального статусу |
| `GET /commands?since=<id>` | журнал команд ретранслятора | за потреби звірки |

Параметрів немає.

| `counts` | кількість записів у таблицях | — |

### 4.3 `GET /readings` — знімки за курсором

| Параметр | Обов'язковий | За замовчуванням | Що |
|---|---|---|---|
| `since` | ні | `0` | повернути знімки з `id > since` |
| `limit` | ні | `500` | максимум записів (≤ 2000) |
| `hostid` | ні | — | обмежити модулем |
| `raw` | ні | — | `raw=1` додає `regs` / `coils` до кожного знімка (у ~5 разів більше трафіку; зазвичай не треба) |

```json
{"readings": [ {знімок}, {знімок}, … ], "next_since": 90}
```

- `next_since` — `id` останнього знімка у відповіді; якщо список порожній — той самий `since`.
- Порожньо: `{"readings": [], "next_since": <since>}`.
- Алгоритм опитування — розділ 8.1.

### 4.4 `GET /raw` — сирі повідомлення (діагностика)

Параметри `since`, `limit` (за замовчуванням 200, ≤ 2000). Відповідь `{"raw": [...], "next_since": N}`; елемент:
```json
{"id": 1630, "ts": 1791390918.37, "time_utc": "2026-10-07T16:35:18Z", "conn": 7, "dir": "modem->cloud",
 "hostid": "3130373031334717003D002E",
 "msg": {"method": "reqdatachange", "hostid": "…", "params": {"packetnum": 2, "03": [{"0000": "00EF"}, …]}}}
```
`dir`: `modem->cloud`, `cloud->modem`, `relay->modem` (наші команди). Зберігаються 14 днів. **Модулю Odoo не потрібен.**

### 4.5 `POST /commands` — надіслати команду

Тіло:
```json
{"command": "auto", "requested_by": "Іван Петренко (res.users 42)", "source": "odoo:schedule"}
```

| Поле | Обов'язкове | Що |
|---|---|---|
| `command` | так | одна з: `auto`, `manual`, `stop`, `start`, `test`, `gen_close_open`, `mains_close_open` (розділ 7.1) |
| `hostid` | ні | на одному модулі можна не передавати |
| `requested_by` | ні | хто ініціював, до 120 символів (обрізається). Рекомендовано: ім'я + id користувача Odoo, або `"Odoo: розклад"` |
| `source` | ні | звідки, до 60 символів. Рекомендовано: `odoo:schedule`, `odoo:timer`, `odoo:button`, `odoo:exception`, `odoo:retry` |

Відповідь `201` — запис команди зі статусом `queued`:
```json
{"id": 5, "created": 1791390900.1, "created_utc": "2026-10-07T16:35:00Z", "hostid": "3130373031334717003D002E",
 "command": "auto", "requested_by": "…", "source": "odoo:schedule", "status": "queued",
 "frame": null, "uid": null, "sent": null, "sent_utc": null, "done": null, "done_utc": null,
 "response": null, "error": null}
```
Помилки: `400` (невідома команда / не JSON), `403` (команди вимкнено), `404` (невідомий hostid), `409` (модуль не на зв'язку / формат не вивчено / у черзі вже 5).

### 4.6 `GET /commands/<id>` — стан команди

Справжній приклад (команда, якою генератор переведено в Авто 07.10.2026):
```json
{
 "id": 4, "created": 1791388639.424243, "hostid": "3130373031334717003D002E",
 "command": "auto", "requested_by": "Тимур (через Claude)", "source": "claude:api",
 "status": "done", "frame": "00050003FF007DEB", "uid": "action",
 "sent": 1791388639.4248836, "done": 1791388642.0822377,
 "response": {"method": "writeConfig", "hostid": "3130373031334717003D002E", "uid": "action",
              "params": "00050003FF007DEB,1"},
 "error": null,
 "created_utc": "2026-10-07T15:57:19Z", "sent_utc": "2026-10-07T15:57:19Z", "done_utc": "2026-10-07T15:57:22Z"
}
```

| Поле | Що |
|---|---|
| `status` | `queued` → `sent` → `done` / `failed` / `timeout` (розділ 7.2) |
| `frame` | надісланий кадр Modbus (hex) |
| `uid` | ідентифікатор у протоколі (`action`, як у хмари) |
| `response` | відповідь модуля як є; `params` = `"<кадр>,1"` (прийнято) або `",0"` (відхилено) |
| `error` | текст помилки для `failed` / `timeout`: `controller rejected the command`, `no reply in 30 s`, `modem disconnected`, `relay restarted` |

`404 {"error": "no such command"}` — немає такого id.

### 4.7 `GET /commands?since=<id>&limit=200`

`{"commands": [ {запис}, … ]}` — записи з `id > since` за зростанням. **Поля `next_since` немає**: курсор — найбільший отриманий `id`. Журнал містить лише команди, надіслані через API (не з застосунку SmartGen і не кнопками).

## 5. Знімок показань

```json
{"id": 90, "ts": 1791390868.86, "time_utc": "2026-10-07T16:34:28Z", "hostid": "…", "reason": "interval",
 "values": { … }, "regs": {"0": 239, …}, "coils": {"0": 0, …}}
```

| Поле | Що |
|---|---|
| `id` | унікальний, зростає; ключ для Odoo (не дублювати записи з тим самим `id`) |
| `ts`, `time_utc` | коли ретранслятор зробив знімок (UTC) |
| `reason` | `first` — перший знімок після запуску ретранслятора; `change` — змінився стан (режим, аварія, автомат, мережа, стан агрегату); `interval` — плановий |
| `values` | розшифровані значення (5.1, 5.2) |
| `regs`, `coils` | сирий образ «адреса → значення» (лише з `raw=1`) |

**Коли пишуться знімки:**
- раз на 60 с (`snapshot_sec`), **поки модуль на зв'язку** (повідомлення за останні 90 с);
- одразу при зміні: стану агрегату (`genset_status`) або сигналів 0, 1, 2, 6, 7, 8, 40–43, 56, 57, 64, 65, 69, 72 (аварії, режими, автомати, реле пуску й палива, стан мережі й генератора).
- Обсяг: ~1 440 знімків на добу + зміни. Зберігаються **180 днів** — Odoo може бути недоступний тижнями й потім догнати.
- **Модуль не на зв'язку → знімків немає.** Пропуск у часі між знімками = не було зв'язку (або не працював ретранслятор). Не інтерполюйте.

**Семантика значень:**
- Значення вже в одиницях (коефіцієнти протоколу застосовано).
- Ключа немає в `values` — значення невідоме (наприклад, одразу після запуску ретранслятора до першого пакета). Обробляйте як «немає даних».
- `null` — контролер повідомляє «немає даних» (на екрані «###», сире значення 32766).
- Модуль читає з контролера сигнали 0–77 і регістри 0–44, 46–55 — **інших ключів не буде** (зокрема `controller_model`, регістр 71, у «Садової» відсутній).
- Числа з `power_factor`, частотами, струмами, напругою АКБ — дробові; решта цілі.

### 5.1 `values`: регістри 03H

| Ключ | Регістр | Що | Одиниці | Приклад 07.10 |
|---|---|---|---|---|
| `mains_ua`, `mains_ub`, `mains_uc` | 0–2 | Мережа, фазні напруги | V | 239 / 234 / 240 |
| `mains_uab`, `mains_ubc`, `mains_uca` | 3–5 | Мережа, лінійні напруги | V | 409 / 410 / 418 |

## 7. Команди

### 7.1 Перелік

| `command` | Кадр 05H, адреса | Що робить контролер | Чим підтверджувати |
|---|---|---|---|
| `auto` | 0003 | режим Авто: генератор сам запуститься при зникненні мережі | `controller_mode == "auto"` (сигнал 41). **Перевірено 07.10** |
| `manual` | 0004 | режим Ручний: сам не запускається | `controller_mode == "manual"` (42). **Перевірено 07.10** |
| `stop` | 0001 | Стоп | `stop_mode` (43) і/або `genset_status` → 0. ⚠️ Як саме поводиться контролер після Manual → Stop, ще **не перевірено** — див. розділ 11 |
| `start` | 0000 | Пуск (працює в ручному режимі) | `genset_status` іде до 9, `speed > 0` |
| `test` | 0002 | Тест (пуск під навантаженням за налаштуваннями контролера) | `test_mode` (40) |
| `gen_close_open` | 0005 | **перемикач** автомата генератора (замкнено ↔ розімкнено) | змінився `gen_on_load` |
| `mains_close_open` | 0006 | **перемикач** автомата мережі | змінився `mains_on_load`. Перевірено 07.10 (натискання в застосунку SmartGen) |

`gen_close_open` / `mains_close_open` — перемикачі, а не «замкнути»/«розімкнути»: перед надсиланням перевіряйте поточний стан і надсилайте лише тоді, коли він не той, що потрібен. Розмикання мережі знеструмлює навантаження офісу — ці кнопки варто ховати за підтвердженням і правами.

### 7.2 Життєвий цикл

```
POST → queued ──▶ sent ──▶ done      модуль відповів «кадр,1»: контролер прийняв запис
                         ├─▶ failed    «кадр,0» (відхилено) / обрив з'єднання / ретранслятор перезапустився
                         └─▶ timeout   немає відповіді модуля 30 с
```

- Команди одного модуля виконуються **по черзі**, з паузою **2 с** між ними. «Ручний + Стоп» — це два POST поспіль, без очікування між ними; порядок зберігається.
- У черзі не більше 5 команд (6-та → 409).
- Звичайний час до `done` — **~3 с**.
- Після перезапуску ретранслятора всі `queued`/`sent` стають `failed` з `error: "relay restarted"`.
- **`done` ≠ режим змінився.** `done` означає лише, що контролер прийняв запис Modbus. Фактичний результат перевіряйте за показаннями (8.3). Якщо ввімкнено `remote_lock`, контролер може прийняти й не виконати.
- Хмара SmartGen наших команд не бачить; застосунок SmartGen покаже лише зміну режиму.

### 7.3 Коли команду не прийме (409) і що робити

| Причина | Як часто | Дія в Odoo |
|---|---|---|
| `modem is not connected right now` | модуль сам перепідключається **кожні 4–25 хв**, кожне перепідключення — кілька секунд; також при обриві 4G | повторити через 10–30 с, до 10 хв |
| `command format not learned yet` | лише після встановлення нового ретранслятора | тривога адміну |
| `N commands already waiting` | якщо надсилати багато поспіль | не надсилати нові, доки не завершаться попередні |
| `403 commands are disabled` | DevOps вимкнув команди | не повторювати; показати «керування вимкнено» |

## 8. Рекомендовані алгоритми

### 8.1 Забір показань (cron раз на 1–5 хв)

```python
import requests

def _api(env):
    icp = env["ir.config_parameter"].sudo()
    base = icp.get_param("smartgen.relay_url", "https://gen-relay.todo.ltd/api/v1")
    headers = {"Authorization": f"Bearer {icp.get_param('smartgen.relay_token')}"}
    return base, headers

def pull_readings(env):
    base, headers = _api(env)
    icp = env["ir.config_parameter"].sudo()
    since = int(icp.get_param("smartgen.readings_cursor", "0"))
    while True:
        r = requests.get(f"{base}/readings", params={"since": since, "limit": 500}, headers=headers, timeout=20)
        r.raise_for_status()
        page = r.json()
        for rd in page["readings"]:
            # ідемпотентно: унікальний індекс по external id знімка
            ...  # створити запис, якщо запису з relay_id == rd["id"] ще немає
        since = page["next_since"]
        icp.set_param("smartgen.readings_cursor", str(since))
        env.cr.commit()                    # курсор і записи — в одній транзакції
        if len(page["readings"]) < 500:
            break
```

- Унікальний ключ запису в Odoo — `id` знімка (SQL-constraint на поле `relay_id`).
- Курсор зберігати в тій самій транзакції, що й записи.
- Мережеві помилки / 5xx — просто вийти; наступний запуск cron продовжить з курсору.

### 8.2 Моніторинг зв'язку (cron раз на 1–5 хв)

`GET /status`: якщо `devices[0].online == false` довше 10 хв або сам API недоступний довше 10 хв — тривога (отримувача ще не визначено, див. розділ 11). Відновлення — повідомлення «зв'язок відновлено».

### 8.3 Команда з перевіркою результату

Погоджено: після команди перевіряти режим, повторювати до 10 хв, потім тривога.

```python
import time, requests

EXPECT = {"auto": "auto", "manual": "manual", "test": "test"}   # лише режими; stop/start перевіряти за genset_status (7.1, 8.4)

def send_and_verify(env, command, who, source, deadline_s=600):
    base, headers = _api(env)
    started = time.time()
    while time.time() - started < deadline_s:
        r = requests.post(f"{base}/commands", json={"command": command, "requested_by": who, "source": source},
                          headers=headers, timeout=20)
        if r.status_code == 403:
            return "disabled", r.json()["error"]
        if r.status_code in (409, 502, 503, 504) or r.status_code >= 500:
            time.sleep(20); continue                       # модуль перепідключається — повторити
        r.raise_for_status()
        cid = r.json()["id"]
        cmd = r.json()
        for _ in range(20):                                # ~40 с на фінальний статус
            time.sleep(2)
            cmd = requests.get(f"{base}/commands/{cid}", headers=headers, timeout=20).json()
            if cmd["status"] not in ("queued", "sent"):
                break
        if cmd["status"] == "done":
            for _ in range(12):                            # до 60 с на підтвердження режиму
                time.sleep(5)
                lt = requests.get(f"{base}/latest", headers=headers, timeout=20).json()
                if lt["time_utc"] >= cmd["done_utc"] and lt["values"].get("controller_mode") == EXPECT.get(command):
                    return "confirmed", cid
        time.sleep(30)                                     # failed / timeout / режим не той — повторити
    return "alarm", "режим не підтвердився за 10 хв"
```

> У реальному модулі не блокуйте воркер Odoo `sleep`-ами на хвилини: зробіть стан-машину (запис «завдання команди» зі статусом і часом наступної перевірки) і короткий cron раз на 15–30 с, який просуває її. Код вище — логіка, не готова реалізація.

- Перед надсиланням: якщо `controller_mode` уже дорівнює цільовому — **не надсилати** (погоджено: «команди лише на переходах»).
- Кожну спробу записувати в журнал Odoo: хто, звідки, `id` команди ретранслятора, статус, підтвердження.

### 8.4 «Ручний + Стоп»

Два POST поспіль (`manual`, потім `stop`); ретранслятор виконає їх по черзі з паузою 2 с. Підтвердження `manual` — `controller_mode == "manual"`; для `stop` — `genset_status` 0 (генератор не працює). Остаточну поведінку `stop` уточнимо (розділ 11).

## 9. Вимоги до модуля, погоджені з Тимуром (06.10.2026)

- **Хто керує:** усі співробітники; журнал команд обов'язковий (хто, коли, що, результат).
- **Розклад:** дні тижня + вікна часу (наприклад, пн–пт 08:45–18:30), кілька рядків на день. Початок вікна → **Авто**; кінець → **Ручний + Стоп**.
- **Робота поза графіком:** тривалість (год:хв) + «Застосувати» → **Авто**; після закінчення → **Ручний + Стоп**. Має пріоритет над розкладом. Кнопки **+15 / +30 / +60 хв** без зупинки таймера. Кнопка **«Зупинити таймер»**.
- Після закінчення або зупинки таймера — стан **за розкладом**: у вікні → Авто, поза вікном → Ручний + Стоп.
- **Дні-винятки:** «Не запускати» / «Інший час» (з вибором вікна) — замінюють розклад на дату.
- **Команди лише на переходах** (без примусового повернення режиму, якщо хтось змінив його в застосунку чи на контролері).
- **Після команди** перевірка режиму, повтор до 10 хв, потім тривога.
- **Керування автоматами** генератора/мережі (`gen_close_open` / `mains_close_open`) — у мокапі як «Замкнути / Розімкнути».
- Отримувач тривог **ще не визначений** — зробити налаштовуваним.
- Мокап модуля (4 сторінки: форма з поточними даними й керуванням, журнал показань кожні 15 хв, аналітика, події): https://claude.ai/artifact/CwaaS3x2U3FHWdKwtFGH5Q. Стиль — актуальна версія Odoo, одна тема, мобільна верстка обов'язкова (спершу керування).
- Цільова база: **erp.todo.ltd** (Odoo 18 — версію підтвердити в Тимура перед початком).

```bash
python3 simulator.py modem 127.0.0.1:9181 3600 &
```

Далі в Odoo (dev): `smartgen.relay_url = http://127.0.0.1:8081/api/v1`, `smartgen.relay_token = dev-token-0123456789abcdefghij`.

Що можна відтворити:
- дані: 251 kWh, 33 год, 38 пусків, АКБ 27.7 V, мережа 231/226/230 V, Standby, режим Auto;
- команди → `done` за ~1 с, режим змінюється в наступному знімку;
- 409 «modem is not connected» — зупинити фейковий модуль (`kill`);
- 403 — запустити ретранслятор без `RELAY_COMMANDS_ENABLED=1`;
- 401 — інший токен;
- відновлення курсору — перезапуск ретранслятора з тим самим `RELAY_DATA_DIR` (id продовжуються).

Повна самоперевірка ретранслятора: `python3 simulator.py` (без аргументів) → `SELF-TEST PASSED`.

## 11. Обмеження й відкриті питання

| Питання | Стан | Що робити в модулі |
|---|---|---|
| Поведінка `stop` і пари «Ручний + Стоп» | не перевірено на контролері (перевірка з відповідальним ще попереду) | реалізувати за 8.4, підтвердження `stop` — за `genset_status == 0`; бути готовим уточнити |
| Значення `ats_status` | у протоколі немає таблиці | показувати код, не інтерпретувати |
| `aux_input_2`, `aux_output_4` активні | призначення невідоме | показувати як «Вхід 2 / Вихід 4» |
| Лічильник ТО (`maint_h`/`maint_min`) = 0 | схоже, вимкнений у контролері | не будувати на ньому тривог |
| GPS модуля | шле нереальні координати; в API не виводиться | не використовувати |
| Отримувач тривог | не визначений | налаштовуваний (користувачі/канал) |
| Інші джерела керування | застосунок SmartGen і кнопки контролера змінюють режим поза Odoo | фактичний режим — лише з показань; зміни «не від Odoo» показувати в подіях |
| Версія ретранслятора | на сервері 1.1.1; 1.1.3 додає 5 полів (5.1) | не покладатися на ці поля |

## 12. Безпека

- Токен — лише в `ir.config_parameter` з доступом адміністраторів; у логи й повідомлення не виводити.
- Тільки HTTPS; перевірку сертифіката не вимикати.
- Ретранслятор не зберігає облікових даних Odoo і сам в Odoo не звертається.
- Будь-яка команда з API — це реальна дія на генераторі офісу. Права на кнопки керування й особливо на `mains_close_open` / `gen_close_open` — продумати (за погодженням: керувати можуть усі, але з журналом).
