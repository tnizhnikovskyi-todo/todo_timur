# Changelog: f3d_collector

## 0.2.1 - виправлення за незалежним рев'ю 0.2.0

* HIGH: «отруєне» показання (Odoo стабільно відповідає HTTP 500) на голові FIFO вічно блокувало чергу: пакет
  зменшувався до 1, але відкидання вимагало `_cap_ok` (успіх, поки пакет зменшено), а «жива» черга ставала лише після
  успіху. Тепер єдине показання після 5 поспіль HTTP 500/413 відкидається, якщо Odoo живий (`GET /health` або інші
  пакети проходять), незалежно від `_cap_ok`; лог `ERROR` з `code`/`ts`/`value`, `Pusher.poisoned_total` і
  `buffer.poisoned_total` у статусі (Odoo зайві ключі ігнорує). Стан зменшення пакета й лічильник невдач — окремо для
  потоків «голова»/«живі»; коли черга відстає, після невдачі йде «живий» пакет, а не повтор тієї самої голови.
* HIGH: HTTP 413 `too_many_readings` (параметр Odoo `td.telemetry.push_max_readings` менший за `F3D_PUSH_MAX`)
  вважався «відхиленим» і увесь пакет видалявся (втрата даних). Тепер 413 пакет НЕ видаляє: ліміт запам'ятовується
  (`Pusher.server_limit`, половина пакета), пакет шлеться повторно меншим; після 200 успішних пакетів на ліміті він
  пробує подвоїтися. Одне показання з 413 — «отруєне» (див. вище). Odoo ліміт у конфігу не віддає (див. нотатки).
* MED: пакет ділився навпіл на будь-якій помилці без статусу, зокрема «connection refused» (рестарт Odoo: 1000 → 31,
  відновлення ~10 подвоєнь). Тепер зменшення — лише для 5xx, 408, таймаутів і обриву з боку сервера
  (`OdooError.shrinkable`).
* MED: `Emitter.flush` губив батч при `CancelledError` (зупинка) чи будь-якому не-sqlite винятку: тепер
  `except BaseException` повертає дані в чергу й піднімає виняток далі.
* MED: черга Emitter у пам'яті при недоступному буфері (диск повний) до 500 000 показань (~150-250 МБ) -> 50 000
  (події — 5 000), найстаріші відкидаються з `ERROR` (не частіше за раз на 60 с) і метрикою `collector_buffer_dropped`.
* LOW: вік черги (політика «відстає») рахується від часу вставки в буфер (`readings.ins`, міграція `ALTER TABLE` для
  старих файлів; рядки без `ins` — за `ts`), а не від `ts` показання: годинники пристроїв (`ts_path` у MQTT) більше
  не тримають `behind=True` вічно.
* LOW: при зупинці (`_flush`) і в `drain-buffer` пакети йдуть з паузою `F3D_PUSH_BACKLOG_GAP_S` від попередньої
  відправки (`Pusher.backlog_pause`), при зупинці — не більше 5 пакетів: рестарт не впирається в 429.
* LOW: файл буфера без `auto_vacuum=INCREMENTAL` (створений до 0.2.0) один раз конвертується `VACUUM` при відкритті,
  якщо рядків ≤ 10 000 і на диску ≥ 2 × корисний обсяг + 32 МБ; для більшого файлу — разова ручна команда з README.
* Тести: `tests/unit/test_regress_021.py` (24 регресії, 23 падають на 0.2.0); фікстура `buffer` працює на
  віртуальному годиннику; тест `test_run_loop_survives_unexpected_error` більше не скасовує задачу посеред `ack`.

## 0.2.0 - буфер і відправка після інциденту «колектор завис на ~30 год»

Інцидент стенда: лог «buffer limit exceeded: dropped 10000 oldest readings» + «database table is locked», цикли
опитування 1,8-1,9 с при періоді 1 с, буфер 209 МБ / 3 млн рядків, Odoo не отримував нових показань, `/health`
показував `buffer_rows: 66`.

Корінь проблеми:

* одне з'єднання aiosqlite ділили опитування, Emitter, Pusher, обслуговування й HTTP push; відкритий курсор `take()`
  однієї задачі й `PRAGMA incremental_vacuum` (в `enforce_limit`) іншої давали SQLITE_LOCKED «database table is
  locked»; виняток вбивав задачу (обслуговування, Pusher, Emitter) без перезапуску;
* `enforce_limit` викликався всередині `put_many` у циклі опитування (checkpoint TRUNCATE + vacuum + `DELETE` по
  10 000 рядків на кожен крок) і `COUNT(*)` по 3 млн рядків двічі за цикл відправки — усе в одному потоці БД,
  звідси цикли по 1,8 с і відставання від потоку показань;
* відправка завжди крутила найстаріше (FIFO), тож за великої черги нове не діставалося до Odoo; якщо `ack` падав
  після того, як Odoo прийняв пакет, той самий пакет слався знову;
* `/health` читав gauge, який ставив лише Pusher/обслуговування (після загибелі задач — застаріле значення).

Зміни:

* `Buffer`: усі операції серіалізовані `asyncio.Lock` і виконуються цілком (запит + читання + commit); WAL,
  `busy_timeout` 5 с, `journal_size_limit`, повтор тимчасових locked/busy без утримання Lock; лічильник рядків
  у пам'яті (`rows`, `count()` — O(1), `recount()` щохвилини); обрізання за корисним обсягом до 90 % ліміту
  партіями ≤ 10 000 рядків (окрема коротка транзакція, Lock відпускається між партіями), `incremental_vacuum(1000)`
  порціями; обрізання лише в задачі обслуговування, не в `put_many`; `take(newest=True)`, `oldest_ts()`.
* `Pusher`: `ack` рівно того, що прийняв Odoo, `_pending_ack` при помилці видалення (без повторної відправки);
  помилки буфера -> retry з бекофом; відставання черги > `F3D_PUSH_STALE_S` (600 с) -> пакети чергуються
  найновіші/найстаріші; кілька пакетів за інтервал при черзі (`F3D_PUSH_BACKLOG_GAP_S` = 1,25 с, < 60/хв);
  пакет, що не проходить, ділиться навпіл, «отруєне» показання (5 поспіль HTTP 500, інші пакети проходять)
  відкидається; `run()` не вмирає.
* `Collector`: фонові задачі під супервізором (перезапуск з бекофом 1...30 с); `/health`, `collector_buffer_rows`
  і статус читають справжній лічильник; конфіг Odoo (`push_interval_s`, `push_max`) має пріоритет над
  `F3D_PUSH_INTERVAL_S` / `F3D_PUSH_MAX` (env — запасні значення).
* `Emitter`: при помилці буфера показання лишаються в пам'яті (до 500 000) і записуються наступним `flush`.
* Налаштування: `F3D_PUSH_STALE_S`, `F3D_PUSH_BACKLOG_GAP_S`.
* Тести: `tests/unit/test_buffer.py` (конкурентні задачі, два потоки з двома з'єднаннями, лічильник, коротка
  обрізка), `tests/unit/test_push_backlog.py` (черга, живі дані, ack-відмова, конфіг Odoo, /health).
