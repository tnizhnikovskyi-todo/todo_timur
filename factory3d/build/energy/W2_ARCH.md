## 2. Техническая реализация

### 2.1 Место в системе и контракты

**Решение об упаковке (A-42).** GAP рекомендовал новый модуль; решение — **новый модуль `td_energy_control`** (LGPL-3, `application=False`), отдельно мост 3D `td_energy_viewer3d` (`auto_install`).

| Критерий | Расширение `td_energy` | Новый `td_energy_control` (решение) |
|---|---|---|
| Класс риска | читающее приложение получает путь записи в устройства | запись изолирована: нет модуля — нет пути управления; `meta.control_available=false` (W1 C-32 уже так задумано) |
| Жизненный цикл | удалить «управление» без «Энергетики» невозможно | отдельная установка/удаление; `uninstall_hook` сохраняет журнал в архивных таблицах |
| Зависимости | `td_energy` пришлось бы зависеть от `td_bms` и (мягко) `td_genset_factory3d` | только `td_energy_control` зависит от `td_bms`; `td_energy` остаётся лёгким |
| Предохранители | флаги `write_enabled`/`automation_enabled` размазаны по приложению | одно место, нейтрализация, `neutralize.sql` модуля |
| Тесты и регрессия | 208 тестов `td_energy` (142 + W1) затрагиваются каждым изменением управления | отдельный цикл; регрессия `td_energy` — проверка контрактов C-38/C-46 |
| Лицензия/владение | одинаковая (LGPL-3) | одинаковая; отдельная папка документов |
| Стоимость | меньше файлов манифеста | +манифест, +ACL (малые) |
| 3D | `td_energy` не может зависеть от `td_viewer3d` (JS-импорт сломал бы бандл) | отдельный мост по образцу `td_constructor_viewer3d` |

Разделение на `td_energy_control` + `td_energy_automation` отклонено: общие модели (`action`, `scenario`) и единый поток подтверждения.

**Граф зависимостей:**

```

                     ▲                │ (мягко, importlib/ir.module.module)

 services: collector ◀── plugin td_collector_energy        iot_sim (swbctl + модели)
```

`td_energy_control` — `depends`: `td_energy`, `td_telemetry`, `td_bms`. `td_energy_viewer3d` — `depends`: `td_energy`, `td_viewer3d`; `auto_install=True`.

### 2.5 Поток данных

**(а) Ручная команда (класс B, два лица).** 1) `en1` на плитке «Увімкнути QS» → `prepare('qs_close')` → `td.energy.action` `prepared`, токен, Odoo-проверки (`ats_parallel_lock`, `qs_current_ok` … из `td.signal.last_value`). 2) Диалог показывает «гаразд/не виконано/немає даних»; «Підтвердити (1/2)» → `confirm(token)` → состояние `awaiting_second`, уведомление `mail.activity` + шина. 3) `en2` → `confirm_second` → пересчёт проверок → `td.command` на `energy_control/intent` с `payload` (`action_id`, `idem`, `kind`, `params`). 4) Коллектор забирает команду (`GET /f3d/telemetry/commands`, ≤ `commands_poll_s`), `CommandLoop` вызывает `plugin.call()`; плагин синхронно проверяет схему/ресурс/жёсткие блокировки по свежим входам и возвращает `accepted=true` → `td.command` `done`, действие `executing`. 5) `Executor`: `qs_cmd=2` → верификация `qs_state=closed` ≤ 10 с (через `ctx.read_signal`) → `done`; API-25 `actions[]` (`done`, `result`) → `_td_close` → журнал, шина, `td_energy` `state` → Пульт обновляется. 6) Отказ контроллера (`qs_ack=2`) или блокировка → `failed/blocked` с причиной. 7) «Скасувати» → `undo` → обратное действие `qs_open` (класс B).

**(б) Автоматика.** `Engine` каждые 2 с: `Inputs` (из `LiveCache`) → сценарии в порядке `backup, peak, self, slots, chp, night, pfc` → запросы ресурсов → арбитраж (ручное перекрытие > сценарии) → `Actuator` (запись только при изменении, повторная запись принудительных режимов каждые `valid_s/3`) → `Reporter` (состояние/события раз в 10 с). Odoo превращает события в записи журнала `origin='auto'`, чипы сценариев — из чисел движка по шаблонам (R-43 п.5). Конфиг `GET config` каждые 10 с с `If-None-Match`; Odoo-изменения (`bump`) видны сборщику ≤ 10 с.

**(в) Слой 3D.** Просмотрщик запрашивает `/f3d/viewer/data` → провайдеры (seq 100 `energy`, seq 101 `energy_layer`) → `energy.layer` (узлы с состоянием `sld_state`, маркеры тревог). Живые обновления: канал `f3d_viewer` (события `td.energy`/сигналы) → `/f3d/viewer/delta` → `applyPatch` → `applyData` расширения → `repaintAll()` и перестроение маркеров (≤ 10 с). Клик по узлу → `cardBlocks` → «Відкрити картку вузла» → `td_energy.node_card`. Из Пульта «Відкрити в 3D» → `action_td_open_3d` → `f3d_viewer.action` (`layers`, `mode='td_energy'`, `code`).

### 2.6 Безопасность

- **Группы:** без новых (E-06): `group_td_energy_manager` («Енергетик»), `group_td_energy_chief` («Головний енергетик»), `group_td_energy_user`, администратор. Класс A — «Енергетик»; класс B — «Головний енергетик» или второе подтверждение другим лицом (SPEC R-39, матрица 4.2).
- **Предохранители (шесть):** `td.telemetry.write_enabled` → `td.energy_control.write_enabled` → `td.source.write_enabled` → `td.signal.write_enabled` → `F3D_WRITE_ENABLED` коллектора; для автоматики дополнительно `td.energy_control.automation_enabled`. По умолчанию все `False`; `neutralize.sql`; `_td_enable_stand` — только вручную.
- **Семантика блокировок.** Две реализации одного реестра: Odoo (подсказка в диалоге, `confirm` блокируется) и сборщик (**жёсткое выполнение**, перед первым и активирующим шагами). `hard+fail` блокирует; `hard+unknown+fail_closed` блокирует (нет данных = опасно); мягкие — только предупреждение; конфиг лишь сужает границы кода. Золотые случаи (SPEC R-41 п.5) — общий контракт обеих реализаций.
- **Токены и подтверждения.** Токен 24 байта, в БД — `sha256`; TTL 60 с; принадлежит пользователю; `confirm` идемпотентен (`FOR UPDATE`, `idem`); второе подтверждение — другое лицо, TTL 600 с, без обхода администратором.
- **Тайм-ауты:** токен 60 с; второе подтверждение 600 с; команда в очереди 120 с; `call()` ≤ 1 с (только приём; ядро 10 с); выполнение ≤ 60 с; шаг 8 с; верификация 10/15/30 с; heartbeat 30 с; применение конфига 60 с; отмена 15 мин; сторожевые таймеры BESS 30 с (автоматика) и сброса 60 с.
- **Идемпотентность (слоями):** токен/`idem` в Odoo; `idem` в `Store` сборщика (повтор → сохранённый результат); уровневые шаги (повтор безопасен); `event_id` для событий; состояния только «вперёд» (с исключением для `expired` по авторитетному отчёту сборщика).
- **Режимы отказов:** 18 строк SPEC R-53 (Odoo/сборщик/контроллер недоступны, местный режим, несвежие входы, дубль/потеря результата, падение во время принудительного режима, частичные шаги, верификация, конфликт ручного и авто, невалидный конфиг, расхождение часов, смена предохранителя, отказ устройства, частота записей, рестарт). Главный принцип: **при потере управления устройства возвращаются в автоматический режим сторожевыми таймерами**; КГУ, QS и уставка воздуха — физические состояния без таймера (возвращаются только явной командой/отменой).
- **Запрещено:** управление системами безопасности (три уровня, R-60), запись в `td_genset` (только адаптер), `x_`-поля, `safe_eval` над данными БД, секреты/стоимость в конфиге сборщика.

## 4. Инструкция

**4.1 Включить/выключить сценарий (Энергетик → второе лицо или Главный энергетик).** 1) «Енергетика → Керування». 2) На карточке сценария нажмите переключатель — откроется диалог «Сценарій «…»: увімкнути?». 3) «Виконати» (главный энергетик) или «Підтвердити (1/2)» (энергетик). 4) У второго энергетика на экране появится баннер «Очікує другого підтвердження» → «Підтвердити (2/2)» в течение 10 мин. 5) Чип меняется с «Очікує застосування» на актуальное состояние после ответа сборщика (≤ 15 с).

**4.2 Ручная команда с блокировками.** 1) Плитка → диалог с текстом и «Перевіркою блокувань». 2) «не виконано» (красное) или «немає даних» для жёсткой проверки — «Виконати» неактивно, прочитайте причину. 3) «Виконати» → состояния «Надіслано → Виконується → Виконано/Не виконано». 4) Результат и исполнитель — в «Журналі команд і перемикань».

**4.3 Изменить приоритеты сброса (Главный энергетик).** «Змінити порядок» → ↑/↓ → «Зберегти порядок» → подтверждение (класс B). Состав и параметры строк — «Налаштування → Пріоритети скидання». Критичные нагрузки добавить нельзя (допускается только частичное или условное снижение, SPEC M-30).

**4.4 Отменить действие.** В журнале у выполненного действия (до 15 мин) — «Скасувати дію»; для рекомендаций — «Скасувати» в зелёном баннере на Пульте. Отмена — отдельное действие с правами по её классу.

**4.5 «Збирач не на зв'язку» / «автоматику призупинено».** 1) Проверьте «Налаштування → Стан керування» (heartbeat, `engine_mode`, причина). 2) Контроллер в местном режиме — переведите переключатель в «Дистанційне». 3) Несвежие данные — «Телеметрія → Колектори». 4) Устройства сами возвращаются в автоматический режим (сторожевые таймеры); КГУ/QS проверьте вручную.

**4.6 Открыть в 3D.** Пульт → «Відкрити в 3D» (слой «Електромережа: стан вузлів», маркеры тревог) или узел схемы/карточка → «Показати в 3D» (подсветка). В 3D клик по узлу → «Відкрити картку вузла».

**4.7 Включение управления (администратор).** 1) Только после просмотра рисков (R1). 2) `td.telemetry.write_enabled`, `td.energy_control.write_enabled`, источники `MB-U73-SWB-CMD`/`ENERGY-CTL`, нужные сигналы (по таблице SPEC 5.6), для автоматики — `automation_enabled`. 3) Коллектор: `F3D_WRITE_ENABLED=true`. 4) Начинайте с одного сценария (`pfc`) в часы дежурства.
