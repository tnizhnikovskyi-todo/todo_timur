# IT-Enterprise: что известно и сможем ли мы писать на этой платформе как на Odoo

Стартовый документ для отдельного репозитория под IT-Enterprise (ITE). Собран по итогам разговора 20.10.2026.

Источники:
- **База знаний ITE-KB** (MCP-сервер, только чтение). Её собрали для команды внедрения Toyota.
- **Наша работа с Odoo 19** в репозитории `todo_timur` (папки `factory3d/`, `odoo_graph/`).

Ссылки на базу знаний даны как `doc_id` и тип источника. Типы источников описаны в §1.2.

## 1. Что такое IT-Enterprise

### 1.1 Продукт в общих чертах
- **Что это.** Украинская ERP-система одноимённого вендора. Платформа называется **ITnet2**.
- **Для кого.** Средние и крупные предприятия.
- **Что покрывает.**
  - бухгалтерский и налоговый учёт;
  - кадры и зарплата;
  - склад (ТМЦ), основные средства;
  - производство (планирование, PDM/техмаршруты);
  - закупки и тендеры (интеграция с публичными закупками и SmartTender);
  - электронный документооборот (SmartManager, электронный архив), договоры.
- **Варианты клиента:**
  - тонкий Windows-клиент (протоколы tcp/http);
  - веб-клиент IT.Web 2016, работает в браузере.

  Источник: help, doc_id=131648.

Общий фон выше написан по общим знаниям. Всё дальше подтверждено базой знаний.

### 1.2 База знаний ITE-KB
Из чего собрана (ite_guide):

| Источник | Что это | Надёжность |
|---|---|---|
| `instr` | инструкции, пройденные в живой системе | самая высокая |
| `help` | официальная справка вендора; в базе только первые ~500 символов темы, полный текст лежит на сервере ENTERPRISE-WEB | высокая, но неполная |
| `forms` | карточки форм: поля, типы, отчёты | |
| `code` | классы и методы декомпилированного ITnet2, работающие с БД | |
| `libs` | описания декомпилированных библиотек; частично построены автоматически по именам классов и namespace'ов | |
| `claude` | рабочие находки; подавать как «по наблюдениям» | гипотезы |

Приоритет при противоречиях: `instr > help > forms > code > claude`.

Свежесть: тексты и код по состоянию на сентябрь–октябрь 2026. Лучше всего покрыты бухучёт и зарплата, остальное в основном справкой и кодом.

Инструменты:
- `ite_search` — поиск. Запрос писать **по-украински**, коротко, бухгалтерскими терминами.
- `ite_get_document` — полный текст документа.
- `ite_form_fields` — поля формы или справочника.
- `ite_table_usage` — кто читает и пишет таблицу.
- `ite_find_class`, `ite_code_context` — класс и его вызовы.

## 2. Карта возможностей конкретной инсталляции

Источник: instr «0. Карта возможностей: что работает, а что нет», doc_id=134898.

### 2.1 Работает полностью, от документа до проводки
- **Касса:** выдача, поступление, подотчёт, возврат остатка и перерасхода.
- **ТМЦ:** поступление, списание, реализация, возвраты в обе стороны, инвентаризация.
- **Услуги:** оказанные и полученные.
- **ОС:** карточка, приход, ввод в эксплуатацию.
- **Валюта.**
- **НДС:** налоговая накладная и корректировка.
- **Начальные остатки.**
- **Отчётность:** ОСВ, анализ счёта, карточка счёта, журнал-ордер, шахматка.
- **Кадры и зарплата:**
  - личная карточка, назначение, штатное расписание, ежегодный отпуск, табель;
  - начисление, расчёт, НДФЛ, ЕСВ;
  - выплата через кассу (платёжная ведомость и расходный ордер);
  - проводки по зарплате, приложение 4ДФ.

  Работает только при открытом расчётном месяце. Без него не создаётся даже табель.

Проверка согласованности: в сводной ОСВ дебет равен кредиту.

### 2.2 Где упирается в настройки внедрения
Признак всегда один: документ создаётся, но расчёт молчит или пишет протокол о нехватке настроек.

| Участок | Причина |
|---|---|
| Банковская выписка | пустой счёт учёта: не задана привязка «банковский счёт → 311» |
| Износ ОС | метод ограничен перечнем объектов учёта |
| Закрытие месяца | регламентный документ привязан к устаревшей хозяйственной операции |
| Книга продаж | не задан отчётный месяц налогового учёта |
| Кадровые приказы | в базовом экране нет добавления; экраны по типам приказов падают с ошибкой (остальной кадровый контур работает) |
| Оклад в карточке | скрыт параметром доступа (`HRUSERGRP`); обход — разовое начисление |
| Военный сбор | вид расчёта есть, но в справочнике начислений и удержаний его нет |
| Больничные, расчёт по среднему, дополнительные отпуска | справочник соответствия ссылается на несуществующие виды начислений |
| Безналичная выплата | пустой справочник «Тип счёта» |
| Индексация | не заведены индексы инфляции |

### 2.3 Не внедрено совсем
- **Производство:** нет вариантов учёта для 23/26 и номенклатуры готовой продукции.
- **Взаимозачёт:** тип есть, ни одного проведённого примера.
- **МСФЗ:** справочники пустые.
- **Автотранспорт:** у хозяйственных операций нет статей.

Это не «сломано», а «не внедрено»: всё включается настройкой.

### 2.4 Полезные приметы
- **Ошибки «тихие».** Кнопка срабатывает, сообщения нет. Подсказку, какого поля или настройки не хватает, ищите в строке состояния внизу и на синих плашках над ней.
- **Ошибка 1713** («Недопустимая ширина поля или дробной части»). Пункт ведёт в старый слой (VFP), который веб-клиент не поддерживает (claude, doc_id=134557).
- **«Запись не найдена» на заведомо верном коде, и F10 не открывает справочник.** Список допустимых значений задан описанием экрана, а его не видно ни в справочниках, ни в правах.
- **«Пункт меню есть» ничего не гарантирует.** Меню строится из реестра, общего для всех инсталляций. Работоспособность зависит от данных настройки.
- **Порядок внедрения:** объект учёта → план счетов → аналитики счетов → подразделения и исполнители → варианты учёта для складских счетов → начальные остатки → документы.
- **Проверка участка до работы:** найти уже проведённый документ того же типа и посмотреть, какие поля в нём заполнены.

## 3. Архитектура (реконструкция)

Официального описания архитектуры в базе нет. Ниже — реконструкция по описаниям декомпилированных библиотек (`libs`) и наблюдениям на живой системе.

### 3.1 Слои

**1. Клиент — тонкий.** Вся логика на сервере. Пример: у диалогового движка Sted2 серверная часть — 4 047 методов, клиентская — 275 (libs, doc_id=124206). В БД клиент почти не ходит (doc_id=124210). Логика на клиенте только там, где без машины пользователя не обойтись (doc_id=124195):
- КЭП (ключ лежит у пользователя);
- оборудование через COM-порт (весы, сканеры, РРО);
- автотесты интерфейса.

**2. Сервер приложений.**
- Windows-служба `ITnet2.Server.Launcher.exe`, по одной на инстанс. В нашей инсталляции это `ITnetSvc.master` и `ITnetSvc.prom`, порт 8222 (claude, doc_id=134561).
- `ITnet2.Server.SessionCore`: сессия, настройки, лицензирование, ЭЦП, аудит изменений БД, OCR (doc_id=124280).
- Меню строит `MainMenuService` из таблиц `MENU`, `MNU`, `ARMM`, `MELU`, `UST`, `USTZ` (code, doc_id=108824).

**3. Бизнес-логика.**
- **`ITnet2.Server.BusinessLogic.Core`** — платформенный слой: 4 085 файлов, ~17 000 методов, 905 таблиц (doc_id=124230). В нём:
  - модель документа и её настройка (`Documents`, `DocumentConfig`);
  - пакеты конфигураций (`Configuration`): публикация, экспорт и импорт, SQLite-пакеты;
  - матрица ролей (`RolesMatrix`);
  - маршруты согласования (таблицы `AG*`);
  - шина событий (`EventModel`, `ServicesManagementSystem` — самый большой класс системы);
  - движок настраиваемых расчётов `ArbitraryCalculation`: формулы на динамических переменных, промежуточные результаты во временных таблицах;
  - НСИ и перекодировка справочников;
  - интеграции: обмен документами между организациями (`FileSharingService`), электронная ТТН, Kubernetes;
  - планировщик, бэкапы, встроенное тестирование конфигураций и отчётов (`Tests`).
- **Предметные модули** — отдельные сборки:
  - `BusinessLogic.LP` — тендеры (doc_id=124239);
  - `BusinessLogic.MP.PDM` — техмаршруты (doc_id=124248);
  - `BusinessLogic.FI` — бухгалтерия: создание проводок, ОС, XBRL, акцизы (doc_id=124233).
- **`Runtime.Methods`** — методы, привязанные к сущностям по коду таблицы: `DMZ`, `DMS`, `PLA`, `SP2`, `KSM`, `DOG`, `ORG`, `TASKS` (doc_id=124256, 124278). Платформа вызывает их динамически.
  - `F2<…>UserRequestMethod` — по действию пользователя (кнопка на форме);
  - `Anycall<…>AnyCallMethod` — откуда угодно: из конфигурации, формул, сценариев;
  - механизм лежит в `Server.Runtime.Methods` (64 файла), реализации — в `BusinessLogic.Runtime.Methods` (5 743 файла).

**4. Экраны строятся из метаданных** (doc_id=124203):
```
Client.Controls.ScrEdit          → пользователь рисует экран
Server.Dialogs.Menuget.Designer  → серверная часть дизайнера, сохраняет в SCRZ / SCRS
Server.Dialogs.Menuget           → ScreenBuilder + InputFormCodeGenerator
InputForm / InputForm2           → сгенерированные *Base-классы
InputForm/*.cs                   → кастомная логика наследуется от *Base
```
Работа с записью идёт через серверные курсоры `<Сущность>Cursor` (doc_id=124231). Следствие: часть ограничений сидит в описании экрана и не видна ни в правах, ни в справочниках.

**5. Доступ к данным** — `ITnet2.Server.Data` (doc_id=124269).
- Классы `DatabaseManager`, `SqlClientBase`, `SqlClient`, `MsSqlBase`: общая база и наследники под конкретную СУБД.
- По системным таблицам в коде видна поддержка **MS SQL, Oracle и PostgreSQL**. SQLite используется для локальных пакетов, ElasticSearch — для индексации.
- Таблицы названы короткими кодами:

  | Код | Что это |
  |---|---|
  | `DMZ` | шапка документа |
  | `DMT` | строки документа |
  | `ORG` | организации |
  | `OBJ` | объекты учёта |
  | `SP2` | справочник |
  | `DOG` | договоры |
  | `SYS` | системная таблица |

**6. Унаследованный слой Visual FoxPro.**
- Признаки в коде: `It9Handler`, `clearFoxResources` в `MainMenuService`.
- Часть функций есть только там, и веб-клиент их не выполняет:
  - отчёты «Анализа выполнения» в договорах;
  - весь кассовый контур розницы (claude, doc_id=205370);
  - запись `GODMEC_NAL`: .NET-код это поле только читает (claude, doc_id=135926).

### 3.2 Модель учёта: настройка, а не код
Цепочка: тип документа → хозяйственная операция (`STO`) → статьи (`STOT`) → проводки. Плюс варианты учёта и аналитики счетов.

«Не работает» здесь обычно значит «не настроено»: у операции нет статей или пустая привязка счёта.

Пример ручной операции: ТГО 9068 со статьями `005`, `010`, `015`, `099` (claude, doc_id=134555).

Известная особенность конфигурации — дубли статей. Пример: схема зарплаты 9545, статьи 210 и 265 дают двойную проводку `Дт 661 / Кт 3773` (claude, doc_id=137289, 137299).

### 3.3 Эксплуатация
- **Планировщик заданий — не служба сервера приложений.** Его раз в минуту запускает задание SQL Server Agent, стартуя клиента (`IT2Client2.exe`) под служебным пользователем. Сервер может работать, а планировщик стоять (instr, doc_id=124188; help, doc_id=131824).
- **Кэширование параметров доступа (`USTZ` / `VARUST`) — вопрос открыт.**
  - Инструкция: после изменения параметра нужен перезапуск службы.
  - Заметка от 04.10: перезапуск не помог (claude, doc_id=134561).
  - Заметка от 02.10: `MENUACCESS` читается при каждом обращении, а содержимое параметра — нет (doc_id=135215).

### 3.4 Чего мы не знаем
- Протокол и транспорт клиент–сервер.
- Типовую топологию развёртывания и масштабирование.
- Как именно пакеты конфигураций накатываются между инстансами и в каком формате архив.
- Как устроено лицензирование.
- Точную границу между .NET и FoxPro (видна только по симптомам).
- Клиентские веб-библиотеки: в основном не разобраны.

## 4. Механизмы доработки ITE

| Механизм | Что даёт | Источник |
|---|---|---|
| **Бібліотеки коду C#** | свои сборки на C#. Подключаются ссылкой «Посилання на збирання користувача» в RRT-методе, виде отображения, интерфейсе, конструкторе помощи, планировщике, экране | help, doc_id=132453 |
| **RRT-методы** | вызов своего кода на событие объекта (например, `ANYCALL` + `AFTERKMAT` — после ввода кода ТМЦ). Свой метод начинается с `_`; тип VFP или C#; у системных можно менять только «Скасовано», локальное условие и команды | help, doc_id=132241, 128321, 133829 |
| **Свои объекты и таблицы** | код начинается или заканчивается на `_` — аналог `x_` в Odoo | help, doc_id=132240 |
| **Бизнес-логика на C#** | в справочниках и конструкторах: класс с `override` базовых методов | help, doc_id=133994 |
| **Модели расчётов, ArbitraryCalculation** | формулы и методы после расчёта с кнопкой Compile | help, doc_id=134003 |
| **Конструктор экранов** | описание экрана в `SCRZ`/`SCRS` → генерация кода | libs, doc_id=124203 |
| **Пакеты конфигураций** | перенос изменений между базами (подробнее ниже) | help, doc_id=132707, 132719, 132685 |
| **Веб-сервисы** | публикация расчётов системы; список публикует администратор. Пакетный обмен: `IMPORT.LOADIMPORTEDDATA`, `IMPORT.STARTIMPORT`, `IMPORT.CHECKIMPORTRESULT`, `EXPORT.GETPACKETS`, `EXPORT.GETPACKAGEDATA`, `EXPORT.SETIMPORTSUCCESSFULMARK`, `EXPORT.STARTEXPORT` | help, doc_id=132581, 132829, 132833 |
| **Экспорт и импорт интерфейсов** | перенос готовых интерфейсов между базами (режим F2) | help, doc_id=134424 |

Как работают пакеты конфигураций:
1. Задаём «объект конфигурации» — набор сущностей.
2. Формируем пакет: снимок этих сущностей на момент формирования. Архив кладётся в служебный каталог сервера приложений.
3. Проводим пакет на целевой базе через реестр заявок или прямым импортом.

Режимы проведения: «только добавление и обновление» или «полная замена с удалением строк». Каталог экспорта на клиент задаёт параметр `GLCONFIG`.

Для платформы v11 вендор пишет, что сервисы общаются через HTTP, REST, GraphQL, gRPC, OAuth и единую шину сообщений (help, doc_id=131640).

## 5. Наш способ работы в Odoo и как он ложится на ITE

### 5.1 Что делаем в Odoo (репозиторий `todo_timur`)
1. **Сначала документы, потом код.** `factory3d/docs/DOC_STANDARD.md`: по `ARCHITECTURE.md` и `SPEC.md` (FR, AC с типом проверки, `ВІДКРИТЕ ПИТАННЯ Q-xx`) разработчик-агент пишет модуль без вопросов, а тестировщик-агент пишет тесты, не читая код.
2. **Доработка — исходники в git:** модули Odoo 19 (manifest, Python, XML) с конвенциями `f3d.*`, `f3d_*`, `factory3d.<module>.<param>`.
3. **Data-модуль без Python:** `factory3d_iot_sim` описывает модели `x_*` через XML-записи `ir.model` и `ir.model.fields`.
4. **Заливка и чтение данных скриптами через XML-RPC** (`plant/odoo_rpc.py`, `odoo_push.py`, `odoo_pull.py`). Внешние ID делают повторный запуск безопасным.
5. **`odoo_graph`:** граф кастомного слоя по метаданным `ir.*` и автоматический поиск проблем.
6. **Своя среда:** Odoo в docker compose плюс эмулятор оборудования.

### 5.2 Сопоставление

| В Odoo | Аналог в ITE | Переносится? |
|---|---|---|
| SPEC/ARCHITECTURE, FR/AC/Q, сборка агентами | то же; методика от платформы не зависит | **Да, полностью** |
| Python-модуль в git | C#: библиотеки кода, RRT-методы, бизнес-логика экранов | **Частично.** Код — текст, его можно писать и хранить в git. Но живёт он в базе и вносится через админ-интерфейс, установки «модулем» нет |
| data-модуль с `x_*` | свои таблицы, объекты, RRT-методы с `_`; учёт через хозяйственные операции и статьи | **По идее да**, прямой аналог |
| установка модуля на тест и прод | пакеты конфигураций | **Да, но вслепую:** формат архива неизвестен, собирать пакет из git пока не умеем |
| XML-RPC `execute_kw` к любой модели | веб-сервисы (каждый расчёт публикуется отдельно) и пакетный IMPORT/EXPORT | **Хуже:** универсального ORM-доступа нет |
| `odoo_graph` по `ir.*` | граф декомпилированного кода уже есть в ITE-KB; граф доработок можно строить по таблицам конфигурации | **Да**, если будет доступ на чтение к БД |
| docker-стенд | Windows-служба, MS SQL, лицензия, FoxPro-слой | **Сложно:** нужен стенд от заказчика или вендора |

### 5.3 Что мешает больше всего
1. **Нет обратной связи.** Odoo агент знает глубоко и может запустить локально. По ITE есть только база знаний: декомпилированный код и обрезанная справка. Живой системы и доступа к её БД у агента сейчас нет. Без стенда ошибки гарантированы: платформа часто падает молча, и ограничения прячутся в описаниях экранов.
2. **Источник правды — база, а не репозиторий.** Пока мы не умеем собирать или разбирать пакет конфигурации, git будет копией, а не оригиналом.
3. **Нет документированного API для своего C#-кода.** Базовые классы RRT-методов и экранов видны только через декомпиляцию (`ite_find_class`, `ite_code_context`).

## 6. План: пилот

**Цель:** проверить полный цикл «SPEC → код в git → внесение в тестовую базу → проверка» на одной маленькой доработке. Например, своя таблица плюс RRT-метод на C# для одного типа документа.

**Что нужно, чтобы работать почти как с Odoo:**
- [ ] Тестовый стенд ITE, до которого агент может дотянуться: веб-клиент через браузер (Playwright) или хотя бы чтение MS SQL.
- [ ] Один выгруженный пакет конфигурации — разобрать формат и научиться собирать его из git.
- [ ] Пара живых примеров своих RRT-методов или C#-библиотек — сверить API с декомпилированным кодом.
- [ ] Полный текст справки вендора по разделам «Адміністрування» (D-AD-ADM-*) и «API» (D-IS-API-*): в базе знаний он обрезан.

**Если стенда не будет:** агент пишет спецификации, код и инструкции, а вносит и проверяет человек. Это рабочий, но заметно более медленный цикл.

**Предлагаемая структура нового репозитория:**
```
docs/
  DOC_STANDARD.md        ← адаптация factory3d/docs/DOC_STANDARD.md под ITE
  ARCHITECTURE.md        ← платформа (раздел 3 этого файла), дополняется по мере проверки
  modules/<доработка>/ARCHITECTURE.md, SPEC.md
src/
  csharp/<библиотека>/   ← C#-код библиотек и RRT-методов (копия того, что внесено в базу)
  config/                ← разобранные пакеты конфигураций
tools/
  ite_graph/             ← аналог odoo_graph по таблицам конфигурации ITE
```
